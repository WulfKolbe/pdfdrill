## 2. appg roundtrip — MATCHES the task's expected figure

    $ .venv/bin/pdf2mmd2-appg-check roundtrip vol01:0 vol01:7
    scored 2916   skipped 1550
      |obs - pred| <= 0.005 bp: 2912 of 2916
      |obs - pred| <= 0.01  bp: 2912 of 2916
      |obs - pred| <= 0.03  bp: 2912 of 2916

**The invocation matters and T-0045's wording hides it.** The task says "the
appg roundtrip (vol01:0, vol01:7) gives 2912/2916", which reads as two samples.
It is THREE: the literal sample `roundtrip`, then `vol01:0` and `vol01:7`
(bench/README.md: `pdf2mmd2-appg-check roundtrip vol01:0 vol01:7`, 696
formulas, 12 workers, ~2 min). Run without `roundtrip` it gives **2605 of
2609, skipped 1417** — reproducibly, twice. The deltas are exactly the
round-trip sample's own contribution, which the README states as "Round-trip
alone: 307 of 307": 2916-2609 = 307 scored, 2912-2605 = 307 within, and
1550-1417 = 133 skipped. So the lower pair is not a regression, it is a
different question. Step 2 must compare 2912/2916 against the three-sample run,
or it will "lose" 307 pairs that were never asked for.

The 4 misses are the accented subscripts `X_{\bar k}` (Rule 12 makes the box
taller), as in F37 — documented, not new.

## 3. pytest -m slow — PASS (4 tests), exit 0

    ....                                                     [100%]
    exit=0

4 slow tests — `tests/ported/test_appg_tables.py`, `test_roundtrip.py` (x2) and
`test_fontmetrics.py` (the T-0038 check that the 155 generated font tables still
match what TeX reports) — LuaTeX round-trips, ~10 min.

**There is no "N passed" summary line, and that is not truncation.** pdf2mmd2's
own `addopts` is `-q -p no:cacheprovider -m 'not slow'`, so passing `-q` again
makes it `-qq`, which prints the progress line and suppresses the count.
Measured on a fast subset: one `-q` → "21 passed in 1.60s"; the extra `-q` → the
dots and nothing else. So `....` + `[100%]` + exit 0 IS the complete output of a
passing run. Written down because I first read a complete log as a killed one
and re-ran it twice for nothing — the exit code is the number that matters.

## Process note — a wrong diagnosis, corrected

I reported the three first runs as killed at session teardown. They were not:
all three had COMPLETED. `bench --check` had printed its verdict, `appg-check`
its summary, and `pytest -m slow` its complete `-qq` output. Two things fooled
me — the missing summary line above, and `pgrep -cf "pytest -m slow"` matching
my own diagnostic shell, because the pattern appears in that shell's own command
line. The re-runs cost CPU and changed nothing. The one real finding from the
detour stands: the appg invocation needs its third sample.

When waiting on a background run, key the guard on the LOG or on an exit-code
sentinel file, never on a process name that your own command line contains.
