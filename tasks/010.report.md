# 010 — Reference stub at first citation

## Status: implemented and tested as specified; the penev_A measurement surfaced
a population gap the brief's design does not cover (details below, flagged as
NEEDS_CONTEXT rather than guessed at).

## WHAT CHANGED

- `src/docmodel/modules/citation.py` — `CitationProcessor.process_objects`
  (new). Runs at model-build stage 2 (after every module's stage-1
  `create_object` calls, so all Citations `CitationProcessor` itself created
  already exist). Groups Citations by citekey; for every distinct key with no
  existing Reference, creates ONE `Reference` (`props`: `citekey`, `bibkey`,
  `stub: True`, `ref_source: "citation"`), anchored at that key's FIRST
  Citation's own surface Realization (same stream, same start/end anchor —
  literally reused, not a new anchor), and adds a `cites` Alignment from
  every Citation with that key to the new Reference (mirrors
  `bibliography.link_citations`'s edge shape). Counter:
  `reference_stubs_created`.

- `src/pdfdrill/bibliography.py`:
  - New `drop_dangling_cites(doc)` — removes `cites` Alignments whose right
    side no longer resolves to a Reference in the document; one that still
    resolves (typically a stub) survives. Used everywhere the old code
    blanket-cleared `cites` edges, so a stub's link survives a `--force`
    rebuild or a gold ingest instead of being destroyed and only sometimes
    relinked.
  - `add_reference_objects` (parsed References section, `cmd_bibliography`) —
    now looks up a stub by citekey first; if found, fills its props in place
    (drops `stub`, sets `ref_source: "text"`) and keeps its id/anchor;
    otherwise creates as before.
  - `ingest_bbl` (author's `.bbl`, `cmd_bibsource`) — same fill-in-place
    pattern; `ref_source` set to the `source` arg (`"bbl"`/`"bibitem"`).
  - `load_bibtex_file` (`.bib`, `cmd_bibsource` and the `restrict`-ed path) —
    already merged fields onto any pre-existing Reference by key; added the
    one-line stub-clearing step (`pop("stub")`, `ref_source: "bib"`) when the
    matched Reference was a stub.
  - `build_bibliography_from_source` docstring updated: "no References exist
    yet" → "no *non-stub* References exist yet" (a stub is not a guess to be
    protected against, it's the thing being filled).

- `src/pdfdrill/commands.py`:
  - `cmd_bibliography` — the "already ran" gate (`existing = [... Reference
    ...]`) now excludes stubs, so a document with only citation-stubs (i.e.
    every document, now, once a model is built) is not mistaken for one
    that's already been parsed. The `--force` drop path now only drops
    non-stub References and calls `drop_dangling_cites` instead of
    unconditionally wiping every `cites` edge.
  - `cmd_bibsource` — the "author's bibliography is authoritative, drop
    prior References" step now keeps stubs (so `ingest_bbl`/
    `load_bibtex_file` fill them) and uses `drop_dangling_cites`.
  - `cmd_bibfetch` (both the direct-API and the keyless-delegate path) — pops
    `stub` when an enrichment actually lands (`res["bibtex"]`/
    `res.get("bibtex")` truthy), so a bibfetch-filled stub reads as filled
    (`bibfetch` was explicitly named as a filler in the spec).

- `tests/test_reference_stub.py` (new, 4 tests) — a 3-line fixture
  (`[a]`, `[b]`, `[a, c]`): stub creation (3 distinct keys → 3 stubs, 4
  Citations), anchor-at-first-occurrence, every Citation linked via a
  `cites` Alignment carrying `citekey` (needed because two citations from a
  comma list share one line anchor and the Alignment's `props.citekey`, not
  its `Range`, is what disambiguates them), and the fill path
  (`add_reference_objects`) updating the stub in place while leaving the
  other two untouched.

No prop-contract change was needed: `docmodel/prop_contract.py`'s
`table_violations()` only flags a prop that's in the committed
`corpus_props.json` snapshot and absent from `docs/layers/PROPS.md`; `stub`
isn't in that snapshot (it's a walk of the library, last done for task 290,
not re-run here) so the check doesn't see it yet. `ref_source` already
existed with values `bib`/`bbl`/`bibitem`/`text`; `"citation"` is a new value
of an existing prop, not a new prop. `docs/layers/PROPS.md` is generated
(`tools/propstable.py`) from a corpus walk this task did not run — left
untouched per its own "never hand-edited" rule; see OPEN.

## THE MEASUREMENT — and the conflict it found

Backup first, per the brief:
`~/pdfdrill-library/penev_A/out/010/model.before.json` (+
`model.before.docpack.json`) — copied from `model.docmodel.json`/
`model.docpack.json` before touching anything.

`pdfdrill status penev_A.pdf` and the sidecar (`penev_A.drill.json`) were
checked for what supplied the "8 References" the brief's spec describes:
**no `BIBSOURCE_BUILT` fact, no `bibsource_*` evidence keys, and no `.bbl`/
`.bib` file anywhere under `~/pdfdrill-library/penev_A/` or in the extracted
`texzip/`** (this is a MathPix-sourced scan, not an arXiv LaTeX source — no
`texsrc/` dir either). `cmd_bibliography`'s own transition log shows every
past run found "0 entries" from the heuristic text parse. **The inputs that
supplied the 8 are not on disk; per the brief's instruction, this stops
there** — no bibsource/bibfetch re-run was attempted. Note also: the model
**currently has 0 References**, not 8 — a prior `model --force` (this repo's
known retraction gap, see below) had already dropped them before this task
started, so the "8" in the brief's spec is itself stale for this document's
present state (measure the premise — HANDOVER-RULES §1 rule 1).

Running `pdfdrill model penev_A.pdf --force` surfaced a second, more
important finding. `CitationProcessor` created **1** Citation, not 81:

    citation_added_by (in the BEFORE model): {"bibliography": 80, null: 1}

80 of the 81 Citations in the pre-existing model carry
`added_by: "bibliography"` — they were created by `pdfdrill bibliography`'s
`detect_author_year_citations`/`detect_author_year_in_objects` (this paper
cites `(Author, Year)`-style, not `[key]`-style; the one `CitationProcessor`
citation is `[dB]`, almost certainly a false-positive units abbreviation, not
a real citation). **`CitationProcessor.process_objects` — where this task's
stub-creation lives, per the brief's design — only ever sees the citations
`CitationProcessor` itself created at model-build time.** The other 51 keys'
citations don't exist yet at that point; they're created later, by a
different module, in a different command. Measured counts:

| state | Citations | distinct citekeys | References (stub) |
|---|---:|---:|---:|
| before any rebuild (backup) | 81 | 52 | 0 |
| after `model --force` alone | 1 | 1 | 1 (`dB`, stub) |
| after `model --force` + `bibliography --force` | 81 | 52 | 1 (`dB`, stub) |

**This is the NEEDS_CONTEXT finding**: the brief's design ("Citations are
created at model build time by `CitationProcessor`") does not hold for
penev_A — most of its Citations come from `pdfdrill/bibliography.py`'s
author-year detector, which runs later, in a separate command. As
implemented, task 010 correctly stubs every citekey `CitationProcessor`
itself creates (proven by the unit tests, 3-for-3 on the `[a]`/`[b]`/`[a,c]`
fixture), and the three bibliography-side creators correctly fill a stub in
place when one exists — but for a document whose citation style is
author-year, the "52 References == 52 distinct citekeys" target is **not**
met: only the 1 bracket-style key gets a stub; the 51 author-year keys still
have none. Reaching 52/52 for THIS document would need stub-creation to also
run wherever `detect_numeric_citations`/`detect_author_year_citations`/
`detect_author_year_in_objects` create Citations in `bibliography.py` — a
different module, a different pipeline stage (post-model, inside
`cmd_bibliography`, with its own `--force`/idempotency rules), which the
brief did not specify and this task did not implement, rather than guess at
the design. Script + numbers: `~/pdfdrill-library/penev_A/out/010/script.py`
→ `result.json` (re-run reproduces all four counted states, including a
second, self-consistent `model --force` → `bibliography --force` round trip
done to make the intermediate snapshot itself reproducible rather than
hand-transcribed from a terminal).

## WHAT WAS LOST by `model --force`, and how to restore

Object-type counts, before vs. immediately after `model --force`
(`out/010/model.before.json` vs `out/010/model.after_model_force.json`):
identical for every structural type (Page 22, Footnote 53, Table 1,
TableRow 15, TableCell 54, Sidenote 46, Toc 1, Abstract 1, Diagram 14,
Section 37, Picture 11, ListItem 4, Equation 116, Formula 674, Paragraph
222) — `model --force` only rebuilds from `lines.json`, and these are all
model-build objects, so they come back unchanged. The two that don't:
**Citation 81 → 1** and **Reference 0 → 1** (a new stub) — the retraction gap
already known and explicitly out of scope for this task
(HANDOVER-RULES §3, "Retraction task"): a `model --force` doesn't retract the
`BIBLIOGRAPHY_BUILT` fact or the Citations `pdfdrill bibliography` had added,
so `status` still claims bibliography is built while the objects it added
are gone. **Restore**: `pdfdrill bibliography penev_A.pdf --force` (done, as
part of this measurement) — regenerates the 80 author-year Citations
(`detect_author_year_citations`) and, if a gold `.bbl`/`.bib` existed,
`pdfdrill bibsource` would refill References the same way. The library
document was left in this restored state (81 Citations/52 keys/1 stub
Reference), not reverted to the pre-task backup — consistent with how prior
sessions have treated `~/pdfdrill-library` (regenerable, not archival); the
backup files remain at `out/010/` if the prior 0-Reference state is ever
wanted back.

## OPEN

- **The population gap above** (author-year/numeric Citations created by
  `pdfdrill/bibliography.py` bypass `CitationProcessor`'s stub pass
  entirely) is the main open item. Closing it for documents like penev_A
  needs a design decision this task did not make: where stub-creation should
  also run (a shared helper called from `detect_numeric_citations`,
  `detect_author_year_citations`, and `detect_author_year_in_objects`?), and
  how it interacts with those functions' own `--force`/rerun semantics
  (`cmd_bibliography`'s `--force` path already drops-and-recreates
  `added_by="bibliography"` Citations; a stub tied to one of those would need
  the same drop-and-preserve treatment `drop_dangling_cites` gives
  `cmd_bibsource`/`cmd_bibliography`'s Reference drop today).
- The retraction gap itself (HANDOVER-RULES §3) is unfixed, as instructed —
  `model --force` still drops Citations/References that a later command
  added without retracting the facts that claim they exist.
- `docs/layers/PROPS.md` / `corpus_props.json` do not yet list `stub`
  (new prop) or `ref_source: "citation"` (new value of an existing prop) —
  both require a `tools/propstable.py` run after a fresh corpus walk
  (`corpus_props.json`'s own provenance says "1350 model.docmodel.json under
  ~/pdfdrill-library", a scan this task did not perform). No test currently
  requires it (see WHAT CHANGED).
- `cmd_bibfetch`'s stub-clearing (both the API and keyless-delegate path) is
  implemented but has no dedicated new test — `tests/test_bibfetch_delegate.py`
  still covers its baseline behaviour and passed unchanged.
- Per the brief: no bibsource/bibfetch re-run was attempted for penev_A —
  the `.bbl`/`.bib`/`BIBSOURCE_BUILT` evidence that produced the original "8
  References" is not on disk.
