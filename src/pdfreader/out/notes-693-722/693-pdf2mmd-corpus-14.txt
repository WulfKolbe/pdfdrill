DEFECT 1 — THE UNICODE DIALECT
------------------------------
A publisher's maths font names its glyphs by CODEPOINT. STIXMath emits
`u1D460`, `u1D6FF`, `uni2032.var`; Computer Modern emits `s`, `delta`,
`prime`. The projection table only spoke the TeX dialect, so a correctly
read glyph was deferred for its name.

Measured as the single largest cause of deferral across three journal
papers: 48 glyphs on one document. The Mathematical Alphanumeric Symbols
block (U+1D400..U+1D7FF) encodes a letter WITH a style, so it decomposes --
U+1D460 is an italic `s`, which maths italic already means; U+1D6FF is
`\delta`; U+1D538 is `\mathbb{A}`.

    1-s2.0-...0565   30.7% -> 82.6%
    1-s2.0-...0274   36.4% -> 75.0%
    1-s2.0-...0171   63.4% -> 67.6%

DEFECT 2 — A SPACE WAS AN UNMAPPED GLYPH
----------------------------------------
15 `space` glyphs in Times-Roman deferred EVERY maths span in
generating_action_compilers -- 0% projected, with nothing wrong but the gaps
between the symbols.

Fixed. The document still reports 0%, and that is now an honest number: all
26 remaining deferrals are `script-or-multi-baseline`, a structural refusal
(stacked limits, matrices), not a glyph the reader failed to name. The two
cases were indistinguishable in the metric before.

ENVIRONMENT HAZARD
------------------
`bootstrap.sh` runs `pip install pdfminer.six` and OVERWROTE the glyph-name
fork in the shared interpreter, after which pdf2mmd raised
`'LTChar' object has no attribute 'invisible'`. The corpus above was run
from pdf2mmd's own venv. Any integration has to settle which pdfminer is on
the path -- 691 measured what the fork is worth (100.0% vs 1.3% glyph names
on Computer Modern), so silently losing it is a real regression.
