WHY THE CODE APPEARS TWICE ON PURPOSE
--------------------------------------
A form field's value is an APPEARANCE STREAM. pdftotext does not see it, a
reader cannot drag-select it, and grep over the PDF does not find it. Verified
here: before this change `pdftotext` over the whole report returned 0 codes
while all 55 fields held one.

After the change, `pdftotext -layout report.pdf | grep -oE "[CWSNK]\|[+-][0-9]+"`
returns 55 — every measured row, as text.

So the two are not redundant, they are different channels:

   type    for a human to read, select, copy, and for any text tool to find
   field   the UPDATE channel — fill_ink_fields.py rewrites it by name after a
           fresh inkdrill run, without recompiling the report

Both are produced from the same map, so they cannot disagree at build time.
They CAN drift afterwards: a re-run of fill_ink_fields.py updates the field and
not the type. That is the cost of the field being an update channel at all, and
it is the reason the type carries the build-time value rather than pretending
to be live.

HOW IT IS BUILT
---------------
   pdfdrill reporttex <pdf> --form --ink <fill_ink_fields --json dump>

   The ink map is required for the code (and for the bullet colour — see
   out/146): the residual class is measured FROM the finished PDF, so the first
   build has no code to print and prints none. 55 of 57 rows carry one; the two
   without are positions 56-57, the zip-truncation documented in out/144.
