THE DEFECT, AS GIVEN
----------------------
`fresh_ink()` (src/pdfdrill/inkreport.py:234) asks content questions about
a stored measurement before resuming instead of re-measuring. Before this
task it asked five (the docstring named four; `pages_bound`, 578, was a
fifth already in the code but not in the docstring's numbered list — fixed
as part of this task, see DOCSTRING below). NONE of them asked whether the
report BUILDER that produced the ink and the stamp is the one that would
run now. 463 (a profile change dropping a section) and 625 (a `\\` inside a
`p{}` cell that put every Scan image on a second line and made every
residual measure an empty cell, out/625.txt) both changed the report's
measured GEOMETRY while ink and stamp stayed mutually consistent and every
existing check passed. Three of the twenty-one documents 625 affected were
never manually re-measured and are the ones the published site still warns
about.

THE THREE CANDIDATES, WEIGHED
--------------------------------
1. Raw `commit` (build_stamp already records it, e.g. "503beea946aa").
   REJECTED. This branch takes many commits a day and almost none touch
   report geometry (see REAL-WORLD VALIDATION below for the verified
   count — FIX ROUND 1, BLOCKING FINDING 1 corrected an earlier wrong
   number here, given as "2 of 106 since 503beea9"). Comparing raw commits
   turns the resume into the mtime check 463 already replaced: it would
   fire on day one of every session regardless of what changed.
2. A hash of the whole file (report_tex.py) or of the generated .tex.
   REJECTED. The file mixes the layout engine with escaping, CJK/glyph
   handling, ink joining, image download and ~90 other functions; touching
   any of them invalidates a measurement whose geometry never moved — a
   whole-file hash is nearly as trigger-happy as the raw commit, for a
   different reason. The generated .tex is closer to the truth (identical
   bytes -> identical geometry, provably) but the measure build's .tex is
   not kept past the compile, and it ALSO changes on every re-rendered
   cell of MATH CONTENT, which is not geometry — as trigger-happy as the
   commit, again for a different reason.
3. A hash over the SOURCE of a NAMED set of functions (CHOSEN).
   `report_tex.GEOMETRY_FUNCS` — 16 functions (15 in the first pass; FIX
   ROUND 1, finding 2 added `_cellrect_row`, below), found by walking the 625
   incident backwards (it touched `crop_cell` and `_cellrect_table_open`
   exactly) and generalising the naming convention the rest of that
   subsystem already uses. Each one either emits a zref/savepos mark,
   decides a mark's position or size, or turns a compiled mark back into
   a rectangle (the READING half — `cellrect_from_aux`, `page_height_bp`
   — is included for the same reason: a change to how a mark is
   INTERPRETED is exactly as invalidating as a change to how it is
   EMITTED). `geometry_signature()` hashes the AST of each function's
   source, not its text, specifically so a comment or docstring edit (the
   exact shape of 625's own fix) changes nothing — proved directly in
   tests/test_geometry_signature.py::
   test_ast_dump_ignores_comments_and_whitespace_the_way_the_signature_relies_on.

   ONE FUNCTION FOUND AND DELIBERATELY LEFT OUT: `legend_foot`, despite
   `table_open` calling it and despite `_table_record`'s own docstring
   naming a row it can cost a lattice. Traced three call sites
   (commands.py: the measure build always calls `cmd_reporttex(...,
   legend=False, ...)`, and the SAME `legend` value reaches both
   `write_build_stamp` and `build_report`'s `legend_on`) to confirm a
   measure build never calls `legend_foot` at all — its source cannot
   affect anything a measurement reads. Named in a comment on
   `GEOMETRY_FUNCS` rather than left for the next reader to rediscover.

   FIX ROUND 1, BLOCKING FINDING 2 — A SECOND FUNCTION FOUND, NOT LEFT
   OUT, PULLED OUT AND NAMED: `build_report`'s hand-built Image-regions
   (DIA) table called `_cellrect_marks`/`_rule_mark`/`_cellrect_col_marks`
   directly, inline, in the same order and with the same `rule_below_key`
   bookkeeping `row()` used to carry inline — an independent SECOND copy
   of the identical sequence, outside GEOMETRY_FUNCS and outside the
   naming-pattern guard (it was never a named function at all). Its own
   in-code comment already named this defect class once (607C: "this
   table is hand-built and never passes through row(), which is why its
   rows carried no marks and the manifest read 28 rows in 2 tables where
   the document has 34 in 3") — the methodology of this task (walk 625
   backwards) covered 625 and 463 but not 607C, though it sits in the same
   file and the same subsystem.

   FIXED, not just disclosed, per the 669 sibling task's own lesson
   (three independent copies of "does this row render" were found one
   call site at a time; the fix was to make the shared judgement TOTAL,
   not to patch the third site and stop): the whole sequence is now ONE
   function, `_cellrect_row(title, cells)`, extracted from `row()`. `row()`
   and the DIA table both call it; neither reimplements it. `_cellrect_row`
   is IN GEOMETRY_FUNCS (16 names now) and its name matches the existing
   `cellrect` naming pattern, so the guard reaches it directly — unlike
   `row`, which still cannot be reached by any naming pattern and remains
   the one named exception.

   SEARCHED ONCE MORE FOR A THIRD SITE, as asked: grepped the whole module
   for every direct caller of `_cellrect_marks(`/`_rule_mark(`/
   `_cellrect_col_marks(`. After the fix, each has exactly one call site
   — inside `_cellrect_row` itself (pinned by
   test_no_third_call_site_for_the_row_marking_sequence). There is a
   THIRD and FOURTH direct caller of two OTHER primitives,
   `_cellrect_table_open`/`_cellrect_header_mark` (the DIA table's own
   header, separately from `table_open()`'s) — named explicitly as NOT the
   same defect class: that is direct reuse of an already-hashed primitive
   with no additional judgement or bookkeeping duplicated around it, the
   same way any other single call to a GEOMETRY_FUNCS function is, not a
   second implementation of a sequence. `build_report` itself stays OUT of
   GEOMETRY_FUNCS (including it would reintroduce the whole-file
   over-triggering candidate 2 rejects) — the fix is that its own
   mark-emission judgement no longer exists independently inside it.

   End-to-end coverage, not only the unit-level extraction test:
   test_dia_row_carries_cellrect_marks_end_to_end (tests/test_report_tex.py)
   builds a real report through `build_report(cellrect=True)` with one EQ
   row and one DIA row and confirms both carry a mark in `_CELLRECT["map"]`
   — proving the fix through the real pipeline, not only against
   `_cellrect_row` called directly.

THE GUARD
-----------
Two tests, not one, because a hash needs both directions pinned:
  - test_every_function_matching_the_known_geometry_naming_patterns_is_named
    — scans report_tex.py for every function matching the SAME naming
    patterns the 16 already use (cellrect/crop_cell/_img_cell/col_widths/
    table_open/_rule_/page_height_bp/auto_px2mm) and fails if one is not in
    GEOMETRY_FUNCS. This is the "future file that should be in the set does
    not silently sit outside it" guard the brief asked for, run as CODE
    against the real module rather than trusted to a person's memory.
  - test_geometry_funcs_is_exactly_the_reviewed_set — pins the tuple's
    CONTENT (order-independent), so a change to it is a diff to THIS test,
    not a silent edit three files away.
Named limit, not a silent one: `row` is in GEOMETRY_FUNCS (it calls every
mark emitter in a fixed order and decides whether an image column exists)
but matches no naming pattern — a generic word no pattern could single out
without also matching unrelated functions. A same-shaped function shipped
under an unrelated name would ship outside both the pattern and the guard —
which is exactly how the DIA table's own inline copy escaped notice the
first time (FIX ROUND 1, finding 2). Extracting it into `_cellrect_row`
and naming that IN both the tuple and the pattern's reach removes that
specific instance from the blind spot; `row` remains the one standing
example the guard is honest about not being able to catch on its own.

TWO NON-FUNCTION INPUTS, NAMED (FIX ROUND 1, MINOR FINDING 9 — one of
these was already hashed but undocumented; the other is new this round):
`CELLRECT_PREAMBLE` (the zref/savepos LaTeX macros that make every mark
possible at all) and `font_metrics_preamble()` (FIX ROUND 1, MINOR
FINDING 3's fix — see below) are folded into the hash directly, since
neither is a function and neither can sit in GEOMETRY_FUNCS. Both are now
named in `geometry_signature`'s own docstring, closing the "hash it but
don't say so" gap the review found in the first pass.

FIX ROUND 1, MINOR FINDING 3 — A REPEAT OF 665 NOW HAS SOMETHING TO CATCH
IT. The first pass disclosed that `PREAMBLE` (fonts, packages, the margin)
sits outside GEOMETRY_FUNCS but did not answer the review's specific
follow-up: "if excluding it is defensible, say what would catch a repeat
of 665." Task 665 (`abf0a996`, before this task's own base) changed
`\usepackage{fontspec}` to `\usepackage[no-math]{fontspec}` — one line,
inside `PREAMBLE`, that repointed every math glyph's font and could push
a cell onto an extra line exactly the way 625 did, without touching any
GEOMETRY_FUNCS function.

Applied the SAME technique GEOMETRY_FUNCS itself uses — a named, reviewed
subset, not the whole file — to `PREAMBLE`: `report_tex.
font_metrics_preamble()` extracts exactly the five lines 665 touched
(`\usepackage[no-math]{fontspec}`, `\setmainfont`, `\setmonofont`, the two
`\newfontfamily` declarations) from the LIVE `PREAMBLE` string by pattern,
rather than duplicating them as a second literal that could drift out of
sync. `PREAMBLE` itself and every one of its call sites are UNTOUCHED —
no build-time behaviour changes; only `geometry_signature()` reads more.
test_a_665_style_preamble_edit_moves_the_signature reproduces 665's actual
one-line edit against this extraction and confirms the signature moves.

Still deliberately NOT the rest of `PREAMBLE` (package guards, the
Unicode-fallback table, the margin) — those churn for reasons unrelated to
glyph metrics far more often than not, and hashing all of it would cost a
remeasurement for every one of those, not just a repeat of 665, which is
the same over-triggering GEOMETRY_FUNCS itself exists to avoid. The
guarded Bengali fallback (`\IfFontExistsTF{Noto Sans
Bengali}{\newfontfamily...}`) is named as a residual gap rather than
silently included or excluded: lower risk (one script, already
conditional on font availability) than the four lines that started 665,
and out of `font_metrics_preamble`'s current pattern.

WHAT HAPPENS WHEN THE SIXTH QUESTION SAYS NO
-----------------------------------------------
Refuses, and says why, through the existing `why` list — the same
mechanism the other five questions use, so a caller printing `why[0]`
(commands.py's `_inkreport_chain` already does, at the "NO RESUME" line)
gets a sentence naming the mismatch rather than a bare False.

MISSING is NOT skipped, unlike the model check beside it. `model_state`'s
check (`if cur and was and cur != was`) treats an absent `model_sha256` as
unknown-therefore-pass, which is correct THERE — a stamp older than 435
predates model-tracking entirely and nothing was known to be wrong with
it. Doing the same here would reopen exactly the loophole 625 exploited,
generalised from "no known defect at the time" to "the field a live
incident was named for": every stamp on disk today predates this check by
construction, so "not recorded, therefore assume unchanged" would wave all
of them through on the very first run, undoing the whole point. This is
the one place this task deliberately diverges from the sibling check's own
convention, and says why rather than copying it silently.

A DELIBERATE OVERRIDE EXISTS: `accept_stale_geometry=False` (default),
threaded through `fresh_ink` -> `_inkreport_chain`/`cmd_residuals`/
`cmd_inkreport` -> `--accept-stale-geometry` on `residuals`/`inkreport`.
It overrides ONLY the sixth question — proved by
test_accept_stale_geometry_does_not_paper_over_a_DIFFERENT_defect, which

operator who sets it is asserting they checked, not asking the tool to
guess.
