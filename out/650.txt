  THE MECHANISM (found by tracing one object end to end, not by reading the
  existing 650 comment and trusting it — that comment names the SHAPE but
  the actual defect is one level deeper than it says):

  1. `cmd_model` (src/pdfdrill/commands.py ~4900) already calls
     `heading_cleanup.extract_footnote_paragraphs` once, unconditionally,
     right after `docmodel.main.run()` returns — NOT only via `pdfdrill
     clean`. On penev_A this lifts the labelled footnotes out of a
     Paragraph that `ParagraphProcessor` had merged with unrelated trailing
     prose (a `footnote`-typed line breaks paragraph grouping, but its
     CHILD lines are typed `text` — an ordinary PROSE type — so nothing
     stops the very next real paragraph's lines from riding along in the
     same group). `extract_footnote_paragraphs` correctly shortens
     `Paragraph.props["text"]` to just the surviving prose ("sensory
     stimulus \(\phi\)...", 92 of the original 1183 chars) — but does
     NOTHING to the Paragraph's `surface` Realization on `mathpix_lines`,
     which still spans all 14 original anchors (footnote text included).
  2. `pdfdrill clean` (the drill's own `clean` step) calls
     `extract_footnote_paragraphs` again (no-op now — the footnotetext is
     gone from `props["text"]`) and then `materialize_transclusions`.
     `materialize_transclusions` rebuilds a paragraph's text from the
     TiddlyWiki projector's OWN rendering (`_projected_paragraphs` ->
     `TiddlyWikiProjector._transclude_paragraph`) — and THAT function reads
     the Paragraph's `surface` Realization directly (`stream.slice_anchors
     (surface.start, surface.end)`), never `props["text"]`. Confirmed live
     (a controlled experiment against a fresh `model --force` build,
     src/docmodel/modules/paragraph.py + heading_cleanup, no drill): the
     module docstring's claim "the projector rebuilds transclusions from the
     immutable source STREAM, so this is idempotent" is true of the stream
     and false of the claim — the REALIZATION (an anchor SPAN into that
     stream, recorded on the object) is what actually gets read, and it is
     stale.
  3. So `materialize_transclusions` re-renders the FULL original 14-anchor
     span, including the already-extracted footnote content — now with its
     `\({ }^{N}\)` label replaced by `{{<fn>||FN}}` (the projector's own
     in-text footnote-marker substitution, since a real Footnote object now
     exists for that number) — and overwrites `props["text"]` with it,
     undoing step 1's extraction.
  4. The NEXT `extract_footnote_paragraphs` (next drill's `clean`) finds
     `\footnotetext` in this text again, but `fsplit.split_bodies` can no
     longer find a `\({ }^{N}\)` label (it is now a `{{||FN}}` token), so the
     WHOLE block is treated as one refnum-less body — `adopt_target`'s
     (page, refnum, extent) match can never fire for a labelled Footnote
     from a refnum-less probe (638's own rule, deliberately) — and a fresh,
     unrecognisable duplicate is minted. Repeat every drill, unboundedly.

  Reproduced at unit scale (tests/test_footnote_dedup.py,
  `test_without_the_flag_materialize_would_have_reintroduced_it`): a
  `footnote` block immediately followed by trailing prose in the same
  ParagraphProcessor group, built through the REAL FootnoteProcessor +
  ParagraphProcessor + TiddlyWikiProjector, produces exactly this cycle when
  the fix's flag is stripped — 2 Footnotes for one printed body after one
  extract + materialize + extract round trip.

THE FIX (src/pdfdrill/heading_cleanup.py)
  `extract_footnote_paragraphs`: when a Paragraph's text is SHORTENED
  (its footnotetext span removed but prose survives), it now also sets
  `props["footnote_extracted"] = True` — the same "this field was edited,
  don't re-derive it" signal `text_source`/`is_translated` already give a
  translated paragraph, kept as its OWN flag rather than reusing
  `text_source` so a footnote-shortened paragraph is never mistaken for a
  translated one by `classify.has_translation`/`docinspect.
  element_translations` (both key on that exact twin; `merge_latex.py`
  already reuses `text_source` for a third, unrelated purpose, so a FOURTH
  meaning on the same key was judged one collision too many).

  `materialize_transclusions`: skips a Paragraph carrying
  `footnote_extracted`, exactly like it already skips a translated one —
  never re-derives from the stale `surface` Realization. Tradeoff, stated
  rather than hidden: such a paragraph's OWN surviving inline math (e.g.
  `\(\phi\)`) no longer gets transcluded to `{{||FO}}` for llmtext/semantic/
  markdown — a small, accepted quality cost against unbounded duplicate
  Footnote creation.

  `footnote_extent.adopt_target` (already in flight when this task started,
  kept as-is): accepts an empty `refnum`, but only ever merges a refnum-less
  body with ANOTHER refnum-less one — an empty refnum still never matches a
  numbered Footnote by extent alone (638's rule). Genuinely needed for the
  "a group with NO label at all" shape (docs/... penev_A page 6 has one);
  orthogonal to the mover above, which is about a LABELLED footnote's own
  paragraph residue, not an unlabelled body.

  Tests added (tests/test_footnote_dedup.py, appended). Exactly which fail
  without the fix, checked directly (not assumed — see fix round 1 below
  for how this table itself was corrected): `test_extract_shortens_text_
  and_flags_the_paragraph`, `test_materialize_never_reintroduces_an_
  already_extracted_footnote_body` (end-to-end, the REAL TiddlyWiki
  projector, no mock), `test_a_regenerated_unlabelled_paragraph_is_
  adopted_not_duplicated`, and `test_adopt_target_merges_two_refnum_less_
  extents_that_overlap` — all four fail on 7bc6f63b (pre-fix) with only the
  new test file overlaid, and pass post-fix. `test_without_the_flag_
  materialize_would_have_reintroduced_it` is NOT among these: it strips
  `footnote_extracted` itself before asserting, so it passes identically
  pre-fix and post-fix by construction — it pins the FLAG, not the fix (see
  fix round 1).
