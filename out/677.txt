677 — publishcheck was wrong in both directions at once

THE TOOL
--------
`docs/HANDOVER.md` says: "Run it before believing anything below."
`tools/publishcheck.py` answers one question — is what the site carries the
build that is on disk here — and it is the only automated answer to that
question. Two defects, both rule 22: a correct answer to a question that had
stopped being the right one.

DEFECT 1 — EIGHT OF TWENTY DOCUMENTS HAD NEVER BEEN CHECKED
------------------------------------------------------------
    docs = {k: (args.docs / k) for k in docs}          # the old line

The library folder is not the site slug. Task 462 renamed nine documents'
bibkeys WITHOUT renaming their folders — the slug `voloshin-hypergraph`
against the folder `Introduction to Graph and Hypergraph Theory (Vitaly I.
Voloshin) (Z-Library)`. So for every Z-Library book the path did not exist,
the document was reported `NO LOCAL BUILD`, and a verdict was printed anyway:

    NO LOCAL BUILD  cardona-qft-methods
    NO LOCAL BUILD  fong-spivak-invitation
    NO LOCAL BUILD  fong-spivak-seven-sketches
    NO LOCAL BUILD  gilmore-lie-groups
    NO LOCAL BUILD  johnston-linear-matrix-algebra
    NO LOCAL BUILD  kohlhase-omdoc
    NO LOCAL BUILD  lyche-numerical-linear-algebra
    NO LOCAL BUILD  mielke-geometrodynamics

Eight of twenty, every one a book. This is the SAME defect as the 2026-09-11
marks run, which resolved inkdrill's key by site slug and silently found
nothing for the same eight documents. The lesson did not travel from one tool
to the other because nothing made it.

THE FIX USES AN AUTHORITY THAT ALREADY EXISTS, NOT A TABLE. `tools/run295.py`
carries a hardcoded `SITE_ALIAS` map of nine entries; importing it would have
worked and would have been a tenth place to keep in sync. Instead:
`<bibkey>.tiddlers.json` is written beside every document, and the bibkey IS
the site slug (`report_tex.resolve_bibkey`: the model's `meta.bibkey` is what
`renamefolder` retargets and what every identifier is built from). One
directory listing per folder resolves it — no model load, no table. Verified:
20 of 20 site slugs resolve. A folder named for its slug still resolves that
way, so an arXiv document with no tiddlers file yet behaves as before, and a
slug that resolves to NOTHING is now named `UNRESOLVED` instead of being
counted as an absent build.

DEFECT 2 — IT COMPARED THE SITE AGAINST A FILE THE PUBLISH DOES NOT USE
-----------------------------------------------------------------------
634 added `<doc>/published/<f>`, a Ghostscript /ebook derivative, because the
originals totalled 947 MB against GitHub Pages' ~1 GB cap. 655's size budget
made the originals fit, the publish went back to copying them, and the
derivatives were left on disk to rot. `compare_document` still preferred
`published/<f>` whenever it existed.

Measured on voloshin-hypergraph, 2026-09-12 — all five site files are
byte-identical to the ORIGINALS and differ from all five derivatives:

    evidence-equation.pdf  orig de903eb0879c  deriv 7a7fc0162cdd  site de903eb0879c
    evidence-formula.pdf   orig 88131d001ce0  deriv a15c7ccf8750  site 88131d001ce0
    evidence-table.pdf     orig 92b9c0f8ce0c  deriv 3aa2075488ec  site 92b9c0f8ce0c
    evidence-image.pdf     orig c430980a1169  deriv de275950867c  site c430980a1169
    residuals.pdf          orig 99327e03ea7d  deriv ea4306fc33ca  site 99327e03ea7d

So twelve up-to-date documents were reported STALE, and the tool's verdict
("THE SITE IS NOT UP TO DATE") was true only by accident.

THE FIX DOES NOT SWAP ONE SILENT PREFERENCE FOR THE OTHER. Both candidates
are hashed, and the status SAYS WHICH ONE MATCHED — `same / original` or
`same / published/ derivative`. A check that cannot say which file it matched
cannot tell a publish from a coincidence. A `stale` line now carries all
three hashes. And a derivative that differs from its original is reported in
its own right as `LEFTOVER`, separately from the publish verdict, because
that rot is what made the tool measure the wrong file for weeks.

TESTS

===========================================================================
677 FIX ROUND 2 — the tuple was the blind spot, and it paid out twice
===========================================================================

`compare_document` compared only `gate.PUBLISHED_FILES` (five names). The
site carries TWELVE kinds per document:

    evidence-equation.pdf   evidence-formula.pdf
    evidence-table.pdf      evidence-image.pdf     residuals.pdf
    report.pdf              report.build.json      report.ink.json
    formula-report.html     inspect.html           tables.html   <slug>.md

Seven were never compared. HANDOVER-RULES rule 22 already names this exact
tuple as an unfixed blind spot — "is this the complete list of files this
document actually publishes now" — and today it paid out twice:

1. **`formula-report.html` would have shipped stale.** It is a COPY of
   `evidence-formula.html` (commands.py:9776-9782), and `cmd_evidence` builds
   ONE format — `"pdf" if pdf_out else "html"` (commands.py:5571). So
   `evidence --all-kinds --pdf` wrote four corrected PDFs and did not touch
   the HTML at all; the copy is refreshed only in HTML mode. Measured on
   0707.4470: `evidence-formula.html` 64,186 bytes at 20:54 yesterday against
   `formula-report.html` 137,466 bytes at 15:55 — two different stale
   generations sitting beside a PDF rebuilt today. `out/html_676.py` is the
   third pass.

2. **`residuals.pdf` would have shipped stale** — already recorded above.

THE FIX IS A UNION, NOT A LONGER TUPLE. Every name in `filenames` that exists
locally, plus every file the site already has for this document. Adding seven
names to `PUBLISHED_FILES` would fix today and rebuild the same blind spot for
the next artefact kind; and that tuple is also `publishready`'s "missing
artefact" list, so growing it would make an HTML file a publish prerequisite,
which is a different decision. A file on the site that nobody put in a list is
exactly the case that needs an answer, and now it gets one.

A file only the SITE has is still skipped rather than reported stale — there
is nothing on disk here to check it against. Both directions are tested.

WHAT 676 DOES *NOT* FIX, MEASURED
---------------------------------
`inspect.html` is UNCHANGED by 674/675/676, and the hope that republishing
would correct it is not met. `docinspect.py` references none of `inlinectx`,
`line_types`, `mathdelims` or host lines; it reads the model, and the model
was not rebuilt. Its own `fillProse` already splits `\(…\)` and `$…$` to
KaTeX, so that math was never broken there either.

A `\[…\]` gap in `fillProse`'s regex was noted as a defect and then
MEASURED: 0 display-math spans in prose objects across 6 published documents,
because display math becomes an Equation and never stays in prose text. Not a
defect; retracted rather than filed. (Rule 19 — write the number down before
the sentence.)

WHAT WOULD CORRECT INSPECT, AND WHAT IT COSTS
----------------------------------------------
Only a model rebuild removes the forbidden-line Formula objects from the
object tree inspect shows. Measured on kohlhase-omdoc: 20 of 458 formulas
would vanish, and **343 of the 438 survivors would get a different
identifier** (78%) because `math_titles` numbers by flow order over the
objects that exist. Every crop filename and every ink row keyed on those
identifiers would be wrong — `crop_sha256` (667) and `fresh_ink` (670) would
refuse, correctly.

THE ALTERNATIVE COSTS NOTHING AND IS THE USER'S OWN STATED NEXT STEP: FLAG
the object at creation instead of skipping it — `props["non_prose_host"] =
"table" | "caption" | …`. The object still exists, so numbering is untouched
and ZERO identifiers move; every gate reads one prop instead of recomputing;
inspect can show and filter it; and a model rebuild becomes safe. The user's
own words: "then we can have some flags that idendified formulas to be
reported and some not to be reported." That is a design change, so it is not
taken unilaterally today — it is the recommendation.
