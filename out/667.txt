DOES A RUNG ALONE ANSWER "IS THIS THE PICTURE I AM LOOKING AT"? NO.
------------------------------------------------------------------------------
   A rung (`reports.budget.CROP_LADDER`, `(scale, quality)`) says HOW a crop
   was re-encoded. It says nothing about WHICH crop -- two structurally
   different crops re-encoded at the same rung would still pass a rung-only
   check, and the rung the user asked to have recorded is, on THIS
   architecture, always the same constant value: `cmd_reporttex` (the
   MEASURE build, report.pdf) never calls `report_tex.scale_crops` --
   only `reports.crops.ensure_crops` does, for evidence-*.pdf/residuals.pdf --
   so every row the measure build embeds is unscaled by construction. Recording
   "rung: None" on every row is honest and traceable, but by itself it cannot
   distinguish "re-encoded, same picture" from "a different picture,
   coincidentally re-encoded the same way."

   WHAT I ADDED BEYOND IT: `crop_sha256` -- the sha256 of the SOURCE file in
   `report-crops/<id>.jpg`, the one file every rung of the ladder is derived
   FROM and which `scale_crops` never overwrites (it writes the scaled copy
   into the separate `report-crops-b/`). report.pdf always embeds this file
   directly; residuals.pdf embeds either this file or a re-encoded copy of
   it. Recording its identity, not the embedded PDF bytes, is what makes a
   rung difference and a genuine content change distinguishable: the same
   `crop_sha256` under two different rungs is exactly 666's finding (benign);
   a changed or vanished `crop_sha256` is the defect the gate exists to
   catch.

FIX ROUND 1 (REVIEW) -- THE VACUOUS PASS, MADE STRUCTURAL, ARGUED AGAINST
THE PRINCIPLE IT DEPARTS FROM
------------------------------------------------------------------------------
   `commands.py:1624-1628` states publish_ready's own principle: "a check
   that cannot see its input FAILS rather than passing quietly... the whole
   point of a gate is to be harder to satisfy than the thing it guards."
   Every other gate in reports/gate.py honours it. `crop_gate` does not: a
   row with no `crop_sha256` at all (measured before 667) passes, `ok=True`,
   rather than failing on absent evidence.

   THE ARGUMENT FOR DEPARTING. Failing outright on absent evidence, applied
   here, means every document measured before this task -- all of them,
   today -- goes from READY to NOT READY the moment this code ships, for a
   field that did not exist when they were measured and that nothing asked
   them to backfill. That is not "harder to satisfy than the thing it
   guards"; the "thing it guards" (a published row showing a picture nobody
   measured) has not become more likely to be true of any of these
   documents -- the CHECK became stricter, not the DOCUMENTS worse. Refusing
   on that basis would be the coverage-gate mistake in the opposite
   direction: 630B already establishes (gate.py, coverage_gate) that a row
   which is UNMEASURABLE BY NATURE (a straddling row) must not be treated as
   a row that fails measurement -- and a row measured under an OLDER SCHEMA
   is the same shape of exception: absent BY CONSTRUCTION, not absent
   because something went wrong.

   WHAT DOES NOT CHANGE. The principle is right for every gate that CAN see
   its input and chooses not to look, or looks and finds nothing -- that is
   exactly the failure mode 213 named (glyphs silently discarded) and every
   other gate here still refuses on it. `crop_gate` is not claiming that
   principle is wrong; it is claiming this ONE input (a field 667 itself
   introduces) is not "input the check failed to see", it is "input that
   does not exist yet for a reason unrelated to whether the guarded property
   holds."

   THE GAP THE REVIEWER NAMED. Granting the departure, `ok=True` still means
   two different things -- "compared, and it matched" vs. "nothing to
   compare" -- and only `detail`'s prose says which. A caller checking
   `if not ok:` cannot tell a verified pass from an unarmed one without
   parsing a string that this file makes no promise to keep stable.

   THE FIX. `gate.GateStatus`, a `tuple` subclass: still exactly `(ok,
   detail)` for every existing 2-tuple consumer (`ok, detail = gate(...)`,
   `checks[k][0]`/`[1]`, `for k, (ok, why) in checks.items()` -- unpacking a
   3-tuple where 2 are expected raises, so the shape had to stay a 2-tuple,
   not grow one), plus a `.verified` attribute: False when nothing was
   armed to check (both of `crop_gate`'s vacuous-pass branches), True when a
   row's crop was actually compared against disk -- whether that comparison
   passed or refused. A caller that wants the OLD gate's guarantee back
   ("this is meaningless unless verified") now has a structural test for it
   (`result.verified`) instead of a substring match on `detail`. Tests:
   tests/test_reports_gate.py::test_crop_gate_verified_flag_survives_a_bare_2tuple_unpack
   (the 2-tuple contract holds), and every crop_gate test now also asserts
   `.verified` (True on both the matching and the refusing real comparison,
   False on both no-rows and no-crop_sha256).

   Only `crop_gate` returns `GateStatus`; every other gate in this file is
   untouched and keeps returning a plain tuple, because none of them departs
   from the principle -- there was nothing for them to structurally flag.

THE SECOND FAILURE -- DECIDED: DOES NOT GET ITS OWN NEW GATE

   report.pdf that was overwritten 32 minutes later, still cited by a

   It does not, for a reason specific to this architecture: the MEASURE

   Sep 5 measurement, so `timestamp_gate` correctly reports READY on that
   axis; what was actually missing was per-row crop identity, which
   `crop_gate` now supplies and which -- unlike a whole-PDF-existence check

FIX ROUND 2 (REVIEW) -- THREADING `.verified` TO THE SURFACES A PERSON READS
------------------------------------------------------------------------------
   Round 1 made the distinction structural on `GateStatus` itself but never
   followed it past `reports.gate` -- a grep for `.verified` outside gate.py
   and its own test file found nothing. The four places that read
   `publish_ready()`'s checks dict all unpack or index `(ok, detail)` and
   discard the third thing: `commands.py`'s `handover_rows` (`blocked_by`/
   `reason`), `_inkreport_chain`'s step-7 ink summary ("FAILING" lines), and
   `cmd_publishready`'s own `--json` and printed output. Round 1's tests
   never exercised any of the four -- every one asserted on the GATE's
   return value, not on an OUTPUT surface, which is exactly why the gap
   survived a full review round.

   THREADED: `cmd_publishready`'s `--json` output now puts
   `"verified": getattr(v, "verified", None)` on every check (`None` for
   every gate but `crop`, which has no such concept -- an honest "not
   applicable", not a guess). Its printed line now marks a check `[un]`
   when `ok` is True and `verified` is False -- an unarmed pass, distinct
   from `[ok]` (a verified pass or a gate with no `.verified` at all) and
   `[  ]` (a refusal) -- so a person reading the line sees "unarmed"
   without it reading as a refusal, per the brief.

   NOT THREADED, DECIDED AND SAID WHY: `handover_rows`'s `blocked_by`/
   `reason` and the ink-summary's "FAILING" lines both iterate ONLY checks
   where `ok` is False. `crop_gate`'s only `verified=False` returns are
   both `ok=True` (the two vacuous-pass branches); every `ok=False` return
   is `verified=True` by construction -- a refusal is always verified. So
   neither loop is missing information by ignoring the attribute: there is
   no case where `.verified` would change what a FAILING check already
   says. Threading it in anyway would add a column no failing check can
   ever populate differently. Both sites got a one-paragraph comment
   recording this reasoning in place, so the next reader does not
   re-derive it.

   THE SILENT JSON DEGRADATION: `json.dumps(some_gate_status)` -- handing
   the tuple-subclass object DIRECTLY to `json.dumps` rather than reading
   its fields -- serialises `[ok, detail]` and drops `.verified` with no
   error, because `json` has no tuple-subclass hook. `cmd_publishready`
   never did this (it always built an explicit `{"ok":.., "detail":..}`
   dict, which is why threading `.verified` there was a one-line addition,
   not a rewrite), but nothing said the trap existed for the next caller
   who reaches for the obvious `json.dumps(v)`. Strengthened
   `GateStatus`'s docstring to name it explicitly and pinned it with
   `tests/test_reports_gate.py::test_gatestatus_json_dumps_silently_drops_verified_this_is_the_trap`
   -- `json.loads(json.dumps(GateStatus(True, "x", False))) == [True, "x"]`,
   asserted, so this stays a documented limitation rather than something
   rediscovered by losing data.

   NEW OUTPUT-SURFACE TESTS (not the gate's return value):
