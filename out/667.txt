DOES A RUNG ALONE ANSWER "IS THIS THE PICTURE I AM LOOKING AT"? NO.
------------------------------------------------------------------------------
   A rung (`reports.budget.CROP_LADDER`, `(scale, quality)`) says HOW a crop
   was re-encoded. It says nothing about WHICH crop -- two structurally
   different crops re-encoded at the same rung would still pass a rung-only
   check, and the rung the user asked to have recorded is, on THIS
   architecture, always the same constant value: `cmd_reporttex` (the
   MEASURE build, report.pdf) never calls `report_tex.scale_crops` --
   only `reports.crops.ensure_crops` does, for evidence-*.pdf/residuals.pdf --
   so every row the measure build embeds is unscaled by construction. Recording
   "rung: None" on every row is honest and traceable, but by itself it cannot
   distinguish "re-encoded, same picture" from "a different picture,
   coincidentally re-encoded the same way."

   WHAT I ADDED BEYOND IT: `crop_sha256` -- the sha256 of the SOURCE file in
   `report-crops/<id>.jpg`, the one file every rung of the ladder is derived
   FROM and which `scale_crops` never overwrites (it writes the scaled copy
   into the separate `report-crops-b/`). report.pdf always embeds this file
   directly; residuals.pdf embeds either this file or a re-encoded copy of
   it. Recording its identity, not the embedded PDF bytes, is what makes a
   rung difference and a genuine content change distinguishable: the same
   `crop_sha256` under two different rungs is exactly 666's finding (benign);
   a changed or vanished `crop_sha256` is the defect the gate exists to
   catch.

WHAT WAS BUILT
------------------------------------------------------------------------------
   `report_tex.crop_sha256(crops_dir, title, bibkey, history)` (new,
   src/pdfdrill/report_tex.py, beside `crop_file` which it reuses for the
   bibkey-rename fallback -- 264) -- sha256 of the resolved crop file, or
   None if there is no crop.

   `commands.cmd_inkconvert` (src/pdfdrill/commands.py) now writes
   `crop_sha256` and `rung` (always None today, for the reason above) onto
   EVERY row of the payload `inkconvert.convert` returns, before writing
   report.ink.json. `inkconvert.convert`/`convert_by_page` and
   `regionink.pair` (the three `measured_against` writers named in this
   task) are UNCHANGED -- the enrichment is additive, at the one call site
   that feeds the redrawn surface's report.ink.json, not a fourth pairing
   implementation.

   `reports.gate.crop_gate(doc_dir, bibkey="", history=None)` (new,
   src/pdfdrill/reports/gate.py) -- for every measured row that carries a
   `crop_sha256`, recomputes it against what's on disk NOW and refuses,
   NAMING THE IDENTIFIER, on a change or an absence. A row measured before
   667 carries no `crop_sha256` at all and passes vacuously (HANDOVER-RULES
   rule 5: absence is not evidence of a mismatch) rather than refusing every
   pre-existing measurement. Wired into `checklist()` under the key `"crop"`,
   which `publish_ready` already calls for every document carrying
   residuals.pdf -- one new key on the existing five-key surface, not a
   parallel gate.

   identity check and answers a question none of the three ask: not "is the
   PDF I measured still the PDF on disk" (all three ask exactly that, in
   different contexts) but "is the PICTURE this specific row shows still the
   picture I measured." I EXTENDED the existing infrastructure (reused
   `crop_file`'s bibkey-history resolution; added `crop_sha256` beside it)
   rather than writing a fourth whole-PDF sha comparison -- there already are
   three of those and a fourth was not needed.

THE SECOND FAILURE -- DECIDED: DOES NOT GET ITS OWN NEW GATE
------------------------------------------------------------------------------
   666 also found `report.ink.json`'s `measured_against` naming a 458-page
   report.pdf that was overwritten 32 minutes later, still cited by a
   residuals.pdf built 4 days after that. The task asked me to decide whether
   this belongs here.

   It does not, for a reason specific to this architecture: the MEASURE
   build is DELIBERATE scaffolding (`_inkreport_chain`'s own comment: "The
   measure build is scaffolding; the reading build is the artefact") --
   destroyed by construction on every single run, always, the moment the
   reading build replaces it. A gate that refuses whenever the measured PDF
   no longer exists under its own name would refuse EVERY published
   document, always -- it would not separate a real problem from the normal
   operation of the two-phase design, which is exactly the failure mode
   `gate.timestamp_gate`'s own docstring already names for the OLD
   PDF-checksum gate it replaced. What `timestamp_gate` compares instead --
   the MODEL's sha256/mtime -- is the right continuity check for "has the
   thing that was measured moved", and it already exists. Verified this is
   not a hidden false-pass: on johnston, the model has not changed since the
   Sep 5 measurement, so `timestamp_gate` correctly reports READY on that
   axis; what was actually missing was per-row crop identity, which
   `crop_gate` now supplies and which -- unlike a whole-PDF-existence check
   -- can genuinely tell a benign case from a bad one.
