THE THREE-STATE FIX (review finding 2)
  Round 1 rendered every non-"conserved" available row the same red
  `class="bad"`, whether the row carried a real anchor defect or was
  simply never audited against the 656 ratchet. `_status_conserve_ledger`
  already returns `has_baseline_row`; round 1's `_corpus_row_html` computed
  it and never read it. Fixed by giving the row ITS OWN state:

    ok         verdict == "conserved".
    unaudited  verdict != "conserved", AND unclaimed == 0 AND
               doubly_claimed == 0, AND NOT has_baseline_row. The ONLY
               thing wrong is an unbaselined violation type — no measured
               anchor defect at all. Rendered in its own colour
               (`--warn`, amber/orange, not red) with its own cell text
               ("unaudited — N unbaselined violation object(s), no
               baseline row recorded yet (0 unclaimed, 0 doubly-claimed)").
    bad        verdict != "conserved" and it is NOT the unaudited shape —
               i.e. a real unclaimed/doubly-claimed anchor (regardless of
               baseline status), OR a genuine regression against a
               baseline someone DID record (`new_types`/`increased` on an
               audited bibkey). Stays red.
    unavailable / errored   `conserve.available == False` — no model, a
               stale one, one skipped by the size guard, or (new) one this
               walk could not read at all. Both render the same dim/grey
               class (`unknown`) on the page — the reader-facing fact is
               the same ("no conservation number for this row") — but are
               counted SEPARATELY in the command's own prose (see below),
               because "the walk itself failed on this document" is a
               different, more actionable fact than "nobody has built a
               model yet."

  `_corpus_row_state(r)` is the ONE function that decides this, called by
  both the row HTML and the aggregate counts (`_corpus_state_counts`) — a
  second hand-rolled tally anywhere else is exactly the mechanism that
  produced finding 1's wrong narrative the first time, and this closes
  that seam rather than papering over its one visible symptom.

THE EXCEPTION ISOLATION FIX (review finding 3)
  Round 1's `corpus_status_rows` called `_corpus_status_row` directly in
  both loops with no try/except. `_status_conserve_ledger` pre-checks
  existence and staleness but does not itself guard `load_model`/
  `conserve`/`gate`/`ledger.materialize` against a corrupt or
  schema-mismatched model — a genuinely malformed `model.docmodel.json`
  (truncated write, bad JSON, an old schema `conserve()` cannot parse)
  would raise straight out of `cmd_corpusstatus`, aborting the ENTIRE walk
  and writing NO `index.html` at all — losing every row already computed
  for the other ~2,930 documents. `test_cwd_restored_even_when_the_
  gatherer_raises` (round 1) demonstrated the raise reaching all the way
  out; it is now rewritten to demonstrate the OPPOSITE (see TESTS).

  Fixed with one seam, `_corpus_row_or_error`, called from both loops in
  `corpus_status_rows`: `_corpus_status_row` wrapped in try/except, and on
  ANY exception a `_corpus_error_row` is appended instead — `errored:
  True`, `conserve.available: False`, `reason` naming the exception type
  and message, artefacts/folder computed defensively (each itself wrapped,
  so a broken `blob_dir` cannot cascade into a second, unhandled
  exception). Verified two ways, per the review's own request to show the
  handler working AND report what it did on the real corpus, separately:

    - CONSTRUCTED: `test_one_malformed_model_does_not_abort_the_whole_walk`
      writes a REAL invalid-JSON `model.docmodel.json` (not a monkeypatched
      stub) for one of three documents and confirms `cmd_corpusstatus`
      does NOT raise, `index.html` still gets all 3 rows, and the broken
      one reads `errored=True`, state `"errored"`, with the caught
      exception's type+message in its `reason`.
    - REAL CORPUS: re-ran the full walk on `~/pdfdrill-library` (2,931
      documents) AFTER this fix. **0 rows were caught by the exception
      handler on this run** (`errored_rows_on_this_real_run: 0` in
      `out/653b/report.json`, cross-checked against the actual
      `index.html` text — no row anywhere reads "errored — "). This is a
      fact about the CURRENT state of this library, not evidence the
      handler is inert: the constructed test above proves the handler
      fires and survives when a document IS unreadable; this run says none
      of the 2,931 documents encountered on THIS pass happened to be in
      that state (the 2 stale + 1 oversized are all caught earlier, by the
      existing staleness/size checks, before `_status_conserve_ledger`
      would ever raise on them).

THE RENDER-PHASE ISOLATION FIX (fix round 2 — new BLOCKING finding)
  Round 1 fixed the GATHER phase only. `_render_corpus_index_html`'s row
  loop — `body = "".join(_corpus_row_html(r) for r in rows)` — had no
  try/except at all, and neither did `_write_corpus_index_html`. A row that
  raised while being RENDERED (not gathered) would propagate straight out
  of `cmd_corpusstatus`, voiding the HTML write for every one of the other
  2,930 rows that had already been gathered successfully — the identical
  catastrophic failure finding 3 was raised to prevent, relocated one phase
  later in the same pipeline. No test exercised the render phase at all
  before this round.

  The defence that "it has not happened" is not a defence, for the same
  reason it was rejected for the gather phase: today's row shapes happen to
  carry every key `_corpus_row_html` reads. A future row shape (a new
  `conserve` field renamed, a `None` where a dict was assumed, a legacy row
  from an older schema) would hit this exact seam.

  Fixed with the render-phase twin of round 1's gather-phase mechanism:
    `_corpus_render_row_or_error(r)`   tries `_corpus_row_html(r)`; on ANY
                        exception returns `_corpus_row_render_error_html(r,
                        exc)` instead and reports `render_failed=True`.
    `_corpus_row_render_error_html(r, exc)`   a row that was gathered but
                        cannot be rendered must not vanish — it is shown,
                        with the bibkey (defensively re-read, never
                        trusting `r` is even a dict), the exception's
                        type+message, and a sentence making clear the row
                        WAS gathered and only rendering it failed. Built
                        with exactly 8 `<td>` cells — one per column the
                        header declares, `1 + 1 + 6` — never a `colspan`
                        cell: a `colspan` merges columns VISUALLY but does
                        NOT create the extra DOM children the inline JS
                        sorter's `a.children[idx]` reads, so a colspan row
                        would leave every later column with no cell to sort
                        on THIS row's account — the same "it happens not to
                        matter today" shape being fixed, recurring one line
                        lower if not watched for.
  Also hardened the sort script itself: `a.children[idx]`/`b.children[idx]`
  are now null-checked before `.getAttribute` is called, so even a FUTURE
  row shape with fewer than 8 cells cannot throw inside the click handler
  and silently break sorting for the whole page.

  The page's summary paragraph also used to fold `errored` into
  `unavailable` (minor finding alongside this one) — the headline sentence
  carried no separate count for it even though the per-row cell text and
  the CLI's own prose both did. Fixed: the summary now reads "...N
  conservation unavailable (no/stale/oversized model), and M could not be
  read at all (errored — its own number, never folded into
  'unavailable')."; when `n_render_failed > 0` a further sentence names it
  too.

  VERIFIED FAILING PRE-FIX, THEN FIXED (same convention as every other
  regression test in this task): reverted just `_render_corpus_index_html`'s
  guard (via `git stash` on `commands.py` alone, test file kept) and ran
  `test_render_phase_isolates_a_single_row_failure` — it failed with the
  bare `RuntimeError` propagating out of `cmd_corpusstatus`, through
  `_write_corpus_index_html`, through `_render_corpus_index_html`'s
  generator expression — the exact call chain the finding named. Restored
  the fix; the same test then passes, and the malformed row's `<tr>` has
  exactly 8 `<td>` cells like every other row, confirmed by direct count.

  Re-ran the full corpus AGAIN after this fix (2,931 documents, 415.7s
  command-reported / 6:56.07 wall clock, exit 0): the state counts are
  BYTE-IDENTICAL to fix round 1's (34/1,196/107/1,594) — asserted, not
  merely restated, in `out/653c/script.py` (`unchanged_from_fix_round_1`).
  0 rows on this real run needed either the gather-phase or the
  render-phase error path (`errored_rows_on_this_real_run: 0`,
  `render_failed_rows_on_this_real_run: 0`, checked against the real
  `>errored — ` cell-text marker, NOT a bare substring search — a bare
  search for "errored" false-positives on the summary paragraph's own
  explanatory prose, which names the word without any row being in that
  state).
