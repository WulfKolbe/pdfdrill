THE DEFECT
----------
`report_tex.render_crops` (src/pdfdrill/report_tex.py:2643, pre-fix) cached
a crop by TITLE alone:

    f = dest / f"{title}.jpg"
    if f.is_file() and f.stat().st_size > 500:
        cached += 1
        continue

Nothing compared the file against the row's CURRENT (page, region). A
2026-09-03 change to how host lines are joined moved what 159 formula
rows across six arXiv documents point at; the cache kept serving the
crop cut under the OLD region. `~/inkdrill-marks/stale-crops.json` (peer
tool `tools/cropcheck.py`, correlation < 0.35 against the host line cut
losslessly from `inspect/pages`) named all 159: 0902.0431 (60),
1510.06699 (85), 2010.14265 (7), 2501.06662 (3), 2106.07890 (2),
bradley_spring22 (2). The 15 published books were clean.

THE FIX — WHAT KEY, AND WHY
----------------------------
`CROP_GEOMETRY_FILE` = `crops.geometry.json`, a sidecar inside
`report-crops/` recording, per title, the `[page, top_left_x,
top_left_y, width, height]` the crop was ACTUALLY CUT FROM. On every
call, `render_crops` now compares that recorded key against the row's
CURRENT region from the tiddler:

  * file present + recorded key == current key -> cached (unchanged case).
  * file present + NO recorded key (every crop rendered before this
    sidecar existed) -> trusted ONCE, entry BACKFILLED from the row's
    current region, so the NEXT change on this title is caught rather
    than the first this code has ever seen.
  * file absent, or recorded key != current key -> re-rendered, and the
    sidecar entry is updated to the new key.
  * row carries no parseable page/region at all -> unchanged pre-671
    behaviour (trust an existing file, skip a missing one); there is
    nothing to compare against, so this is not guessed at.

WOULD IT HAVE CAUGHT THE 2026-09-03 JOIN? Yes, for every title whose crop
was rendered — and therefore had its geometry recorded — before the join
changed what its row points at: the next `render_crops` call after such
a change compares the row's new (page, region) against the recorded one,
finds a mismatch, and re-renders. That is the ordinary lifecycle (a crop
exists before a later code change touches its row), which continuous
operation of this sidecar provides from here on. PROVED, not just
argued: with the real bradley_spring22 PDF and a real (unmutated)
cached crop copied into a scratch directory, an unchanged row stayed
cached (0 rendered); the SAME row with its page/region edited to a
different host line (simulating the 2026-09-03 class of change) was
re-rendered on the next call (1 rendered), and the sidecar recorded the
new geometry. This is NOT a retroactive fix for the 159 crops rendered
before the sidecar existed — those were handled explicitly (below) by
removing them so this code sees them as absent, not as an
untracked-but-correct cache hit that would otherwise backfill their own
wrong geometry as if it were right.

IS THIS THE SAME IDEA AS 670's geometry_signature? Same failure SHAPE
(HANDOVER-RULES rule 19: a freshness check that does not ask the
question that matters), NOT the same mechanism, and not shareable as one
function. `report_tex.geometry_signature()` (670) hashes the SOURCE CODE
of the functions that lay out `report.pdf` itself (`GEOMETRY_FUNCS`,
`CELLRECT_PREAMBLE`, `font_metrics_preamble()`) — it answers "did the
CODE that computes REPORT geometry change", a whole-document, CODE-
identity question, used to decide whether a cached ink MEASUREMENT can
still be trusted. This defect sits entirely upstream of that subsystem:
the host-line join lives in the docmodel/refine pipeline, touches no
function in `GEOMETRY_FUNCS`, and changes DATA (which page/region a
tiddler carries) rather than CODE. Reusing `geometry_signature` here
would not have caught this — none of the functions it hashes decides
what page or region a formula's host line resolves to. What travels
between the two is the PRINCIPLE, not code: a per-row DATA identity
question needs a per-row data comparison; a per-build CODE identity
question needs a source hash. Documented at both definitions
(`CROP_GEOMETRY_FILE`'s comment in report_tex.py cross-references
`geometry_signature`'s, and vice versa was already in place from 670).

STEP 3 — report-crops-b/, VERIFIED REGENERATED, NOT ASSUMED
-------------------------------------------------------------
`report_tex.scale_crops` never overwrites unless told to (`force=True`);
`reports/crops.py`'s production `_apply_budget` always passes
`force=True` for exactly this reason, so a caller happy to reuse a
same-rung rebuild does not silently repeat one for its own use, but this
task called `scale_crops` directly rather than through `ensure_crops` (the
production entry point also compiles `evidence-formula.pdf`, out of
bounds here).

The rung was NOT re-derived by calling `reports.budget.choose_rung`
freshly on today's byte total. Measured first: for bradley_spring22, a
fresh `choose_rung` call on the 181 current Formula-kind crops returns
scale=1.0 (4.65 MB, under the 20 MB budget) — but every one of its 179
untouched sibling crops is published at ratio 0.6993 (the `CROP_LADDER`
entry (0.70, 75)), which only a build with a LARGER total could have
chosen. This is a genuine, pre-existing drift in that document's budget
math (the corpus has apparently shrunk under budget since that rung was
last chosen) — unrelated to 671 and NOT corrected here, since scope is
the 159 stale crops' CONTENT, not every document's rung currency. Acting
on the fresh recomputation would have left these two titles' scaled
copies at a DIFFERENT scale than their 179 siblings — a new
inconsistency this task would have introduced. Instead, the actual rung
in force for each document was DETECTED by measuring an untouched
sibling Formula crop's real (report-crops, report-crops-b) width ratio
and matching it to the nearest `CROP_LADDER` entry, then applying that
exact (scale, quality) to only the named stale titles via the same
production `report_tex.scale_crops` call:
