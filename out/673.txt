THE USER'S WORDS
-----------------------------------------------------------------------------
"some integration of inkdrill as pdfdrill command without a code
integration, but as an external tool that is called" — this ADDS a
command inside the established subprocess-discipline architecture
(`refine.inkdrill_root`, `regionink.inkdrill_available`,
`inkmeasure.py`'s own "pdfdrill CONSUMES inkdrill: it is a subprocess,
never an import"); it does not invent one.

WHAT WAS BUILT
-----------------------------------------------------------------------------
`src/pdfdrill/inkmarks.py` (new) — the subprocess boundary and the key
resolution, pure and independently testable:

  `run(pdf, key, marks_root, library, timeout)` — runs inkdrill's
  `tools/formulamarks.py marks <key> --library <library> --work
  <marks_root>/<key>/work` via `subprocess.run(..., capture_output=True,
  text=True)`, which keeps stdout and stderr in SEPARATE buffers by
  construction. Only `r.stdout` is ever parsed, and it is parsed (json.loads)
  before this module returns anything — a bad capture fails at the
  subprocess boundary, never three steps downstream. Raises
  `refine.InkUnavailable` (typed, names what it tried) when inkdrill or its
  formulamarks.py tool is missing; raises `inkmarks.MarksRefused` (typed)
  when stdout is empty or not one parseable JSON document.

  `candidate_keys(pdf, site_key)` / `resolve_key(pdf, site_key,
  marks_root)` — inkdrill's `--library ROOT KEY` opens `ROOT/KEY`
  literally, so its key is ALWAYS the library folder name
  (`pdf.parent.name`); for an arXiv id that equals pdfdrill's own bibkey
  (`commands.resolve_bibkey`, the SITE SLUG published to the tiddler wiki)
  because the folder IS named for the id, but for a Z-Library book it does
  not. `resolve_key` tries the folder name FIRST (matching what inkdrill
  actually uses) and the site slug only when it differs, by checking which
  one(s) have a finished `<key>/work/meta.json` under `marks_root`
  (default `~/inkdrill-marks`, documented since 672's own
  `reports/marks.py` docstring). NEVER GUESSES: raises `MarksRefused`,
  naming every key it tried, when NEITHER has a finished run, and — the
  case that must never be settled silently — when BOTH do and they point
  at different directories, telling the caller to pass `--key` explicitly.

`cmd_marks` (`src/pdfdrill/commands.py`, `@_writes("marks")`) — the glue:
resolves the key (or uses an explicit `--key`, still checked for a
finished run), runs `inkmarks.run`, and:

  * inkdrill's own `refused` field on the document → writes
    `marks.json.REFUSED` (never `marks.json`) and RAISES `MarksRefused`
    (propagates through `cli.main`'s generic handler as
    "Error [MarksRefused]: ...", exit 1) — reported as a refusal, never as
    success, per the brief's requirement.
  * otherwise → writes `marks.json` beside the document (atomic
    tmp+os.replace) and returns a report whose first lines ALWAYS name
    which key matched and how, then rows/measured/marked, then
    `reading_changed: N` explicitly (never left inside the JSON for a
    reader to find), then `suppressed`/`not_measured` breakdowns.

THE TWO-ENV-VAR DEFECT — FIXED, ONE FUNCTION NOW
-----------------------------------------------------------------------------
`refine.inkdrill_root()` read `INKDRILL_ROOT`; `regionink._INKDRILL_HOME`
read `INKDRILL_HOME`, independently, at import time. Nothing made them
agree — an environment that set one but not the other could point the two
modules at two different checkouts with no error anywhere.

FIX: `refine._env_inkdrill_home()` is now the ONE function that reads
either variable — INKDRILL_ROOT wins when both are set (it is the older,
typed-error path, and the name every doc that mentions this checkout
already uses); INKDRILL_HOME is kept as a deprecated alias so an
environment that only ever set it does not silently regress. There must
never be a third name, per the brief. `regionink.py`'s own env read was
deleted; `_INKDRILL_HOME` is now `_env_inkdrill_home() or
(Path.home() / "inkdrill")` — the SAME function `refine.inkdrill_root()`
calls, not a second copy of the same logic that could drift again.
Verified with a real subprocess (both env vars set to different real
checkouts) that the two modules agree — see tests above.

THE TWO JUDGEMENT CALLS
-----------------------------------------------------------------------------
1. Does `marks` also build the evidence PDF?  NO, not by default.
   `pdfdrill marks` stops at `marks.json`; `pdfdrill evidence <pdf>
   --marks <path>` (unchanged since 672) is the caller's job, one command
   already fully capable of it. Reasons: (a) the two write different
   artifacts and the single-responsibility split matches every other
   pairing in this codebase (`regionink` vs `reporttex`, `inktables` vs
   `model`); (b) a caller who only wants to see `reading_changed`/
   `suppressed` counts before deciding whether a rebuild is worth it
   should not be made to pay for a full evidence PDF re-render and
   re-encode; (c) `evidence-formula.tex` being current is a genuine
   dependency this command's `requires: [evidence]` in commands.yaml
   declares even though `cmd_marks` never calls `cmd_evidence` in that
   path — CLAUDE.md's own rule ("a layer's requires names everything it
   READS, not everything it calls") applies here exactly the way it does
   for `reporttex`/`mathpix`. `--build` is the opt-in that closes the loop
   in one call for the common case, by calling `cmd_evidence(...,
   marks_path=...)` in-process after `marks.json` is written — safe
   because the per-document lock is RE-ENTRANT within one process
   (`doclock.py`'s own stated rule, the same one `--ensure`'s prerequisite
   chain already relies on).

2. How is the directory key resolved when the two naming schemes
   disagree?  Try the LIBRARY FOLDER NAME first (what inkdrill actually
   uses to open `--library ROOT KEY` as `ROOT/KEY`), try pdfdrill's own
   bibkey/site-slug second only when it differs, and NEVER pick between
   them silently: if neither resolves to a finished run, refuse naming
   both; if BOTH do and they are different keys, refuse naming the
   ambiguity and require `--key` explicitly. The report always states
   which one matched and by which route. This is the direct fix for the
   second 2026-09-11 defect (site slug tried alone, first, and silently
   correct only for arXiv ids).

CONCERNS
-----------------------------------------------------------------------------
1. `resolve_key`'s ambiguity check is presence-only (`work/meta.json`
   exists), not content-aware — if a document were ever renamed such that
   BOTH its old and new library folder names carry a finished run (an old
   folder left behind after a rename, say), this correctly refuses rather
   than picking the stale one, but it also does not know WHICH is stale;
   a human has to look and pass `--key`. That is the intended behaviour
   (never guess silently) but is worth noting as the shape a real
   ambiguity would take.
2. `--marks-root`/`--library` are new optional overrides with no env-var
   equivalent, by design (the brief explicitly warned against a third
   name for the inkdrill-checkout pair; these are a different concern —
   document-data locations — and adding an env var for them was judged
   unnecessary scope). If a caller needs them for automation, CLI flags
   already work.
3. `requires: [evidence]` in commands.yaml is presence-based
   (`artifact:evidence` = at least one `evidence-<kind>.{html,pdf}`
   exists), not formula-kind-specific, matching the existing looseness of
   every other `done_when`/`requires` pair in this manifest — `--ensure`
   auto-running `evidence` with no `--kind`/`--all-kinds` would return a
   usage message rather than building anything, a pre-existing property
   of `cmd_evidence`'s own argument handling that this task did not
   change.
