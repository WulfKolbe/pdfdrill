WHY THE COLUMN WAS EMPTY
------------------------
`download_crops` filters for "_EQ" or "_TAB" in the title — the intent was
always both — and then skips anything whose canonical_uri does not start with
http. Across the 21 published documents:

  EQ tiddlers with a canonical_uri    8,718 of 8,718
  TAB tiddlers with a canonical_uri       0 of   351

MathPix records no crop uri for a table. So the filter was right, the fetch
was right, and the column was empty for a reason nothing in the code said out
loud. 423 gave the section six columns and the sixth had no source.

WHAT WAS BUILT
--------------
`report_tex.render_crops(tiddlers, dest, pdf)` — crops each region-bearing
tiddler without a CDN uri out of a Ghostscript render of its page, into the
same `report-crops/<title>.jpg` the CDN path writes. Nothing in the report
builder changed: `crop_cell` and `crop_file` find the file exactly as before.

Three things that would have been wrong silently, each with a test:

  * MathPix regions are in ITS page-image pixels, not ours. Every coordinate
    is scaled by (raster width / that page's page_width), read PER PAGE.
    11 of 305 documents in this corpus carry more than one page_width, and a
    page scaled by another page's width lands on the wrong part of the page
    and still looks like a plausible piece of it. This is the trap
    refine.scan_crop already documents; render_crops reuses its width reader.

  * A page with no recorded width is SKIPPED, not defaulted.

  * The crop is resized back to the region's MathPix pixel size. crop_cell
    sizes an image as jpg_width x px2mm and px2mm is mm per MATHPIX pixel, so
    a 400-dpi crop left at its own width computes ~1.6x too wide, hits the
    column cap, and silently stops being pixel-exact — the one property the
    Scan column claims. Rendering at 400 dpi and downsampling is also a better
    picture than rendering at MathPix's ~250 dpi directly.

  * The page is parsed OUT OF THE FILENAME rather than zipped against the
    request list. `rasterize` globs its output directory, so one stale page
    from a crashed run would shift every pairing by one and crop each region
    from its neighbour's page. Tested.

VERIFIED END TO END
-------------------
Two documents rebuilt to a scratch report.tex at the paper the reports
actually use (a3 landscape):

  penev_A             Tables: 2 rows, 1 \includegraphics   width=39.7mm
  voloshin-hypergraph Tables: 2 rows, 2 \includegraphics   width=40.6, 57.3mm

Those millimetres are region_width x px2mm exactly (391x0.10157, 400x0.1016,
564x0.1016), so the crops are at their true physical size, which is what the
equations column has always done and the tables column never could.

One thing worth recording because it nearly became a false alarm: my first
check built a4 portrait and every crop came out at exactly 38.0mm. Three
identical numbers across two documents looked like a fixed fallback. It was
the column cap — a4 portrait leaves the image column 42mm, and crop_cell caps
at col_mm - 4. The reports build a3 landscape, where the cap is 122mm and
nothing is capped. Checking a suspicious coincidence cost two minutes; taking
it for a defect would have cost more.
