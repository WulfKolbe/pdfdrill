==============================================================================

Branch eqblobs-and-gzip-tex, base commit 8de4ff87, clean, pushed.

THE FIX
-------
`report_tex.renderable()`'s third gate (src/pdfdrill/report_tex.py, around
line 1691) used to be one line:

    if r"\[" in lx or r"\]" in lx or re.sub(r"\\\$", "", lx).count("$"):
        return ""

Split into two, per the brief:

    if r"\[" in lx or r"\]" in lx:
        return ""
    dollar_mask = re.sub(r"\\\$", r"\\X", lx)   # same escape rule as before,
    dollar_pos = [m.start() for m in re.finditer(r"\$", dollar_mask)]
    if dollar_pos:
        text_ranges = text_spans(lx)
        if any(not any(a <= p < b for a, b in text_ranges)
               for p in dollar_pos):
            return ""

`\[`/`\]` refuse UNCONDITIONALLY, unchanged. `$` is now scoped to
`text_spans()` — task 662's promoted primitive (`src/pdfdrill/
text_escapes.py`), the SAME span-finder `cjk_defect` already uses for the
identical kind of question, reused rather than re-derived, as instructed.
`text_spans(lx)` with no second argument uses its default `TEXT_IN_MATH`
macro set (`\text`, `\textrm`, `\textnormal`, `\textit`, `\textbf`,
`\mbox`, `\operatorname`) — the general "is this text mode" question, not
`cjk_defect`'s narrower `CJK_TEXT_MACROS` (which excludes `\operatorname`
for a content-specific reason that does not apply here).

The escape handling for `$` is UNCHANGED in substance: the old code
removed every `\$` (escaped dollar, i.e. currency) via `re.sub` before
counting; the new code performs the identical substitution but into a
same-length placeholder (`\$` -> `\X`) so the surviving `$` positions are
preserved for the span check. Byte-for-byte the same set of `$` characters
is now "real" vs "escaped" as before — only what happens to a REAL one
changed (checked for text-span membership instead of refusing
unconditionally).

THE `\[`/`\]` DECISION, ARGUED (not left to fall out of the code)
------------------------------------------------------------------
`\[`/`\]` keep refusing unconditionally, in every location, including
inside a `\text{}` argument. They are DISPLAY-math delimiters. Every cell
this gate judges is already wrapped in the report's own outer `$...$`
(or, after 661's `to_inline_env()`, addressed from inside that wrapper).
Display mode cannot legally open inside inline math, and that is true
regardless of which brace group the `\[` is typed from — a `\[` inside
`\text{...}` would try to open display math while TeX is already in math
mode via the surrounding `$...$`, which is exactly as broken as a bare
`\[` in the cell. Unlike `$` (which pairs with itself and, inside
`\text{}`, opens and closes ordinary NESTED inline math that never
touches the cell's own delimiters), `\[`/`\]` have no such "contained"
reading — there is no scope in which a display-math opener sitting inside
an inline-math cell is safe. So location never rescues them, and they are
deliberately NOT run through `text_spans()`.

PART TWO — THE EIGHT (PLUS ONE) FIGURE-SHAPED ROWS: UPSTREAM, NOT TOUCHED

The gate was NOT changed for these, per the brief, and correctly so: a
`\begin{figure}...\end{figure}` float cannot typeset inside a maths cell
regardless of what is inside it, and refusing it is the gate doing its
job. What follows is a measurement of the upstream defect, not a fix.

WHAT CREATED THEM, AND WHY (traced to the exact line, not inferred)
------------------------------------------------------------------------
`src/docmodel/modules/equation.py:212`, `EquationProcessor.find_items`:

    latex_raw = payload.get("text_display") or payload.get("text") or ""

For a MathPix `lines.json` line typed `"math"`/`"equation"`
(`EQ_TYPES`), this prefers `text_display` over `text`. For most line
types this is the RIGHT choice and is the convention every other
`docmodel/modules/*.py` reader of these two fields relies on
(`header.py`'s own docstring: `text_display` is the LaTeX-command form,
`text` the plain caption/content). For all eight rows here, checked
directly against each document's own `.lines.json`, the SAME line's two
fields diverge in a way unique to equations sitting inside a genuine
LaTeX float:

    type: "math"
    text:         "\[\nN_{LU}:=...\n\]"                          (clean)
    text_display: "\n\n\begin{figure}\n\captionsetup{...}
                  \caption{Listing 3.3 cforwardsolve}\n\[\n
                  N_{LU}:=...\n\]"                                (wrapped)

(lyche-numerical-linear-algebra obj_904ab7b5e410, verbatim, the richest
example: the caption text is independently present, correctly typed as
its OWN `figure_label` line immediately before the math line in the same
`lines.json` — `text_display` duplicates it into the math line's own
reconstruction rather than the docmodel ever cross-referencing the two.)
All eight rows across all three documents show the identical pattern,
confirmed individually, not sampled: `text` is always bare display math
with no wrapper; `text_display` always adds the full
`\begin{figure}[...]...\end{figure}` float around the identical maths.

MathPix's own line-typing is not wrong here (the line genuinely IS the
equation, per `type: "math"`) — its `text_display` reconstruction is doing
FULL-PAGE-LAYOUT reconstruction (float, caption, the works) for a field
the docmodel module reads as if it were just the equation's own latex.

WHY `_normalize_latex`'s existing `_DOC_ENVS` machinery does not already
catch this: it exists for the MIRROR case (446/483/485) — an UNMATCHED,
dangling `\begin{itemize}`/`\end{theorem}` etc. glued onto ONE end of an
equation line by MathPix's own line-splitting — and it explicitly
declines to strip a wrapper whose opener AND closer are BOTH present and
balanced. Here `\begin{figure}` and `\end{figure}` are both genuinely
present (the whole float, caption included), so this is not a dangling
fragment; it is a real, balanced non-equation environment standing in for
one. Adding `"figure"` to `_DOC_ENVS` would not, by itself, fix these —
the strip logic would still decline to touch a balanced wrapper.

PROPOSED OWNER
---------------
`src/docmodel/modules/equation.py`, `EquationProcessor.find_items` /
`_normalize_latex` (same module, same task): the fix belongs at ROW
EXTRACTION time, not at render time, because the defect is a
mis-segmentation ("this Equation's own content is not an equation, it is
a captioned float") rather than an unsafe-to-typeset value. Two directions
worth weighing (not chosen or implemented here — out of this task's
scope, per the brief's explicit "do NOT fix" instruction): (a) detect a
BALANCED `\begin{figure}...\end{figure}` wrapper around genuine display
math and either fall back to the line's own `text` field or unwrap the
float while dropping its caption (unlike the itemize/theorem case, this
would DISCARD content — the caption text — so it needs its own
judgement call about where that caption text should go instead: probably
nowhere, since a `figure_label` line elsewhere on the page already carries
it independently for johnston/lyche, unconfirmed for kohlhase); (b) treat
a `type: "math"` line whose `text_display` opens `\begin{figure}` as a
signal to reclassify the object as a Diagram/Picture/Figure rather than
an Equation, since MathPix's own text_display is effectively telling the
module "this region is a captioned float, not a bare formula."

THE NINTH ROW — CHARACTERISED SEPARATELY, A DIFFERENT DEFECT, NOT FIXED
----------------------------------------------------------------------------
lyche-numerical-linear-algebra obj_2697f43fe888 (page 215) is refused by
the same `\[`/`\]` substring check but for an UNRELATED reason: its
`latex_refined` value contains the literal substring `\\[1ex]` — amsmath's
OPTIONAL SPACING ARGUMENT after a `\\` line break inside an
`aligned`/`array` body (standard, legal LaTeX, not a display-math opener).
Checked directly: this value contains ZERO `\]` anywhere at all — so no
genuine `\[...\]` PAIR is present, confirming there is no real display
environment here, only the false trigger. The gate's `r"\[" in lx` check
matches any backslash-immediately-followed-by-bracket, so it cannot
distinguish `\[` (display math) from the second backslash of `\\[1ex]`
(line-break spacing) — a GATE FALSE POSITIVE, a different and narrower
input shape than either the CJK class or the figure-capture class. Named
here per the brief's instruction, deliberately NOT fixed: 668's scope was
the `$`-in-`\text{}` decision argued above, not this second, unrelated
`\[`/`\]` false-positive on amsmath spacing syntax. A future task fixing
it would need to distinguish `\[`/`\]` (odd or even backslash count
before the bracket, paired with a genuine partner) from `\\[<length>]`
(even backslash count immediately before `[`, no matching `\]` at all).
