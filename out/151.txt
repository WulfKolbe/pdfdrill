A DIAGNOSIS THAT LOOKED LIKE A FAILURE AND WAS NOT
---------------------------------------------------
   GET /reports/  ->  404       immediately after the push
   pages API      ->  "status": "errored", last build 2026-08-06

That reads as "the site is broken and my push made no difference", and it is
wrong. The Pages API also reports:

   "build_type": "workflow"

The site is deployed by a GitHub Actions workflow, not by the legacy Jekyll
builder — and the `status`/`builds` fields describe the LEGACY builder, which
has not run since 6 August and is irrelevant here. The stale "errored" is a
record of a subsystem no longer in use.

The Actions run for the exact commit confirms it:

   sha a418eb62c15fdb8602b489eb7dab180f73ff7b92   conclusion: success

and both URLs then returned 200. The 404 was the propagation gap between the
push and the deploy completing, not a broken build.

Had I trusted the API's `status` field I would have reported the publish as
failed and gone looking for a Jekyll problem that does not exist —
`.nojekyll` is present, there is no `_config.yml`, and no underscore-prefixed
files. All three of those checks were clean, which was the first sign the
Jekyll theory was wrong.
