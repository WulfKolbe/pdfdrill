THE CLASSIFICATION (brief item 1 — "say what the 49 have that they lack")
  Every one of the 12 was checked directly against the model: does a
  Citation object exist over it (by line anchor + span)? For ALL 12, NO —
  confirmed by dumping every Citation whose citekey matched the ref number
  and checking its anchored text against the 12 locations; none matched.

  CLASS 1 — TABLE CELL (7: refs 6, 10, 12, 13, 14, 15, 17)
    "Forster et al. [10]", "Tensor products of Hilbert transforms [6]", etc.
    — MathPix Table I's own cells, line type `simple_cell`/`complex_cell`.
    CAUSE: `detect_numeric_citations` filtered `p.get("type") not in
    ("text", "title")` — a cell is neither, so the line was never looked at,
    not a regex miss. Confirmed: the IDENTICAL phrase also exists as a
    duplicate `text`-type Paragraph elsewhere (`Tensor products of Hilbert
    transforms \cite{Chan2004}` at a different line), which WAS scanned and
    IS cited — the citekey the table cell lacks is sitting right next to it
    in the model, under a different object.

  CLASS 2 — DIAGRAM CAPTION (2: refs 28, 29)
    "Adelson's checkerboard illusion [29]", "(compare also [28])" — MathPix's
    OWN `\caption{…}` text, embedded inside a `diagram`-type line's
    `text_display` (a full `\begin{figure}…\caption{…}…\end{figure}` block).
    CAUSE: same type filter (`diagram` excluded). Same duplicate-text pattern
    as Class 1: an identical "text"-type Paragraph carries the SAME caption
    and IS cited (`\cite{Adelson2006}` already printed on a nearby page) —
    only the Diagram object's OWN copy of the text was blind to it.

  CLASS 3 — LOCANT (3: refs 1, 1, 21 — one inside a Footnote body)
    `[1, Ch. III.1]`, `[1, Ch. III]`, and (inside the monogenic-function
    footnote) `[21, Ch. II.5]`. CAUSE: `_NUMCITE = re.compile(r"\[(\d[\d,\s
    \-–]*)\]")` required the WHOLE bracket to be digits/commas/dashes/
    whitespace; a trailing ", Ch. III" locant is not in that character class,
    so the match fails and NOTHING is created — even though the line type
    IS `text`/`title` and even though `_numlist_spans` (645/642) already
    gives a LEADING digit-list its own span and silently drops anything
    after it that isn't a digit or a range. This is the one class the brief
    anticipated correctly ("the detector's regex misses the shape").

  A "NEW RULE THE BRIEF DID NOT ANTICIPATE" (Before-You-Begin instruction):
  Classes 1 and 2 are not the shapes item 1 listed (inline maths, a line
  break, `[1,5]`/`[10-12]`/`[1]-[3]`) — they are "the surrounding text is
  not a Paragraph (a caption, a table cell...)", which item 1 DOES name as a
  possible cause, just not with these exact MathPix type strings. The rule I
  chose: extend `detect_numeric_citations`'s line-type filter from
  `("text","title")` to also include the four table-cell types
  (`simple_cell`, `complex_cell`, `table_spanning_cell`, `table_split_cell`
  — `docmodel.modules.table._CELL_TYPES`'s own set) and `diagram`
  (`docmodel.modules.picture._SKIP_TYPES`). Reasoned from the SAME kind of
  evidence 645/638 used elsewhere: a citation's text does not stop being a
  citation because MathPix classified its LINE as something other than
  prose.

THE FIX, PER CLASS, AT THE DETECTOR (never a projector patch on the symptom)
  src/pdfdrill/bibliography.py
    `_NUMCITE` gains an optional locant tail: `(?:,\s*[^\]\d][^\]]*)?` after
    the digit-list — requires a literal `,` (so `[1,2]`/`[10-12]` are
    unaffected: the base pattern already consumes them) and a non-digit
    first character after it (so `[1,2,3]` cannot misparse as "1" + locant
    "2,3"). `_numlist_spans` needed NO change: it already walks the group by
    splitting on `,`/`;` and silently drops any part that is not a digit or
    a range, so the locant text is automatically excluded from the span —
    only the leading number gets one, exactly as the group logic requires.
    `_CAPTION_CELL_TYPES = ("simple_cell", "complex_cell",
    "table_spanning_cell", "table_split_cell", "diagram")` added to the type
    filter in `detect_numeric_citations`.
  src/docops/projectors/citations.py
    `CITED_TEXT_TYPES` gains `"Picture"`, `"Diagram"` — `LaTeXProjector._render`
    DOES have a branch for both (the `% figure pN: …` comment when there is
    no `latex_code`), so the substitution reaches wherever that branch
    prints. `"Table"` is deliberately NOT added: a `Table` with no
    `latex_code` renders `raw_text` inside `\begin{verbatim}…\end{verbatim}`,
    where LaTeX never interprets `\cite{…}` — substituting there would print
    the literal command text instead of a citation. This is the ONE class
    left un-surfaced by design; see RESULTS below and CONCERNS.
  src/docops/projectors/latex.py
    The Picture/Diagram branch now calls `self._cite(obj, caption)` on the
    RAW caption (same order as every other caller: before `_escape_text`,
    so a citekey is never re-escaped) before falling back to the comment.

  A REGRESSION FOUND AND FIXED IN THE SAME TASK (not anticipated by the
  brief, found by rebuilding and reading the actual .tex — rule 14 twice
  over). `apply_subs`'s literal, cursor-based search for a BARE DIGIT source
  (`"1"`, `"21"`) is exactly what the LOCANT and DIAGRAM classes need, and it
  is unsafe: on the FIRST rebuild, `(see [1, Ch. III.1])` came out as
  `(see [{{…_REF_Stein\cite{Stein1970}970||CIT}}, Ch. III.1])` — the digit
  "1" INSIDE the token name `Stein1970` (a `{{…||CIT}}` token `clean` had
  ALREADY materialised for a DIFFERENT `[1]` on the same line) won the
  search before the real bracket was reached — and a genuinely unrelated
  `-1` in running prose ("...exactly two choices: ... and -1, i.e., the
  identity...") became `-\cite{Stein1970}`. Both reproduced exactly and
  fixed with `_numeric_source_in_context`: a bare-numeric `Sub.source` is
  only accepted at a position immediately preceded (after whitespace) by
  `[`, `,`, or `;` — precisely what `_numlist_spans` requires to split one
  out in the first place. A failing match keeps searching forward instead of
  giving up. Scoped to bare-numeric sources only (a fullmatch on
  `\d+(-\d+)?`) — an author-year source is never this short, so ordinary
  `(Smith 1999)`-style matches are untouched.

CONCERNS
  penev_A was NOT rebuilt with `--force`, on purpose. `cmd_bibliography`
  passes `max_num=n` where `n` is the COUNT of parsed bibliography entries
  (52), not the count of NUMBERED references (0) — a pre-existing,
  UNRELATED quirk that means `detect_numeric_citations` would actually run
  on penev_A's full range 1..52, and a stray in-range bracket that is NOT a
  bibliography citation (a footnote cross-reference like the literal "[16]"
  637's own evidence photographed, referring to a FOOTNOTE refnum, not a
  Reference number) could create a bogus new stub Reference. This is not
  one of this task's three classes and touching it was out of scope; it is
  named here rather than risked on penev_A's frozen 637/642/645/647b
  evidence.
  The TABLE class is measured, fixed at the detector (a Citation object now
  exists, correctly linked), and DELIBERATELY left unsurfaced in the .tex —
  `\begin{verbatim}` cannot carry a `\cite`. Making it reach the page would
  mean changing how a raw-text Table renders at all, which is a different,
  larger task and was not attempted here as a symptom patch.
  The `apply_subs` corruption was NOT part of the brief's anticipated
  classes; it was found only because the fix was actually rebuilt and the
  .tex actually read (rule 14). It is a latent risk for ANY bare single-
  digit numeric citation sharing an object with an earlier coincidental
  digit, not specific to this task's 3 classes — fixed generally
  (`_numeric_source_in_context`), not patched for these 3 occurrences only.
  `\Földiák`/`\Wässle`-class ASCII-surname misses (645-b) and the line-break
  citation class (642-a) are UNRELATED prior findings for the AUTHOR-YEAR
  detector; Steerable is IEEE-numeric (0 author-year citations), so neither
  applies here and neither was touched.
