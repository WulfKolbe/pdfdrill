640 — the full drill on both documents, and what it does to the superscripts
=============================================================================

Both documents were drilled with `bash tools/drill_full_sandbox.sh <pdf>` at
63c028b (647's loud harness), then projected with `pdfdrill latex <pdf>
--dump-stages`. Every number below is a count off the artefacts that run
produced — `latex/<key>.tex`, `model.docmodel.json`, `latex/stages/*` — taken
by `out/640/script.py`, which is committed as evidence beside each document
together with its `result.json`.

THE HEADLINE, BEFORE THE TABLES: the full drill CHANGES the thing 641 was
scoped against, and changed it for the worse. `clean` is the step. On penev_A
it took the .tex from 21 `\footnotemark[n]` (642, yesterday) to 0, put 63
literal `(?penev_A_FN0003)` placeholders and 44 `<sup>N</sup>` HTML tags into
the document instead, and the underscore in those identifiers stopped the
compile at page 5 of 97. §3 measures it; §6 is FIX ROUND 1, which closes it —
the projector now resolves every template the TiddlyWiki projector emits, from
one table, and penev_A goes to 107 `\footnotemark[n]`, 0 placeholders and 97
pages with 0 errors. 641's own premise — a body superscript whose n matches a
bibitem number — has ZERO instances on either document, for two different
reasons. Both are §4.

§2 and §3 are the state AS MEASURED BEFORE FIX ROUND 1, and are left that way
on purpose: they are what the ruling was made on.

  -83 is exactly 638's count of UNRESOLVED running-text markers, and -21 is

  THE CAUSE, READ OUT OF THE CODE AND CONFIRMED IN THE MODEL. `clean` →
  `heading_cleanup.materialize_transclusions` writes the TiddlyWiki
  PROJECTION of each paragraph back into `props["text"]`, so the raw
  `\({ }^{3}\)` a paragraph carried becomes `{{penev_A_FN0003||FN}}`. It
  preserves the pre-materialisation text under `props["text_source"]` (185
  paragraphs have one; all 185 differ from `text`; they hold all 104 markers).

  `footnotes.object_text` reads `props["text"]` — it tries "text", then
  "content" — so `resolve()` now sees tokens where it expects markers and
  reports 0 markers of 0. And the LaTeX projector's transclusion resolver
  handles `||FO` by array lookup but has no `||FN` branch, so each of the 63
  FN tokens is emitted as its fallback: the literal string
  `(?penev_A_FN0003)`. In the .tex, where 642 had

      … expectation for finding a low-dimensional representation. \footnotemark[2] Indeed, …

  today stands

      … expectation for finding a low-dimensional representation. (?penev_A_FN0003) Indeed, …

  This is a REGRESSION IN THE OUTPUT, not a bookkeeping difference: the string
  prints. It is filed as 640-a. Two candidate fixes, neither taken here (this
  task measures):
    (i)  `footnotes.resolve` reads `text_source` when it exists — the markers
         are still there, exactly, and it is a one-line change to
         `object_text`; or
    (ii) the LaTeX projector grows a `||FN` branch and resolves the token to
         `\footnotemark[n]` / `\footnotetext[n]{…}` directly, which is
         strictly better because the token already NAMES the Footnote object
         and needs no page/order disambiguation at all — 638's whole
         resolution apparatus becomes unnecessary on a cleaned document.
  (ii) is the one to prefer, and it is worth noticing that `clean` did 638's
  hard job for it: the marker→body pairing 638 recovered from page geometry
  with a 21-of-104 hit rate is, after materialisation, a stated identity.

  638-c UNCHANGED AND UNCOUNTED ELSEWHERE: 93 markers sit inside Sidenote
  bodies on penev_A, and `LaTeXProjector._render` still has no Sidenote
  branch, so none of that text reaches the .tex at all.

  THE TABLE. `latex_pipeline.TEMPLATE_ACTIONS` gives every key of
  `tiddlywiki.TEMPLATES` (644's macro layer) exactly one of three actions:

    ARRAY    FO FREF EQ EQBLOCK      the readarray lookup, `\Expr{i}`

  `test_every_tiddlywiki_template_has_a_latex_branch` fails when a template is
  added to TEMPLATES without a row here, and
  `test_every_handler_template_has_a_handler_on_the_projector` fails when a row
  says HANDLER and no handler exists. A template with no branch at the call
  site is a REFUSAL: it renders nothing and is COUNTED
  (`template_unhandled:<TPL>`). It is never a literal placeholder again.

  THE BRANCHES, and the one judgement call each needed
    ||FN   → `\footnotemark[n]` at the mark, `\footnotetext[n]{…}` at the end
             of the block that carries it (638's convention, unchanged).
             A MATERIALISED marker names its Footnote by TITLE, so there is no
             disambiguation to do at all — 638's page/refnum rule exists for a
             BARE `{ }^{n}`, which carries no identity. The two lanes now live
             side by side: `_mark_footnotes` still owns the bare markers,
             `_footnote_token` owns the materialised ones. Inside a footnote
             body a nested mark emits the superscript ONLY (`\footnotetext`
             inside `\footnotetext` is a LaTeX error, and 638 measured that a
             marker inside a body is usually the next body's printed label).
    ||CIT  → `\cite{key}`: the object's own `citekey` when the title names a
             Reference, else `parse_title(...).key`. Exact, and it needs none
             of 642's span arithmetic.
    ||SN   → `\marginpar{\footnotesize …}`. STATED CHOICE: a margin note, not a
             footnote. The TiddlyWiki template is `<aside>` — margin
             typography — and folding a sidenote into the footnote stream would
             renumber the footnotes the publication printed, which is the one
             thing 638 exists to preserve. (0 SN tokens on either document
             today; the branch exists so the next document does not print
             `(?…)`.)
    BLOCKS → PIC/DIA/TAB/LI/PARA/ABS/PROOF/TOC render through the projector's
             OWN `_render` for that object, so there is one renderer per type
             and not two. Depth-guarded at 3.
    `<sup>N</sup>` → `\footnotemark[N]`. Not a template: it is what
             `_substitute_footnotes` emits when a marker's refnum names no
             Footnote object (44 of them on penev_A — 638's extraction gap seen
             from the projection side). Left alone the HTML tag printed into
             the .tex. A mark with no body IS `\footnotemark[n]`.

  THE TITLE→OBJECT INDEX IS THE TIDDLER PROJECTOR'S OWN NUMBERING, not a copy:
  `tiddlywiki.titles_by_id(doc, bibkey)` delegates to `_assign_titles`. 644's
  six-bodies-one-title collision came from a second implementation of "the i-th
  Footnote in flow order"; there is not going to be a third.

  DOUBLE-PRINTING. An object a materialised marker transcludes must not ALSO be
  emitted standalone. `_skip_ids` is read ONCE, before the first block, so the
  decision is pre-computed in `_prepare` — an in-render `add` comes too late
  for anything earlier in the flow, which is exactly the case on penev_A (the
  Footnote bodies precede the paragraphs that mark them).
