WHAT THE REVIEW CAUGHT (fixed this round)
------------------------------------------------------------------------

1. UNITS (blocking). `budget.py` computed `budget_mb * 1024 * 1024` —
   binary MiB — while every other "MB" in this task (the brief, out/654.txt,
   the corpus driver's `/1e6`) is DECIMAL MB. Proof, unchanged from the
   review: gilmore's original evidence-formula.pdf is 115,427,118 bytes;
   `/1e6 = 115.427` matches every "115.4 MB" this task has quoted;
   `/1024/1024 = 110.08` does not. The enforced ceiling was ~20.97M bytes,
   4.9% more permissive than 20.00M. FIXED: `budget.py` now defines
   `MB = 1_000_000` and every conversion goes through `_bytes_for_mb`/
   `_mb_for_bytes`, so the unit cannot drift apart from the rest of this
   task family again. `crops.py`'s reporting math uses the same helper.

2. THE CONSEQUENCE (blocking). Recomputing under decimal MB moved THREE
   documents to a smaller rung than round 0 had chosen: cardona-qft-methods
   (0.60->0.50), fong-spivak-seven-sketches (0.50->0.42, the FLOOR), and
   voloshin-hypergraph (0.70->0.60). All three were rebuilt for real (below).
   Round 0's "gilmore genuinely cannot meet 20MB, a 2.3MB/12.7% gap" language
   also mixed a MiB-computed "predicted" number with a decimal-MB "actual"
   number in the same sentence — an apples-to-oranges subtraction. This
   report states every number in ONE unit throughout.

3. THE OVER-BUDGET FLAG WAS DEAD ON REAL DOCUMENTS (blocking).
   `choose_rung`'s `over_budget` can only ever compare PREDICTED CROP BYTES
   against budget — it never sees the compiled PDF, so on every document in
   this corpus it said nothing was over budget even though four documents'
   real files were. FIXED, per the review's own instruction ("report against
   the artefact... the honest report is what the brief asked for", NOT a
   safety margin on the search): `reports.budget.check_artifact(pdf_path,
   budget_mb)` reads the REAL compiled file's `stat().st_size` after
   `compile_fixpoint` runs, and `evidence.build`/`residuals.build` call it
   when given `budget_mb`, setting `res["bytes"]`/`res["over_budget"]`/
   `res["budget_mb"]`. `commands._evidence_line` (and `cmd_residuals`'s
   equivalent line) now print "-- OVER BUDGET: N.NMB compiled > 20.0MB
   budget" using THIS number, never the crop-byte prediction.
   `_apply_budget`'s note in `ensure_crops` was reworded from "OVER BUDGET"
   to "predicted ... (floor, still over budget predicted)" so the two
   claims (a prediction vs. a verdict on the finished file) are never
   confusable in the tool's own output again. VERIFIED against the real,
   re-compiled corpus (below): the code itself now prints OVER BUDGET for
   exactly 0902.0431, gilmore-lie-groups, and johnston-linear-matrix-algebra
   — the three documents whose predicted crop bytes narrowly fit the rung
   they landed on, but whose actual compiled PDF (fonts, table structure,
   PDF object overhead — a roughly FIXED cost, not proportional to how hard
   the images were compressed) pushes it back over 20MB decimal.

4. RESIDUALS' CORRECTED SECTION BYPASSED THE BUDGET (blocking), plus a
   PRE-EXISTING PREREQUISITE BUG the fix uncovered. `residuals.py`'s
   Corrected section called `rt.findings_tex(..., crops=doc_dir /
   "report-crops", ...)` — the full-size directory, keyed by identifier,
   never touching the row objects `ensure_crops` had already budgeted. This
   was genuinely untested: the one real-corpus spot-check offered in round 0
   (gilmore's residuals.pdf) had ZERO corrected pairs.
     FIXED: `findings_tex` gained an optional `crop_for: ident -> (Path,
   px_width) | None`, checked before the plain directory lookup (default
   None keeps the legacy `build_report` caller, which has no row objects to
   offer, byte-identical). `residuals.select()` now stamps each corrected
   pair with `_crop`/`_px_width` from the SAME `index` (identifier -> row)
   the other four sections already use, and `residuals.build()` passes a
   `crop_for` built from that.
     WHILE WRITING THE TEST THE REVIEW ASKED FOR ("at least one corrected
   pair"), a SEPARATE, PRE-EXISTING bug surfaced: `findings_tex`'s internal
   `row()` helper is called for the Corrected section as `row(ident + "
   (was)", ...)` / `row(ident + " (now)", ...)`, and `row()` used that SAME
   suffixed string for BOTH the displayed identifier AND the crop lookup
   (`scan(ident)`). No crop file has ever been named "<ident> (was).jpg", so
   the Corrected section's Scan column resolved to "---" unconditionally,
   for EVERY caller, at ANY rung, before this task existed. My `crop_for`
   wiring could not be exercised at all until this was fixed too — `row()`
   gained a `scan_ident` parameter (default: same as the displayed ident,
   preserving every other call site exactly), and the two Corrected-section
   calls now pass the bare identifier as `scan_ident` while still displaying
   " (was)"/" (now)" to the reader. This is stated as a finding, not
   buried: it was not caused by this task, but this task's own required
   test could not pass without it, and it changes user-visible output (the
   Corrected section's Scan column, previously always blank, now shows the
   image) for every caller of `findings_tex`, not only `residuals.py`.
     VERIFIED against a REAL corpus document with real corrected pairs:
   0902.0431 has 10. Its rebuilt `residuals.tex` embeds
   `report-crops-b/0902.0431_EQ*.jpg` (the budgeted copy) for every one of
   them, never `report-crops/...` (the full-size original) — confirmed by
   grep, not asserted.

Two minor findings, both fixed: `ensure_crops`'s per-kind loop variable is
now `kind_note`, distinct from the function's final `note`; `_encoded_size`
now prints its re-encode failures, matching `scale_crops`'s own behaviour,
instead of swallowing them silently.

CORPUS RE-MEASUREMENT — WHAT WAS REBUILT vs WHAT WAS INFERRED
------------------------------------------------------------------------

METHOD. A cheap, no-xelatex re-check (`pdfdrill evidence <pdf> --all-kinds`,
no `--pdf`) was run for all 20 documents first — `ensure_crops` still runs
and writes real re-encoded files (force=True), so the printed rung/predicted-
MB numbers are authoritative without paying for a single PDF compile. This
took under 8 minutes total (script + log:
~/pdfdrill-library/out/655/{rung_recheck.py,rung_recheck.json,
rung_recheck.log}) and showed the rung UNCHANGED for 17 of 20 documents.

REBUILT FOR REAL (`--all-kinds --pdf`, full xelatex compile):
  - cardona-qft-methods, fong-spivak-seven-sketches, voloshin-hypergraph:
    rung genuinely changed (finding 2's consequence); their evidence-
    formula.pdf on disk was STALE (built under the old rung) and had to be
    recompiled. Script + result:
    ~/pdfdrill-library/out/655/{rebuild_changed.py,rebuild_changed.json,
    rebuild_changed.log}.
  - 0902.0431, gilmore-lie-groups, johnston-linear-matrix-algebra: rung
    UNCHANGED, but re-run anyway to exercise the NEW artefact-level OVER
    BUDGET check for real rather than infer it — their already-built PDFs
    were reproduced (byte counts identical to within a few bytes of
    xelatex's own non-determinism; e.g. gilmore 20,445,336 -> 20,445,344).
    Script + result: ~/pdfdrill-library/out/655/{reverify_boundary.py,
    reverify_boundary.log}.
  - residuals.pdf for 0902.0431 (10 real corrected pairs — the only
    document in the corpus that actually has any): confirms finding 4's fix
    on a real document, not only the unit test.

INFERRED, NOT REBUILT: the other 14 documents. Their rung is unchanged
(confirmed by the cheap re-check) and their crop content is unchanged, so a
deterministic re-encode + a deterministic xelatex compile reproduces
exactly the bytes already measured in round 0's corpus rebuild — those
"after" numbers were already computed by dividing real `stat().st_size` by
1e6 (decimal, correct throughout, in BOTH rounds; the unit bug was internal
to the ACCEPTANCE THRESHOLD inside `choose_rung`, never in the measurement
script that reported the corpus table). Recompiling them would spend
xelatex time to re-confirm arithmetic that does not depend on today's fix.
