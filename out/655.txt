------------------------------------------------------------------------
THE SEAM DECISION
------------------------------------------------------------------------

Three candidates were named: inside `ensure_crops`, inside the evidence
command, or a new small module. Chose a NEW MODULE, `reports/budget.py`,
CALLED FROM `ensure_crops` (`reports/crops.py`) — not either candidate
alone.

WHY A NEW MODULE, NOT INLINE IN `ensure_crops`. `ensure_crops` already has
two jobs (call `download_crops`/`render_crops`, then fill `row.crop`); the
ladder-walk-and-predict logic is a third, independently testable
concern — "which rung fits this population under this budget" needs no
row, no bibkey, no crop_file lookup, only a directory and a list of
titles. Keeping it in its own module let the five REQUIRED unit tests
(under-budget/no-copy, over-budget/first-fit, floor/over-budget,
width-preserved, source-untouched) run against `choose_rung` directly, with
no `ensure_crops` plumbing (fake download/render functions, row
dataclasses) standing between the test and the thing being tested.

WHY CALLED FROM `ensure_crops`, NOT FROM THE EVIDENCE COMMAND. This is the
one that actually matters, and it turns on WHICH POPULATION the budget must
be computed against. `gate.PUBLISHED_FILES` names FIVE files per document —
`evidence-equation.pdf`, `evidence-formula.pdf`, `evidence-table.pdf`,
`evidence-image.pdf`, `residuals.pdf` — and the four `evidence-<kind>.pdf`
files are each a SEPARATE compile of a SEPARATE row subset (`reports/
evidence.py:build`, one call per kind). The budget has to be decided per
KIND, against exactly the crops THAT kind will embed — gilmore's problem is
its FORMULA evidence at 115.4MB; its equation/table/image evidence were
never close to 100MB. `ensure_crops` is the one place that already holds
the FULL, UNFILTERED `rows_by_kind` dict (built once by `build_rows`, before
`cmd_evidence`'s own `--kind`/`--all-kinds` filter and before `residuals.py`
narrows it to the open subset), so grouping by kind there gives the budget
function EXACTLY the population each `evidence-<kind>.pdf` will draw from —
computed once, in the one place both `cmd_evidence` and `cmd_residuals`
already call. Deciding it in the evidence command instead would need the
same per-kind grouping re-derived there, AND a second copy inside
`cmd_residuals` for the same rows — two call sites computing the same
number from the same input, which is exactly the "two mechanisms nobody
separated" shape rule 18 warns about.

WHY `residuals.pdf` NEEDS NO BUDGET OF ITS OWN. It draws a SUBSET of the
same equation/formula rows `evidence` already budgeted, selected by
`residuals.select` (open items only). Because `ensure_crops` computes the
per-kind rung against the FULL population before any filtering, a residuals
row simply inherits whichever copy (full-size or already-scaled) that row
was given — always a fraction of a population already brought under
budget. Measured: gilmore's `residuals.pdf` built at 875KB, reusing the
already-floored formula crops without any separate check (out/655.txt
"REAL CORPUS PROOFS" below).

WHY THIS KEEPS `from_document.py` THE ONLY MODEL-AWARE MODULE. Neither
candidate needed to change on this axis — `ensure_crops`, `evidence.py`,
`residuals.py` and now `budget.py` all take rows/paths/titles, never a
`docmodel.core.Document`. The constraint was a check on the decision, not a
reason to pick one seam over the other; it ruled out nothing here because
no candidate needed the model. It IS a reason `budget.py` reads crop FILES
and a title list rather than, say, taking a `Document` and re-deriving
region metadata itself — that would have made it a second model-aware
module for no reason, since the crop bytes already on disk are the ground
truth for what will actually be embedded.

IMPLEMENTATION
------------------------------------------------------------------------

`src/pdfdrill/reports/budget.py` (NEW):
  `CROP_BUDGET_MB = 20.0` — the user's sentence, verbatim, in the docstring.
  `CROP_LADDER = ((0.85,75),(0.70,75),(0.60,72),(0.50,70),(0.42,70))` —
    measured 2026-09-09 on 200 sampled gilmore crops (task-655-brief.md);
    FLOORED at 0.42/q70 (0.35/q68 measured "degrading" by eye on
    gilmore-lie-groups_FO0006 and is never offered).
  `choose_rung(src_dir, titles, budget_mb, ladder) -> (scale, quality,
    total_bytes, over_budget)`. Rung 1.0 means "leave the originals alone" —
    its `total_bytes` is `os.path.getsize` on today's files, NEVER a
    re-encode, which is what makes an under-budget document provably
    byte-identical (item 4). Every smaller rung is the REAL re-encoded size
    of every one of `titles` computed IN MEMORY (`io.BytesIO`, never
    touching disk) — the search costs CPU, not I/O, and only the WINNING
    rung is ever written to disk (by `scale_crops`, called once, after the
    search ends). `over_budget=True` only when even the floor does not fit;
    the floor is still what gets built.

`src/pdfdrill/report_tex.py` — `scale_crops` gained `force: bool = False`.
  Its existing mtime cache (skip re-encoding if the destination is already
  newer than the source) is right for a same-rung rebuild but WRONG for a
  rebuild that lands on a DIFFERENT rung (a grown document, a changed
  budget) — the destination would look "fresh" and silently keep the OLD
  rung's bytes under the NEW rung's name. `reports.budget`'s caller in
  `crops.py` always passes `force=True`; every other property (originals
  untouched, returns `{title: ORIGINAL pixel width}`) is unchanged.
  `tests/test_scale_crops.py::test_scale_crops_force_bypasses_the_mtime_
  cache` reproduces the stale-cache bug with `force=False` and shows
  `force=True` fixes it, on real Ghostscript-free PIL round-trips.

`src/pdfdrill/reports/rows.py` — `px_width: str = ""` MOVED from
  `EquationRow` up to the base `EvidenceRow` (538 gave only equations this
  field, since only equation crops were ever scaled). Every row kind can
  now be routed through a scaled copy, so every kind needs somewhere to
  carry the ORIGINAL pixel width forward; `reports/tex.py:render_row`
  already reads it via `getattr(r, "px_width", "")`; no renderer changed.

`src/pdfdrill/reports/crops.py`:
  `CROPS_DIR_B = "report-crops-b"` — the scaled copies' home, same reason
  `scale_crops` itself refuses to touch its source: `report.pdf`'s tables
  and the CDN equation crops read `CROPS_DIR` directly.
  `_apply_budget(lst, crops, crops_b, budget_mb)` — one kind's rows (crop
  already resolved via `crop_file`'s bibkey-history lookup, task 264, NOT
  re-derived from `identifier`). Gathers the DISTINCT crop stems, calls
  `choose_rung`; at rung 1.0 returns the rows untouched; otherwise calls
  `scale_crops(..., force=True)` and repoints `crop`/`px_width` for exactly
  the rows whose stem came back in the returned widths dict (a row whose
  file failed to re-encode keeps pointing at its full-size original — a
  graceful degrade, not a crash).
  `ensure_crops` now loops `for kind, lst in rows.items()`, calling
  `_apply_budget` per kind, and appends a compact note ("budget (20MB):
  formula scale=0.42 q=70 18.1MB") only when at least one kind was scaled —
  a document that needs nothing says nothing extra.

`src/pdfdrill/commands.py` — `cmd_evidence`/`cmd_residuals` gained
  `budget_mb: "float | None" = None`, defaulting to `reports.budget.
  CROP_BUDGET_MB` when not given, threaded straight to `ensure_crops`.

`src/pdfdrill/cli.py` — `_do_evidence`/`_do_residuals` parse `--budget-mb`.

`.claude/skills/pdfdrill/commands.yaml` — `budget_mb` flag added to both
  `evidence` and `residuals`; `python3 tools/skillsync.py all .` re-run
  (manifest ↔ HANDLERS still in sync, 148/148; SKILL.md and
  `_help_generated.txt` regenerated).

------------------------------------------------------------------------
A FINDING (rule 12 — an unexplained delta is a finding, not an observation)
------------------------------------------------------------------------

Six documents' formula evidence lands 0.3-2.1MB OVER the 20MB budget even
though `choose_rung`'s OWN prediction for every one of them was under
budget (e.g. gilmore: predicted 18.1MB of crop bytes at the floor, actual
compiled PDF 20.4MB — a 2.3MB, 12.7% gap). None of these were reported
"OVER BUDGET" by the code's own check (that check is against the ladder,
and every one of the six found a rung whose CROP bytes fit).

MECHANISM: `choose_rung` predicts the SUM OF CROP FILE BYTES, not the
compiled PDF's bytes. 538's own measurement says images are "~96.8%" of an
evidence PDF — true at the ORIGINAL, unscaled size, where the ~3.2%
non-image overhead (xelatex's own apparatus: fonts, table structure, PDF
object overhead) is a small absolute number against a huge image total. Once
the images are compressed down by 2-3x, that SAME roughly-constant absolute
overhead becomes a much LARGER fraction of a much SMALLER total — the crop-
byte prediction does not shrink to account for it, so the actual PDF ends up
further above the crop-byte figure than at full size. This is consistent
with, not contradicted by, 538's 96.8% figure: that number was never claimed
to hold at every compression ratio, and this task's budget spec (brief item
2) explicitly chose to predict from crop bytes rather than repeatedly
compiling a real PDF, for speed — this is the cost of that choice, made
visible rather than hidden.

NOT FIXED HERE: closing this gap would mean either compiling the real PDF
to verify (expensive — the brief explicitly rejected this for the search)
or giving `CROP_BUDGET_MB`'s ladder search a safety margin (e.g. searching
against `budget_mb * 0.9`) to absorb the overhead — a threshold with no
measured basis yet, and a decision that changes user-visible sizing, so
left for the user rather than picked unilaterally (rule 9/10). Every actual
number this produces is still reported above (the "after" column); nothing
is silently rounded down to look like it met 20MB when it did not.

WHAT WAS NOT DONE
------------------------------------------------------------------------

* `residuals.pdf` was NOT rebuilt across all 20 documents (it draws a small
  subset of already-budgeted rows and was not the reported problem). Spot-
  checked on gilmore: rebuilt at 875KB, inheriting the floor-rung formula
  crops with no separate budget check, exactly as the seam decision
  predicts (see "REAL CORPUS PROOFS" above is silent on it deliberately —
  it is a design consequence, not a new measurement, and stated in the seam
  decision section instead).
* The pre-existing `report-crops-b/` directories found in several document
  folders (dated 2026-09-03, before this task existed) are leftover from an
  earlier, unrelated exploratory use of `scale_crops` — the same name this
  task's `CROPS_DIR_B` constant also uses. They were left in place rather
  than deleted (not this task's data to discard) and confirmed, on
  `1605.05775`, to be inert: `ensure_crops` neither read nor wrote them
  when nothing needed scaling. Where THIS task's code DOES scale a kind, it
  passes `force=True`, so any stale file with the same name from that
  earlier run is overwritten with the current rung's correct bytes, not
  silently kept.
