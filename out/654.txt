654 — the locally rendered crops were drawn from the wrong page box
=====================================================================

THE USER'S REPORT, CHECKED FIRST (rule 14): gilmore-lie-groups_FO0006's crop
does not capture its line. It does not. Reproduced independently before any
code changed (scratchpad/g15_fo0006.png, drawn by the controller): the
recorded region for FO0006 — page 15, latex `(+,-, \times, \div)`, host line
"four standard operations of arithmetic \((+,-, \times, \div)\) as well as
extraction of the nth" — lands the crop five text lines below that line.

THE MECHANISM. MathPix's own page image is the PDF's CropBox, not its
MediaBox. `pdf_reading.rasterize` renders the MediaBox (no `-dUseCropBox`),
and `report_tex.render_crops` mapped MathPix pixels onto that raster with
ONE scale factor read off the width (`s = raster_width / mathpix_page_width`)
and no origin offset for the CropBox's inset. On a page whose CropBox equals
its MediaBox this is a no-op; on a page whose CropBox is inset, it is wrong
on both axes, and the y error is PROPORTIONAL to y, so it grows down the
page — about one line near the top, five lines by y=1599 on gilmore p15.

THE DECISIVE PROOF (this is stronger than eyeballing an aspect ratio, and it
needs no assumption about scanner resolution or physical page size — see the
final section). A single rendering produces ONE dpi, not two. Compute the
implied dpi on each axis two ways — MathPix's page_width/page_height against
the CropBox extent, and against the MediaBox extent:

    gilmore-lie-groups p15
      MediaBox  (0, 0, 493, 700) pt          = 493.00 x 700.00 pt
      CropBox   (13.68, 30.24, 452.68, 692.80) pt = 439.00 x 662.56 pt
      MathPix   1525 x 2301 px
      dpi against CropBox : 250.11 (x)  250.05 (y)   <- agree to 0.02%
      dpi against MediaBox: 222.72 (x)  236.67 (y)   <- disagree by 6.3%

    cardona-qft-methods p8
      MediaBox 595.00 x 842.00 pt   CropBox 410.68 x 619.50 pt
      MathPix  1426 x 2152 px
      dpi against CropBox : 250.00 (x)  250.11 (y)
      dpi against MediaBox: 172.56 (x)  184.02 (y)   <- disagree by 6.6%

    kohlhase-omdoc p10
      MediaBox 595.00 x 842.00 pt   CropBox 430.00 x 660.00 pt
      MathPix  1494 x 2292 px
      dpi against CropBox : 250.16 (x)  250.04 (y)
      dpi against MediaBox: 180.79 (x)  195.99 (y)   <- disagree by 8.4%

The CropBox reading lands the two axes within 0.16 dpi of each other and
within 0.16 dpi of a round 250; the MediaBox reading forces them 6-8 dpi
apart, which no single Ghostscript/MathPix render can produce. MathPix
rendered the CropBox. `pdf_reading` never asked it to.

Three things this settles:

1. MathPix renders every page of every one of these 20 documents at 250 dpi
   OF THE CROPBOX. skewC never exceeds 0.12 dpi across 3,835 pages. It is a
   constant, not a per-document choice — at least across this corpus.
2. Exactly four documents carry an inset CropBox (cardona-qft-methods 377/378
   pages, gilmore-lie-groups 332/333, kohlhase-omdoc 422/425,
   voloshin-hypergraph 302/303), and they are exactly the four whose local
   crops were wrong. The other sixteen have CropBox == MediaBox on every
   page, which is why the fix is a byte-identical no-op for them (measured
   below, both synthetically and on a real published document).
3. On the four, the MediaBox reading forces the two axes 11.6-20.8 dpi apart
   — an impossibility for one rendering — which is the arithmetic version of
   the same five-line visible error.

WHY THIS SURVIVED: on every one of the four affected documents, PAGE 1's
CropBox equals its MediaBox (skew 0 there even under the MediaBox reading).
An inspection that only ever looked at page 1 — the natural first page to
check — saw nothing wrong. The defect only shows once a real inset CropBox
page is checked (verified on gilmore p18 and p15 in this task).

THE METHOD PITFALL, HIT ONCE HERE TOO: a first draft of the corpus-wide dpi
table opened `report.pdf`/`residuals.pdf` by a `*.pdf` glob inside the
document folders and produced nonsense figures — the same mistake 634 named
("six PDFs sit beside every document"). The reliable rule, used throughout
this task's scripts: derive the PDF from `<lines.json stem>.pdf` /
`<folder name>.pdf`, never glob.

WHAT THE DPI FIGURE IS NOT NEEDED FOR. The user separately asked how
MathPix's own render resolution is defined — it is not a documented
constant, and for a scanned book the PHYSICAL page size can only come from
outside the PDF (the Gilmore hardcover measures 25.0 x 18.4 cm, close to
this page's MediaBox — 493 x 700 pt = 17.39 x 24.69 cm at 72 pt/in — so the
MediaBox here is close to the scanned sheet and the CropBox is the trimmed
content area within it; the two are not simply proportional, which is
exactly why a shared scale factor is the wrong tool). The 654 fix itself
needs NEITHER a dpi NOR a physical page size: the mapping is
`raster_px / mathpix_px`, per axis, and BOTH are measured directly off the
artefacts on disk — the rendered raster's own pixel dimensions and MathPix's
own page_width/page_height in lines.json. Nothing is assumed or looked up.
That is why the fix is robust to whatever resolution MathPix picks per
document — 250 dpi is an observed constant across this corpus (see above),
not something the code depends on.

THE DECISION (step 1 of the brief).

(a) rasterize with `-dUseCropBox` so the raster IS MathPix's page, then scale
    x by width and y by height independently.
(b) keep the MediaBox raster and map through the CropBox offset.

CHOSE (a). Reasons:

  * Fewer moving parts: no offset arithmetic anywhere. Once the raster's
    origin coincides with MathPix's own origin (both are the CropBox's
    top-left corner), the mapping needs only two per-axis ratios,
    `raster_size[i] / mathpix_size[i]`.
  * It makes the raster mean what every consumer already assumes ("the
    raster is the page") — matching what a PDF viewer shows by default for a
    page with a CropBox, and what MathPix's own page image already is.
  * PROVEN SAFE for the shared rasterizer before it was touched (the "Before
    You Begin" gate): a page whose CropBox equals its MediaBox renders
    BYTE-IDENTICAL with and without `-dUseCropBox`. Measured directly (not
    assumed) on:
      - gilmore-lie-groups page 1 (equal boxes) — `cmp` clean.
      - pdfdrill's own report.pdf page 1 (A3, equal boxes, the ink chain's
        input) — `cmp` clean.
      - Programmatically, in `tests/test_pdf_reading.py::
        test_use_cropbox_is_byte_identical_when_boxes_agree` (real
        Ghostscript, not mocked).
      - On the real corpus: `refine.render_crops` re-run on the UNAFFECTED
        published document 1605.05775 (12 pages, equal boxes throughout) —
        138 of 138 crops byte-identical to what the pre-654 code had already
        written (script + result:
        ~/pdfdrill-library/1605.05775/out/654/{script.py,result.txt}).
  * NOT chosen (b) because it needs the CropBox origin as a live input to
    EVERY call site doing the mapping, and a mistake there (as this defect
    itself was) is silent — (a) needs no offset at all, so there is nothing
    to get backwards.

CropBox/MediaBox for the mapping itself: NOT read (see "what the dpi figure
is not needed for" above) — `-dUseCropBox` performs the alignment inside
Ghostscript; the code only needs to measure the rendered raster's own pixel
size afterwards. `pdfinfo -box` is used only for the diagnosis/proof above
and for the byte-identity gate, never inside the mapping formula.

Implementation: `pdf_reading._gs_base`/`rasterize`/`render_page` gained an
opt-in `use_cropbox: bool = False` parameter (default off — every OTHER
raster consumer in the codebase is untouched by default). A new pure
function, `pdf_reading.mathpix_to_raster(x, y, w, h, *, raster_size,
mathpix_size)`, does the per-axis scale + clamp and returns `None` rather
than a plausible-looking wrong box when either MathPix dimension is falsy or
the result is empty (rule 5). `report_tex.render_crops` and
`refine.scan_crop` now call `rasterize(..., use_cropbox=True)` and route
through this one function; nobody else computes the mapping by hand.
