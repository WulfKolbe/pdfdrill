C. A THIRD DEFECT, FOUND ONLY BY RUNNING THE REAL COMMAND
------------------------------------------------------------------------------
The on-disk bundle has 32 dead links where my in-memory harness had 0, because
the real `cmd_model` builds object types my harness does not: the on-disk model
has 32 References and 4 Citations, and my 7-document harness produces neither.

All 32 are the same shape:

    references/0008113v1_REF_Malakhov1998.md   [citation](./.md)

The source is `{{||CIT}}` — a template transclusion with an EMPTY title, which
in TiddlyWiki means "the CURRENT tiddler through template CIT". okf takes the
title before `||`, gets `""`, and `_link_path("")` returns `./.md`: a link to a
file whose name is empty.

This is neither of the two classes 267 diagnosed and neither 269 nor 270
touches it. It is not fixed here — 271 is a verification step, and a defect
found during verification should be named rather than quietly repaired inside a
step whose numbers are supposed to be comparable.

Recorded as open:
    okf `{{||CIT}}` — empty-title template transclusion emits `./.md`.
    32 occurrences in 0008113v1 alone; every Reference unit carries one.

WHAT THIS SAYS ABOUT THE HARNESS
------------------------------------------------------------------------------
The 7-document harness runs `config.json`'s 18 modules. `cmd_model` runs those
AND the bibliography/reference stage. So every number in 268-271 measured from
the harness is sound for the object types it builds and blind to References and
Citations — which is exactly how a whole defect class stayed invisible across
four steps. The on-disk run is the one that found it.

Nothing changed in this task.
