THE NAMING DEFECT IS REAL AND UNIVERSAL
----------------------------------------
  titles that are NOT four-digit padded:   314 of 314

Every one is `<bibkey>_H<n>` — `_H1`, `_H2`, … `_H10`. The sort defect
named in the task is present in every document that has any section at all,
and `_SEC<nnnn>` appears nowhere.

THE DETECTION RULE IN THE SPEC WOULD FIND FAR FEWER, NOT MORE
---------------------------------------------------------------
This is the finding I would want before writing any code against it.

  lines of type `section_header`, corpus-wide          2,215
  of those, with a non-empty `children_ids`              153   (6.9%)
  Section objects that exist today                       314

The specified detector — `type == "section_header"` AND `children_ids`
non-empty — matches 153 lines. The existing producer yields 314 objects,
twice as many, so it is not using that rule. Building to the spec as
written would REPLACE 314 sections with at most 153 and lose over half of
them, including every section in documents whose headers carry no children.

Per document the gap is stark: gilmore has 218 headers, 2 with children, 4
Sections. cardona has 259 headers, 12 with children, 24 Sections.
lyche 292 / 32 / 64. The ratio Section = 2 x children-bearing headers holds
almost exactly across the corpus, which says the current producer pairs each
such header with something — but it is not the rule in the brief.

WHAT I HAVE NOT DONE, AND WHY

Not built to the spec: doing so would be a net loss of 161 sections and I

about is a real one and its replacement needs a coordinate that exists.
