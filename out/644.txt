644 — the internal label scheme, settled
========================================

THE DECISION: LEAVE THE TITLES. SETTLE THE SCHEME IN ONE TABLE.
  The user offered two routes — regularise every title to PREFIX + four
  digits with no separator, or leave the titles and fix the macro layer.
  Neither was quite the fault. What had drifted was not the titles: the
  titles ALREADY satisfy "one shape per object type", and this run measured
  that mechanically on both documents (0 kinds with more than one shape).
  What had drifted were the CONSUMERS. Every CLI carried its own copy of the
  shape — nine format strings and five regexes across eleven modules — and
  three of the copies were already wrong (see WHAT THE COPIES HAD GOT WRONG).

WHY NOT THE RENAME
  A rename buys nothing that the titles do not already have, and it costs:
    * every crop file on disk is named after a title
      (`report-crops/<bibkey>_EQ0001.jpg`, `_TAB_001`, `_PIC_0001`);
    * every identifier printed in the evidence PDFs published this week is a
      title, and `\ident{...}` in those .tex files is what `inkconvert` and
      `reports/gate` join measurements to;
    * `REF_<citekey>` is a CONTRACT, not a label — the LaTeX injector and
      `crossref` resolve against it, and `citekeys.citation_title` exists
      because three call sites once derived it independently and disagreed
      (46 of 46 dangling on 2209.00445v3);
    * `renamefolder` already treats `<bibkey>_PIC_0001` as a row id it must
      rewrite by substitution.
  A rename is a corpus-wide migration to make a table tidier. The table can
  hold the shapes exactly as they are.

  padded Sections to four digits since 566.

THE ONE DELIBERATE DIFFERENCE: FOOTNOTES (646-a)
  646 measured 17 title collisions on penev_A and 13 on penev_B — one
  tiddler standing for up to SIX Footnote objects. The SHAPE was never the
  problem (`FN` + four digits is right and is unchanged); the NUMBER SOURCE
  was. `FN<refnum>` used the PRINTED footnote number, and printed numbers
  restart on every page, so `penev_A_FN0001` named four objects and
  `penev_A_FN0009` named six. On import TiddlyWiki keeps one and the other
  five bodies are gone. A title must name exactly one object, so:

    the footnote number is now the object's POSITION IN THE FLOW,
    exactly as Sidenote, ListItem and every other counted type.

  The printed number is not lost — it stays in the `refnum` FIELD, which is
  what the `FN` template renders, so the superscript a reader sees is
  unchanged. `_substitute_footnotes` still resolves a marker through
  `fn_by_refnum` (first footnote with that printed number wins), so no
  transclusion dangles; what it does NOT yet do is resolve per paragraph,
  which stays open as 646-a. This fixes the silent overwrite, not the
  mis-targeting.

  `IMG` IS A DEAD PREFIX, and is declared as one rather than quietly kept. No
  projector has ever emitted `<bibkey>_IMG<NN>` — a picture is `_PIC_0001` —
  and a scan of the whole library (1336 `report.tex` files and every
  `tiddlers.json`) finds zero occurrences. It stays ACCEPTED because 596's
  contract is "wide enough not to miss a row" and narrowing it is a behaviour
  change this task did not measure. It lives in `inkmeasure._DEAD_PREFIXES`
  and reaches the pattern through `prefix_alternation(..., extra=...)`, whose
  docstring says that every use of `extra` is a claim that a prefix is dead.

THE GUARD — REBUILT IN FIX ROUND 1, BECAUSE THE FIRST ONE COULD NOT SEE
  `test_no_second_shape_regex_survives_in_src` matched the literal text
  `(?:FOX?` / `(?:FOX|FO`. It could not see a CAPTURING group, and it could
  not see an alternation in which FO is not first — so it passed, green, while
  four live shape regexes stood. A guard that cannot fail is rule 11 in its
  purest form, and it was mine.

  `test_no_second_title_prefix_regex_survives_in_src_or_tools` is built FROM
  the table: it parses every string literal in `src/` and `tools/` with `ast`
  and flags any `A|B(|C…)` run holding two or more of `TITLE_SHAPES`' own
  prefixes AND sitting where a title's prefix sits — immediately after the `_`
  that follows the bibkey. That `_` anchor is what separates a TITLE
  alternation from a TEMPLATE one: `{{…||(FO|EQ|FREF)}}` in `commands.py`
  names templates, and FO and EQ are both a template and a prefix. Without
  the anchor the threshold has to be raised to 3 to avoid that false
  positive, and at 3 `crossref`'s two-prefix `_(EQ|FOX?)` slips through. The
  anchor buys the threshold of 2, which is what catches it.

WHAT THE COPIES HAD GOT WRONG — three live defects, found by writing them down
  1. `distill_reader` numbered Footnote `_FN_{i:03d}`, Sidenote `_SN_{i:03d}`
     and ListItem `_LI_{i:04d}` — a separator and a digit width the projector
     has NEVER emitted. Every footnote, sidenote and list-item anchor the
     distill page built pointed at a tiddler that does not exist.
  2. `llm_text` numbered Section `{b}_H{i}` — unpadded, which the projector
     stopped emitting at 566. Every Section pointer in the LLM dump named a
     title that does not exist.
  3. `report_tex.TYPED_TITLE` demanded a digit FLUSH against the prefix
     (`_(…|TAB|DIA|PIC)\d`), so it never matched `_TAB_001`, `_DIA_0001` or
     `_PIC_0001`. The 463 guard — "an empty report from a non-empty
     projection is a defect" — was blind to three of the five kinds
     `rows_for` reports on, because `rows_for`'s own regex (the second copy,
     without the `\d`) matched them and the guard's did not.
  All three are fixed by construction: there is one shape and one place.

CONSUMERS DELIBERATELY NOT MOVED, WITH THE REASON
  `inkconvert._IDENT` / `_IDENT_FIND` and `reports/gate._IDENT_ANY` match an
  identifier FRAGMENT inside `\ident{...}` in a generated .tex — it carries
  `\allowbreak{}` inside the braces and a ` (was)`/`(now)`/`(basis)` suffix
  after the digits. `parse_title` cannot read that without changing what they
  match, and rule 17 was learned on exactly these three patterns. They keep
  their character classes and their explicit SUBSET of kinds; only the
  prefixes now come from the table, via `prefix_alternation`.

  `transclusion_render.num_from_title` is NOT moved. It answers "the last
  number in this title", which is deliberately shape-agnostic: it is called
  on `REF_<citekey>` titles too, where `parse_title` correctly reports no
  number at all and would change what `distill_reader._prose` renders for a
  citation. Its behaviour is kept and this paragraph is the record.

  `tools/*.py` (census481, bed492, uniscan475, parallel474, midstring486,
  census509, pkggap482, beddiag492) each carry `_(EQ|FOX?|TAB)\d`. They are
  frozen per-task measurement scripts under rule 19 — the exact source that
  produced a published number — not consumers of the live scheme. Rewriting
  them would break the reproducibility that is their only job. All eight are
  whitelisted BY NAME with the task each belongs to in
  `tests/test_title_scheme.py::_FROZEN_SCRIPTS`, never by a blanket `tools/`
  exemption, and a test asserts each still exists and still offends.

WHAT IS LEFT
  644-a  `_substitute_footnotes` still resolves a marker by a DOCUMENT-WIDE
         printed-number map, so all four markers printed "1" still point at
         the first footnote numbered 1. The titles no longer overwrite each
         other, which is what 644 owed; the per-paragraph resolution is
         646-a and is untouched.
  644-b  `Toc` is in `BLOCK_TEMPLATE` but not in `_BLOCK_TYPES_IN_SECTION`,
         so the `TOC` entry there is unreachable. Harmless, and left alone
         rather than removed: the two sets are now tested against each other
         in the direction that matters (every block type HAS a template).
  644-c  The `EQ` template is defined and emitted by nothing. Either a
         substitution should produce it (an in-text "see Equation 1.1") or
         it should be documented as hand-use only. It is the latter today.
  644-d  `formula_report`'s `_p<NNN>` suffix is a second identity for one
         equation. `parse_title` strips it, so nothing breaks, but the
         suffix has no reader that needs it and could go.
  644-e  `num_from_title` is the last shape-adjacent reader not on the
         table, for the reason above. Moving it means deciding what a
         citation's "number" is, which is a `distill_reader` question.
  644-f  `IMG` is accepted by `inkmeasure._IDENT_TOKEN` and emitted by
         nothing (zero occurrences in 1336 library `report.tex` files).
         Removing it is a one-line change to a measured-zero population; it
         was left because 596's contract is deliberately permissive and
         narrowing it belongs with a re-measurement of that pipeline.
  644-g  The guard reads STRING LITERALS. A shape alternation assembled at
         runtime from pieces ("EQ" + "|" + "FO") is invisible to it. Nothing
         in the tree does that today; if one appears, the guard will pass.

CONCERNS
  The FN change is a real change to a published artefact: anyone holding a
  wiki built before this commit has `FN<printed number>` titles and will get
  `FN<flow position>` on the next projection. Nothing links to a footnote
  from outside the array (no crop file, no evidence-PDF identifier, no
  `\ident{}` row is ever an FN), so the blast radius is inside the array —
  but it is not zero, and it is the reason it is called out as the one
  deliberate difference rather than folded into "byte-identical".
  Both documents were measured; penev_B carries no Reference, Table, Toc,
  Abstract or ListItem objects, so five rows of the table are exercised on
  penev_A alone and four kinds (Theorem, Proof, CodeListing, LtxCommand)
  on neither. Those four are covered by unit tests only.
