WHY `base` AND NOT `commit`
------------------------------------------------------------------------------
The commit CONTAINING a report cannot exist when the report is written: the
write-up and the change it describes land in the same commit, so its hash is
not computable until after the file is on disk. Naming the base — the tree the
work started from — is a pointer rather than a claim, and the containing commit
is one command away whenever anyone wants it:

   git log --diff-filter=A --format=%H -1 -- out/237.txt

The retrofit uses the same definition: the PARENT of the commit that added each
file, and the commit date as the timestamp. Both are facts git recorded, not
reconstructions.

WHY THERE IS NO BRANCH FIELD, THOUGH I WROTE ONE FIRST
------------------------------------------------------------------------------
The first version emitted `branch=eqblobs-and-gzip-tex`. Git records no such
thing. `rev-parse --abbrev-ref HEAD` is the branch NOW, not the branch a commit
was made on, so on 151 retrofitted reports that field would be an unverifiable
claim wearing the costume of provenance — the exact failure this line exists to
prevent, introduced by the line itself.

It also adds nothing: the hash locates the tree by itself. Dropped, and a test
asserts it stays dropped.

THE RETROFIT REPORTED SUCCESS WHILE DOING THE WRONG THING
------------------------------------------------------------------------------
Removing the branch field meant re-stamping. The strip pass reported

   stripped the branch-bearing stamp from 0 files
   stamped 151, already had one 0, skipped 0, of 151

and both numbers were consistent with success. They were not. The strip
pattern was double-escaped inside a heredoc, so `\\d` reached Python as a
literal backslash-then-d and matched nothing; the stamper then found no
well-formed first line on any file and PREPENDED, leaving all 151 with two
stamps. `head -1` looked perfect on every one of them.

Caught by asking a different question than "did it report success" — how many
files carry TWO stamp lines. 151. Fixed by replacing rather than prepending,
with an assertion that the two hashes agree before deleting either. A test now
covers the duplicate case specifically, because the failure was invisible to
the check that was supposed to prevent it.
