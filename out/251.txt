WHAT IS ACTUALLY WRONG: 1,239,021 SUBTYPE VALUES, NONE READ

them — every `subtype` comparison in src/ is against "code" or "acronym", both
of which pdfdrill SETS itself (diagram.py stamps subtype="code" for TikZ). The
field arrives populated on 31% of all lines and no module consults it.

DehyphenationProcessor's docstring calls its own rule "intentionally a *naive
demo*" that "will false-positive on real hyphenated compounds like
'one-to-one' (it produces 'oneto-one')", and invites replacement by "dictionary
lookup, language model, compound detection". The replacement it needs is none
of those. MathPix already answered the question per line, 142,042 times for the
hyphen case alone, and the answer is sitting in a field nothing reads.

ParagraphProcessor does not read it either — no occurrence of `subtype` or
`continues_line` anywhere in paragraph.py.

WHY THIS ONE WAS INVISIBLE
------------------------------------------------------------------------------
out/250's contract checks that every TYPE is claimed. Every type carrying these
subtypes is claimed — text, diagram, chart, page_info are all in CLAIMED — so
the contract passes and 1.2M unread values sit underneath a green check.

A type-level contract cannot see a field-level gap. The same enumeration that
found `list_item` would have found this on day one if it had enumerated KEYS as
well as type values; it enumerated one field because that was the field the
question named.
