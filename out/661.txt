    _ENV_MAP = (("align", "aligned"), ("alignat", "aligned"),
                ("flalign", "aligned"), ("eqnarray", "aligned"),
                ("gather", "gathered"), ("multline", "gathered"),
                ("split", "aligned"))

    def to_inline_env(latex: str) -> str:
        out = latex or ""
        for src, dst in _ENV_MAP:
            out = re.sub(r"\begin\{%s\*?\}" % src, r"\begin{%s}" % dst, out)
            out = re.sub(r"\end\{%s\*?\}" % src, r"\end{%s}" % dst, out)
        out = re.sub(r"\(?:begin|end)\{equation\*?\}", "", out)
        return out.strip()

THE DESIGN QUESTION — where the transform belongs
----------------------------------------------------
`renderable()` is measured, tested (60+ existing tests depend on its exact
behaviour), and its whole contract is "judge this value." Every rewrite it
already performs (whitespace collapse, the 634 boldsymbol/operatorname
swap, furniture-drop, delimiter-glue repair) is a SAFETY normalization —
none of them changes which environment a reader would say the value is.
Mapping `align` to `aligned` is a different kind of move: it changes the
value's own identity, not just its safety. Bolting it into `renderable()`
would blur that line for every future reader of the function's docstring,
which currently earns its claim ("safe to put inside $...$, or refuse")
honestly.

So the map lives OUTSIDE the gate, as `to_inline_env()`, and a new function
composes the two:

    def display_safe(latex: str) -> str:
        return renderable(to_inline_env(latex)) if latex else ""

`renderable()` itself gained one paragraph saying explicitly that it does
NOT call `to_inline_env()`, and why — so the boundary is stated where a
reader of the gate would look for it, not only where the map is defined.

Every call site in report_tex.py that previously called `renderable(latex)`
to decide "does this row render" or "what goes in the Rendered cell" was
switched to `display_safe(latex)` — seven sites: `row()` (the main
Display-equations/Inline-formulas builder), `unresolved_formulas()`,
`refused_for_align_only()`, `findings_rows()`, `findings_tex()`'s local
`rendered()` closure, `b_tex()`'s per-row loop, and the Tables section's
per-row loop. This matters beyond tidiness: `unresolved_formulas()`'s own
docstring states an invariant — "qualifies... exactly the row whose
Rendered cell says (not rendered)" — that breaks the moment the actual
Rendered cell (in `row()`) and this classifier disagree on what "renders"
means. Routing every one of the seven through the same `display_safe()`
keeps that invariant true BY CONSTRUCTION rather than by the two
implementations happening to agree today.

Two call sites were deliberately NOT switched, and are named as such in
`display_safe()`'s own docstring:
  - `region_render()` (image-region LaTeX, DIA/PIC) — a different
    function's concern, gated by its own `_MATH_ENVS` allowlist. Mapping
    there BEFORE that allowlist check would let `align`/`gather`/etc.
    through it as a side effect — a scope decision for that function, not
    this task.
  - `listing_cell()`'s `\(...\)` spans inside an `lstlisting` body — a much
    narrower, rarer shape (formulas inside a code listing); not measured
    to carry a display environment anywhere in the corpus, left unchanged.

THE CONSEQUENCE — which form is published
--------------------------------------------
DECISION: the "LaTeX source" column shows `latex` UNTRANSFORMED — MathPix's
(or the e-print source's) own reading, exactly as read. The "Rendered"
column shows the SAME reading with `to_inline_env()`'s map applied, via
`display_safe()`. The two columns are allowed to disagree, by construction,
on the population where the map fires.

ARGUMENT. The "LaTeX source" column's entire reason to exist — stated
throughout this file's own history (233's whole point: "what did the OCR
read" vs "what does this document say" are two different questions this
report exists to keep apart) — is fidelity to the reading. A silent
substitution of one environment name for another, however rendering-
equivalent, is exactly the kind of edit that column exists to NOT show.
The alternative (map the source column too) would mean the report no
longer has ANY column that states what MathPix returned for these rows —
weakening the report's core claim for the sake of two matching columns.

This is not a new posture for this file: `renderable()`'s OWN existing
rewrites (634's boldsymbol/operatorname swap, furniture-drop, delimiter-
glue repair) already make the Rendered cell diverge from the LaTeX-source
cell for other rows, and no prior task treated that as a defect requiring
a matching source-column edit — the source column's job has always been
"the reading," the render column's job has always been "what can safely
be typeset from it." This fix keeps the same division; it does not
invent one.

`row()`, `findings_tex()`'s `rendered()`, `b_tex()`'s loop, and the Tables
loop were each given a short comment stating the source cell is built from
the UNCHANGED `latex`. `b_tex()`'s docstring ("The three columns: LaTeX
source, its rendering, the image") was extended to say so explicitly,
because B.pdf carries no legend at all (B_WIDTHS' own docstring: "Three
columns, and nothing else") and has nowhere else to say it.

For every OTHER table (row()/findings_tex/the Tables section, which share
`table_open()`/`legend_foot()`), a new legend line was added and is now
ALWAYS printed (matching 181's own precedent for LEGEND_CONF: "the
confidence bands ALWAYS apply, so the legend is always printed" — the
LaTeX-source/Rendered columns are present on every table this legend
serves, so the key that says they may differ applies unconditionally):

    LaTeX source: MathPix's reading, unchanged; Rendered: the same
    reading, with a display environment (align/alignat/flalign/eqnarray/
    gather/multline/split) mapped to its in-math form so it can typeset
    in this cell — the two may legitimately differ

TWO TRAPS, both checked directly
------------------------------------
1. MAP, NOT UNWRAP. `to_inline_env()` renames the environment; it never
   deletes the `\begin{X}...\end{X}` wrapper. Verified two ways in
   `test_to_inline_env_maps_not_unwraps`: the mapped output still strips to
   NOTHING under `_strip_innermost_envs` (no residue at all — the wrapper
   is still there to be stripped) and `renderable()` accepts it unchanged;
   an UNWRAP built by the same test (deleting only the `\begin`/`\end`
   tokens, leaving the body bare) is shown to fail `has_bare_align_marker`
   after the same strip — the exact condition 659 spent a task removing
   from the opposite direction (an outer environment stripped while ITS OWN
   bare `\\`/`&` were exposed). This task does not reintroduce that shape
   from the inside.

2. RULE 17. Every fixture in the new tests starts from a genuine DISPLAY
   environment (`\begin{align}`, `\begin{split}`, etc.) with a bare `&`/`\\`
   inside it — never `aligned`/`gathered` already. A fixture starting
   in-math would pass against the UNPORTED code (nothing refuses `aligned`
   today) and would prove nothing about this map. Checked explicitly for
   `split`: `test_split_alone_reaches_renderable_but_is_not_yet_
   typesettable` confirms the RAW value passes `renderable()` unrefused
   (the auditor's own framing: this is not an over-refusal bug), and the
   live-compile test below shows what actually breaks it.

CORPUS SEARCH — why 1911.08029, not 0902.0431
--------------------------------------------------
0902.0431 (this task's default example document, and the population 657/
659 already measured) was checked FIRST, as the brief anticipated it might
need to be replaced. `grep -rl` over ~/pdfdrill-library's model.docmodel.json
files for the seven env names found 0902.0431 among 49 candidates — but a
TEXT hit is not a REAL hit: the `\begin{eqnarray*}` in that file sits inside
an alternate "latex_candidate" realization (a cross-reference text blob
from a different stream), never in the Equation's OWN `latex` prop that
`report_tex.rows_for`/`row()` actually reads. Checked directly via DocGraph:
0902.0431 has 1,219 Equation objects and 0 of them carry any of the seven
names in `props["latex"]"` — those three occurrences resolve to
`\begin{aligned}` in the actual reading. So 0902.0431 is confirmed to carry
NO display environment in any cell, exactly the brief's contingency, and a
different document was chosen.

Re-checking all 49 grep candidates through DocGraph (script and full output
saved at ~/pdfdrill-library/out/661/, corpus-level per 525's convention —
no single document): 9 of 49 carry a genuine `Equation.latex` hit, and
EVERY ONE of the nine is `split` — zero real occurrences of align/alignat/
flalign/eqnarray/gather/multline were found anywhere in this library's
Equation.latex props. This is a real, reportable finding, not an artefact
of the search: MathPix's own extraction (and whatever normalization runs
between it and `props["latex"]`) already appears to fold align/gather/
eqnarray/alignat/flalign/multline into their in-math forms upstream of
this gate for every document sampled — but `split` slips through
unnormalized. The fix stays correct and general for all seven regardless
(and is defensive for any future source that does emit them raw — an
e-print's own LaTeX, `injectlatex`'s path, is exactly such a source), but
the CURRENT corpus's measured population is `split` alone.
