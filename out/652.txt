THE 656 CORRECTION — WHY THE VERDICT IS NOT A RAW COUNT, AND NOT A RAW
VIOLATION COUNT EITHER
  The brief (written before 656 landed) asked for a verdict line reading
  "conserved" / "NOT conserved: N unclaimed, M doubly-claimed, K
  unreachable", using `conserve()`'s three raw counts. 656's corpus scan
  (1,362 models, `out/656.txt`) found `unreachable` alone is ~100%
  BY_DESIGN/OUT_OF_SCOPE noise on every real document: Page, TableCell,
  TableRow, Toc, Document are ALWAYS 100% unreachable by construction
  (verified routes, not defects — `docops.conserve.BY_DESIGN`), and
  Formula/Paragraph/Equation/… run 20-90% unreachable through a working,
  already-catalogued path (`OUT_OF_SCOPE`). A page that printed raw K would
  call every healthy document broken, which is exactly the failure mode
  the correction named.

  The obvious fix — sum `classify_unreachable(reach)["violations"]` instead
  of raw `unreachable` — is what the first draft of this task did, and it
  is WRONG in a way that only shows up on the two documents the corpus
  actually audited: penev_A and SteerableWaveletFramesBasedontheRieszTransform
  both carry real VIOLATION-class objects (Citation, List — 656's ninth and
  seventh violation types) that are AT baseline, matched exactly
  (`conserve_baseline.json`), and `conserve --gate` reads PASS for both
  (`out/656.txt`'s own "GATE VERDICT — penev_A: PASS", "... SteerableWavelet:
  PASS"). A verdict built from the raw violations sum would print "NOT
  conserved" for BOTH of the two documents this repo has actually reviewed
  — worse than the bug being fixed, because now the one case with a real
  human-reviewed baseline reads as broken.

  So the verdict is built from `docops.conserve.gate(doc, res=res)`'s own
  partition, not from `classify_unreachable` alone:
    unresolved = sum(g["new_types"].values())
               + sum(d["now"] - d["baseline"] for d in g["increased"].values())
    conserved  = (unclaimed == 0) and (doubly_claimed == 0) and (unresolved == 0)
  `new_types` (a violation type with no baseline row at all) and the
  positive delta of `increased` (more than the recorded baseline) are the
  two ways a document gets WORSE — those are what "NOT conserved" reports.
  `decreased` (fewer than baseline, including a fix dropping a type to
  zero) is explicitly EXCLUDED from this per-document verdict: it is good
  news, and it is a reason to update `conserve_baseline.json` (a
  repo-maintenance fact `format_gate_report`'s "FIXED"/"DROPPED" lines
  already carry), not a defect in THIS document. `matched` counts,
  BY_DESIGN and OUT_OF_SCOPE are all shown on the page (a labelled list plus
  `format_gate_report`'s own text verbatim when a baseline row exists) but
  never folded into the verdict.

  A bibkey with NO baseline row keeps `gate()`'s own zero-tolerance posture
  unchanged — every violation type it has becomes `new_types`, so it reads
  "NOT conserved" until someone audits it and records a baseline row. This
  is the SAME stance `conserve --gate` already takes for any document
  outside the seven-bibkey baseline (656: "an unaudited document gets ZERO
  TOLERANCE, not a silent pass"); the page does not invent a softer rule,
  it reports the existing one honestly, and it makes plain WHY on the page
  itself ("no baseline row recorded for this bibkey yet, so none of them is
  reviewed (zero tolerance, 656)").

  Verified live on both real documents (see EVIDENCE): penev_A's verdict
  reads "NOT conserved: 243 unclaimed, 29 doubly-claimed, 0 unreachable
  object(s) beyond what is already recorded" — the 84 VIOLATION-class
  objects (Citation=81, List=3) are ALL matched to baseline, so `unresolved
  = 0`; the document is still correctly flagged NOT conserved because of
  243 real unclaimed anchors and 29 real doubly-claimed ones (out/646.txt's
  own 243 figure for penev_A, unchanged), which is an honest, unrelated
  fact this task did not touch or hide.

  A regression test (`tests/test_status_html.py::test_baseline_row_
  surfaces_the_gate_report`) initially FAILED against the first,
  violations-sum design — exactly the bug this section describes — before
  the design was corrected to use `gate()`. Kept in the suite as the case
  that would catch it coming back.

  artefact size" section — for each of `reports.gate.PUBLISHED_FILES`
  present in the artefact list, the real byte size and over/under its 20 MB

  directory, which is a prediction over files this command has no reason to
  touch, not a read of the built PDF — out of scope for a page that is
  supposed to stay a pure read of what's already on disk.

  SteerableWaveletFramesBasedontheRieszTransform in the library currently
  carries one (651's own evidence run used a throwaway copy, not a

  REAL such file in the two named documents; it is covered by a synthetic
  fixture in `tests/test_status_html.py` instead

BRIEF ITEM 3 — THE LOCK, CONFIRMED RATHER THAN ASSUMED
  The brief flagged this as an open question: `status` has always been
  read-only, and `--html` makes it write a file — does
  `test_every_pdf_writer_holds_the_lock` force `@_writes` onto `cmd_status`?
  Read `tests/test_doclock.py::_doc_folder_writers` before assuming: it AST-
  walks every top-level `cmd_*` function in `commands.py`, and only flags one
  whose body contains a literal write-op call (`write_text`/`mkdir`/…) AND
  references `blob_dir`/`Sidecar`/`sc`. `cmd_status`'s own body — text or
  HTML branch — contains NO such literal call; the actual `.write_text`/
  `.mkdir` calls live inside `_write_status_html`, a SEPARATE function whose
  name does not start with `cmd_`, so the AST scan never sees them and never
  requires `cmd_status` to carry `@_writes`.

  This is not a loophole invented for this task — `commands.py` already has
  exactly this shape for a different reason: `_inkreport_chain` (its own
  docstring, cited there) is deliberately NOT `cmd_`-prefixed so the AST scan
  skips it, because it is always reached through a `cmd_*` caller that
  ALREADY holds the lock (re-entrant). This task's reason is the opposite —
  `cmd_status`'s TEXT branch is NEVER meant to hold the lock at all — but the
  mechanism (push the literal write calls into a non-`cmd_`-prefixed helper)
  is the same, and it is the one the codebase already uses, not a new
  pattern.

  `_write_status_html` is decorated `@_writes("status_html")` regardless —
  the real cross-process protection this exists for. Verified two ways
  (both in `tests/test_status_html.py`):
    - a second OS process holding the document's lock makes
      `cmd_status(pdf, html=True)` raise `doclock.DocumentBusy`
      (subprocess-based, mirrors `test_doclock.py`'s own
      `test_second_process_refuses`);
    - the lock is acquired and released within one call (no leaked lock
      file after a normal write).
  `tests/test_doclock.py::test_every_pdf_writer_holds_the_lock` and
  `::test_lock_coverage_is_reported_not_assumed` both still pass unchanged
  (76 writer rows found, same missing=[] and unguardable-count=5 as before
  this task — `cmd_status` is not among the 76 rows at all, confirming it
  was never flagged).

CONCERNS / THINGS I NOTICED BUT DID NOT FIX
  1. THE CONTENT-HASH PROOF IS CWD-RELATIVE, NOT AN ARTEFACT OF THIS TASK.
     `sc.mark(MODEL_BUILT, inputs=[lines_path], ...)` records
     `str(lines_path)`, and whoever ran `pdfdrill model` on penev_A /
     SteerableWaveletFramesBasedontheRieszTransform did so with the
     document's own folder as the process CWD, so the recorded key is the
     bare filename ("penev_A.lines.json"), not an absolute path.
     `proofs.verify()` later re-hashes `Path(path).read_bytes()` against
     THAT string — which only resolves correctly when re-checked from the
     SAME cwd. Running `pdfdrill status --html
     ~/pdfdrill-library/penev_A/penev_A.pdf` from this repo's root reports
     the model STALE (content_hash of a nonexistent
     `./penev_A.lines.json` relative to the repo root is `None`, which
     never matches the recorded hash); running the identical command with
     cwd set to the document's own folder reports it fresh. `status --html`
     handled this exactly as designed — it said "stale" and did not
     rebuild — but the underlying proof mechanism's cwd-dependence is a
     latent correctness gap in `proofs.py`/`_stale_or_absent` that predates
     this task and affects every command that checks a proof, not just
     `status`. Not fixed here (out of scope — `634`/`proofs.py` territory,
     not `652`'s); named so it does not get rediscovered as a fresh
     mystery.
  2. `conserve()`/`classify_unreachable()`/`gate()`/`ledger.materialize()`
     project the whole document in memory (the same cost `pdfdrill
     conserve`/`model --ledger` already pay). This only runs under
     `--html`, never for plain `status`, on purpose — but a very large
     model could make `--html` noticeably slower than the instantaneous
     text form. Not measured against a large document in this task; if it
     becomes a problem, the fix is the same one `--gate` already has (an
     explicit, opt-in cost), not a change to `status`'s own default.
  3. `_status_budget_notes` only recognises the five literal
     `reports.gate.PUBLISHED_FILES` names. A document with a differently
     named evidence PDF (there are none in this codebase today) would get
     no budget note; this mirrors `gate.py`'s own closed list rather than
     inventing a looser pattern match.
