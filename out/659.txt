659 — fix the environment strip: outer pairs with outer, not inner
====================================================================

"start 659 and fix the strip." The user's original question ("why does my
residuals report show equations marked '(not rendered)'?") is answered by
this defect: `renderable()`'s environment-strip loop
(report_tex.py:1465-1471 pre-fix) used a non-greedy regex
`\begin{(\w+\*?)}.*?\end{\1}`, which on `\begin{array} … \begin{array} …
\end{array} … \end{array}` pairs the OUTER `\begin` with the INNER `\end`.
The residue is then an unbalanced outer `\begin{array}` whose own `\\`/`&`
sit unshielded at brace depth 0; `has_bare_align_marker` reads them as
longtable tab marks and the row is refused.

THE FIX
-------
`report_tex.py`, new `_strip_innermost_envs()` (placed right after
`_env_balanced`, its neighbour depth-walk), replacing the loop inline inside
`renderable()`. The regex:

    _INNERMOST_ENV = re.compile(
        r"\begin\{(\w+\*?)\}((?:(?!\begin\{\1\}).)*?)\end\{\1\}", re.S)

is a negative lookahead that refuses to cross a nested `\begin` of the SAME
name — a match can only ever be an environment with no further same-name
nesting inside it — applied in a loop (cap 12, see below) so nests peel
inside-out. `renderable()` now calls `_strip_innermost_envs(lx)` where it
used to inline the broken loop; everything else in `renderable()` is
untouched.

CAP: 12, not 6
--------------
The pre-fix loop capped at 6; the salvaged code caps at 12. I chose 12,
matching the salvaged/measured value, because:
  (a) it is the value the 32-false-demotions-to-zero measurement actually
      used, so keeping it is keeping what was proven, not guessing a new
      number;
  (b) each iteration is one linear regex pass over an already-short
      equation string — the marginal cost of 12 vs 6 iterations on this
      population is not measurable;
  (c) a HIGHER cap can only ever strip MORE, never less, so it cannot turn
      a previously-safe row unsafe; and
  (d) past the cap, the behaviour is conservative BY CONSTRUCTION, not by
      a separate check I had to add — see TERMINATION below.

TERMINATION — malformed input, and past the cap
------------------------------------------------
Three malformed cases, each tested directly against `_strip_innermost_envs`
(tests/test_report_tex.py::test_env_strip_terminates_on_malformed_input):
  - unmatched `\begin` (no `\end` at all): the regex never matches; the
    first substitution is a no-op; the loop exits on iteration 1.
  - unmatched `\end` (no preceding `\begin`): same — no match, no-op, exits
    iteration 1.
  - a `\end` before any `\begin`: the regex can only pair a `\begin{X}`
    with a LATER `\end{X}` of the same name, so a leading orphan `\end` is
    never consumed; if the rest of the string DOES contain a genuine
    complete pair, that pair legitimately strips (this is correct, not a
    bug) and the loop still terminates.
  All three leave a residual `\\`/`&` that `has_bare_align_marker` still
  sees, so `renderable()` still refuses them — malformed input was never
  going to render regardless of this fix.

  Past the cap (tests/test_report_tex.py::
  test_env_strip_cap_is_conservative_past_its_depth): a same-name chain
  exactly 12 deep fully peels to nothing. A chain 13 deep, built so the
  OUTERMOST wrapper directly carries its own bare `\\` beside a
  fully-peelable 12-deep inner chain, needs ONE more iteration than the cap
  allows for that outer wrapper — it survives unstripped, its own `\\` is
  still visible to `has_bare_align_marker`, and the row is refused. Verified
  directly, not asserted: a nest deeper than the cap is refused, never
  silently passed with a partial strip.

AGREEMENT CHECK — `\substack{a \\ b}`
----------------------------------------
Per the addendum: both approaches were checked against this exact case.
  - report_tex.has_bare_align_marker(r"\substack{a \\ b}") -> False (not a
    bare marker: PASSES, not refused) — its own brace-depth walk treats
    `\substack{...}` as a shielded macro argument.
  - The salvaged structurally_safe() calls `_strip_brace_macro` first,
    which explicitly deletes `\substack{...}` bodies, then the same
    env-strip (no-op here, `\substack` is not an environment), then checks
    for bare `&`/`\\` — also PASSES.
  They AGREE: neither refuses `\substack{a \\ b}`. No finding here — the
  two approaches reach the same verdict by different mechanisms (general
  brace-shielding vs. a named-macro strip), exactly as out/657 already
  established for this document's own `\stackrel` case.
