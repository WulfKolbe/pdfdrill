634 — the claim ledger: every module records the anchors it consumed
====================================================================

`pdfdrill model --ledger <pdf>` prints how many `mathpix_lines` anchors were
claimed zero times and how many more than once. THIS IS THE MEASUREMENT, NOT
THE FIX. Object counts, props and projections are byte-identical with the
ledger present; the only change to any artefact is one new key under
`meta` in the model file.

The pipeline is ADDITIVE, so nothing in it could say that the Contents region
was claimed by nobody or that a line was claimed twice. Both were already
true and both were invisible. They are now two integers that add up.

--------------------------------------------------------------------------
THE BLOCK / INLINE RULE, SAID OUT LOUD (the brief asks for it here)
--------------------------------------------------------------------------
A CLAIM is a `surface` Realization on `mathpix_lines`.

  BLOCK      it carries NO sub-anchor offset/length: the object consumed the
             whole line. THE USER'S TWO COUNTS ARE ABOUT BLOCK CLAIMS ALONE.
  INLINE     it carries offset AND length: the object lives INSIDE the line.
             A Formula inside a paragraph line is NESTING, not a second
             consumption — counting it would make every prose line carrying
             maths look mixed up (1426 such realizations on penev_A, 755 on
             Steerable). Recorded, reported separately, never counted.
  CONTAINER  the object's type is in `CONTAINER_TYPES` — `Page` alone.
             `PageProcessor` gives every Page a surface realization spanning
             EVERY line of its page, by construction rather than by claim.
             646 measured what counting them does: all 3178 penev_A anchors
             become doubly claimed and the measure says nothing. Recorded and
             reported (3178 / 1437 container claims below), never counted.
             The exclusion is printed in the command's own output.

The rule is `docops.conserve`'s rule, adopted deliberately and not
reinvented: the two instruments have to be comparable ANCHOR BY ANCHOR, and a
private definition here would make a divergence look like a finding.

--------------------------------------------------------------------------
WHY IT IS RECORDED AND NOT DERIVED — the measurement that decided it
--------------------------------------------------------------------------
646's `anchor_claims` already derives claims from the finished Document. It
can say a line is claimed twice and name the two TYPES. It cannot name the
two MODULES, because the finished document does not carry that:

    penev_A, model on disk: 1448 objects, of which
        1271 carry NO `added_by` prop at all   (the base build's modules)
         131 `bibliography`,  45 `footnote_cleanup`,  1 `citation`

"A Footnote and a Paragraph both claim this line" is a symptom.
"footnote_cleanup and paragraph both claim this line" is the address of the
code that has to change. That is the whole reason 634 is a second instrument
and not a second report.

WHAT WAS BUILT — ONE HOOK, NOT FIFTY-FOUR
--------------------------------------------------------------------------
  src/docmodel/core.py         `DocObject.add_realization` is THE one place a
      realization is attached to an object. All 54 attach sites in the
      codebase go through it (checked: `realizations=` appears as a
      constructor argument exactly once, in `Document.from_dict`, which is a
      reload and not a claim). So the claim is recorded there, in three
      lines, guarded by a module-level bool that is False in a read-only
      process. Nothing in `src/docmodel/modules/` had to be edited, and a
      module added tomorrow is in the ledger the day it lands.

  src/docmodel/ledger.py  NEW. `note` (the hook), `realization_key`,
      `recording`/`start_recording`/`reset`, `materialize`, `persistable`,
      `for_save`, `format_ledger`. The recording SITE is read off the calling
      frame (`sys._getframe`), which is why no call site needed a parameter.

  src/docmodel/main.py    switches recording on for the rest of the process
      (not just the module loop — `cmd_model` runs `heading_cleanup` after
      the build returns and saves the result), and writes the ledger into the
      file it serialises itself.

  src/pdfdrill/cli.py     switches recording on for every command. A drill is
      22 separate processes; `lists`, `annotate`, `bibliography` and `clean`
      each add objects to a model `model` built, and their claims belong in
      the same ledger.

  src/pdfdrill/model_io.py `save_model` writes `meta["ledger"]` into the
      SERIALISED dict, never into the caller's Document — the same shape
      `written` already uses, and for the same reason. Best-effort by
      contract: a measurement must never be able to fail a save, and a
      failure keeps whatever ledger was there rather than dropping it.

  src/pdfdrill/commands.py `model_ledger` — READ-ONLY. It never rebuilds: a
      stale or absent model is REFUSED, naming the exact `pdfdrill model
      <pdf>` that fixes it. `cli._do_model` routes `--ledger` BEFORE
      `cmd_model`, so the `@_writes` document lock is never taken and no code
      path from the flag to a build exists. `preflight.READ_ONLY_FORMS` lets
      the read through the attestation gate while the bare `model` build
      stays gated. It does open the document's sidecar (a `pdfinfo` probe),
      which every command does. See THE SPEND below for why the refusal is
      there instead of a convenient auto-rebuild.

  manifest  `.claude/skills/pdfdrill/commands.yaml`, `--ledger` on `model`;
      `python3 tools/skillsync.py all .` run; manifest <-> HANDLERS in sync
      (148/148). Not a new verb and not a tool: a flag on the layer that owns
      the model.

WHAT PERSISTS, AND WHY ONLY THAT
  `meta["ledger"]` carries the ATTRIBUTION map (object id -> realization key
  -> recording site) plus the summary. The 0-claim and >1-claim LISTINGS are
  not persisted: they are recomputed from the live document on every read, so
  a stored ledger can never describe a document the model no longer holds.
  The attribution is the one thing that cannot be recomputed — it is the
  memory of who attached what, in a process that has since exited. That is
  what makes the ledger read the same for a fresh build and for a full drill:
  `save_model` merges what THIS process recorded with what the previous one
  persisted, and where an object carries `added_by`, that wins.

  Cost on penev_A: 180,908 bytes of ledger in an 11.4 MB model (+2.0% on the
  file; 1444 objects attributed, 2043 realizations).

  A model built before this code exists is entirely `unattributed`, and the
  report SAYS so rather than guessing a module from the type.

THE CONSERVE CROSS-CHECK — ANCHOR BY ANCHOR, NOT COUNT BY COUNT
--------------------------------------------------------------------------
Two instruments can agree on "243" and disagree about WHICH 243, and that
agreement would be worthless. The check is set equality on the anchor ids.

                                              penev_A     Steerable
  ledger claimed 0        vs conserve unclaimed  243=243     132=132
  ledger claimed >1  vs conserve doubly_claimed    42= 42     136=136
  ledger block claims     vs conserve claims     2977=2977   1441=1441
  ledger inline      vs conserve inline_skipped  1426=1426    755= 755
  SAME ANCHORS (0-claim set)                        YES         YES
  SAME ANCHORS (>1-claim set)                       YES         YES
  only in ledger / only in conserve                0 / 0       0 / 0

  NOTHING TO RECONCILE. The two agree exactly, on both documents, on every
  anchor, and they were built to be able to disagree — the ledger walks the
  objects in its own loop, groups by MODULE rather than by type, and counts
  container spans that `conserve` skips before it reaches the inline test.
  Both numbers also match out/636.txt's control (penev_A 243 / 42 with
  Footnote+Paragraph 35; Steerable 132 / 136), so the rebuild is confirmed
  like for like and no number moved.

  ONE DEVIATION, INHERITED AND STATED: `CONTAINER_TYPES = ("Page",)`. Read
  literally, the brief's claim rule makes a Page a claimant and every anchor
  doubly claimed. 646 ruled on that and this task adopts the ruling rather
  than making a second one; the container claims are REPORTED (3178 / 1437)
  so nothing is hidden by it, and a test pins that a Page claims nothing.

THE SPEND — ONE 8-PAGE MATHPIX EXTRACTION, BOUGHT BY ACCIDENT (fix round 1)
--------------------------------------------------------------------------
WHAT WAS BOUGHT. One MathPix extraction of `evidence-equation.pdf`, 8 pages,
in `~/pdfdrill-library/penev_A/`. Nobody asked for it. It is the only spend
this task caused, and the round-0 report's "no extraction re-purchased" was
true of the two rebuilds and false of the task; it is corrected above.

HOW. The evidence capture ran

    pdfdrill model --ledger $DOC/*.pdf > $DOC/out/634/model-ledger.txt
    pdfdrill conserve        $DOC/*.pdf > $DOC/out/634/conserve.txt

and EVERY PUBLISHED DOCUMENT FOLDER HOLDS SIX PDFs — the document plus
`evidence-formula.pdf`, `evidence-equation.pdf`, `evidence-image.pdf`,
`evidence-table.pdf`, `report.pdf` and `residuals.pdf`, written by earlier
tasks. The glob sorted `evidence-equation.pdf` first. Both captures were
therefore of the WRONG DOCUMENT — and because that document had no model,
round 0's `--ledger` (which rebuilt "only if stale") chained
`cmd_model` -> `cmd_mathpix` and paid for the extraction. Three failures in
one line, and each has its own fix:

  THE GLOB. `out/634/capture.py` derives the PDF from the FOLDER NAME, never
    globs, refuses the six by name, refuses more than one argument, and
    checks each capture's first line before writing it. Both captures were
    retaken; their first lines now read
      `CLAIM LEDGER — penev_A  (stream mathpix_lines)`
      `conserve penev_A: NOT CONSERVED`

  THE REBUILD. `model --ledger` is READ-ONLY and REFUSES a stale or absent
    model, naming `pdfdrill model <pdf>`. A command whose purpose is to
    report on what exists must not be able to create it, and the spend
    decision stays with the caller. `cli._do_model` routes the flag before
    `cmd_model`, so no path from it to a build survives — pinned as SOURCE
    (`test_no_path_from_the_ledger_flag_to_a_build_or_a_purchase`), because
    the failure was a call chain and no fixture reproduces a purchase.

  THE CERTIFICATION. INSPECT.txt listed both wrong files as penev_A's own.
    408's rule — a path in INSPECT.txt is a promise — checked existence and
    non-emptiness, and both files were perfectly real. `taskout.inspect_list`
    now takes an `expect` and holds the file's FIRST LINE to NAMING the
    document. "Naming", not "containing": the bad capture's first line was
      `Uploading /home/wkolbe/pdfdrill-library/penev_A/evidence-equation.pdf...`
    which CONTAINS "penev_A", inside the folder path — a substring test
    passes it, and the check would have been written and still missed the
    defect it exists for. A token holding a path separator is not a name.

WHAT WAS DONE WITH THE ARTEFACTS. Kept, not deleted — they were paid for —
and moved out of the document folder into
`~/pdfdrill-library/penev_A/out/634/accidental/`, where `status` and every
glob will not find them and treat them as penev_A's:
  evidence-equation.lines.json, .md, .tex.zip, .pdf.drill.json, .pdf.drill/
  (the last holding the model built from that purchase).

WHAT IS OPEN
--------------------------------------------------------------------------
  634-a is the first thing to fix and it is small: give the Abstract the
    extent it read. 40 + 12 lines stop being "covered by no object" on the
    two documents in hand, and 646-h's pure-loss class shrinks to whatever
    is left after it.
  634-c wants a ruling, not a patch: should a stub Reference carry a
    `mathpix_lines` surface realization at all? penev_A's and Steerable's
    `bibliography` disagree with each other today.
  The recorder attributes a realization by (role, span, offset, length) on
    its object. A pass that MUTATES `props["offset"]` after attaching would
    move the key and lose the attribution — it would read `unattributed`,
    never wrong. No pass does that today; it is not asserted anywhere.
  `MAX_RECORDED_OBJECTS` is 200,000 and has never fired. It is a rule with a
    counter (`overflow`, printed when set), not a measured population.
  The ledger is not in `docs/layers/`. It is a flag on `model`, declared in
    the manifest; if it grows a layer of its own it needs a doc.
  `preflight.READ_ONLY_FORMS` holds one entry and it is a PROMISE ABOUT A
    CODE PATH, not about a flag name: `model_ledger` must stay unable to
    write or spend. The source-level test asserts that today; a second entry
    added without the same test would reopen the gate quietly.
  Every other task's evidence capture in this library was taken the same way
    round 0's was — by hand, often with a glob. `inspect_list` can now check
    them, and none of them has been rechecked.
