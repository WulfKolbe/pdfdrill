WHAT WOULD ACTUALLY CLEAR IT
------------------------------------------------------------------------------
A consumer for `latex_refined`: a projector that prefers a recorded, verified
refinement over the original where one exists, and says on the page which rows
it used. That is a layer, with the choice visible rather than silent, and it is
what turns this loop's output from evidence into effect. Twenty-seven
acceptances from out/216 are waiting in the same state — accepted, measured,
recorded, and read by nothing.

It is not built here, and it should not be smuggled into a task whose own
wording forbids overwriting the original. It is the next task, not this one.

TWO THINGS THIS RE-RUN FIXED
------------------------------------------------------------------------------
**A re-request inherited the previous outcome.** Re-ingesting a proposal for a
row that already had one left `recorded: True` in place, so the record stage
reported "nothing accepted to record" about a proposal it had just accepted —
it had recorded the older version. Every field describing a previous outcome
(recorded, verified_by, evidence, reason, the ink numbers, the per-stage
errors) is now cleared when a request re-proposes a row. Stale outcome fields
make a fresh run look like it did something it did not, which is the failure
class this sequence keeps finding.

**record_one appended instead of replacing.** Recording twice left two
provenance="change" realizations on one object, and a reader finding both has
no way to tell which one `latex_refined` came from. It now replaces any
existing refined realization for that object. Verified: one record on disk
after two runs.
