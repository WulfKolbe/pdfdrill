666 - report.pdf vs residuals.pdf: is the measured crop the displayed crop?
==============================================================================

DOCUMENT CHOSEN, AND WHY
------------------------------------------------------------------------------
   Introduction to Linear and Matrix Algebra (Nathaniel Johnston) (Z-Library)

   PDF derived from the folder name, never a *.pdf glob (per this task's
   instructions and the incident that motivates them, HANDOVER-RULES rule
   about the six-PDF-per-folder trap): the folder's own
   `.pdf` is the source document; `report.pdf` and `residuals.pdf` sit
   beside it, both present.

   Chosen over the other 20 library documents that carry BOTH report.pdf
   and residuals.pdf because it has the most embedded images in each:
   35 in report.pdf, 31 in residuals.pdf (next closest: "Lie Groups,
   Physics and Geometry" at 15/25; "Numerical Linear Algebra and Matrix
   Factorizations" at 6/23). More images means more rows to test the claim
   on rather than an anecdote.

METHOD - HOW ROW <-> IMAGE CORRESPONDENCE WAS ESTABLISHED
------------------------------------------------------------------------------
   `pdfimages -list <pdf>` gives, per embedded image: page, a running
   index ("num"), pixel width/height, and encoding. `enc jpeg` is a real
   photographic scan crop; `enc image` (4 images in residuals.pdf, 0 in
   report.pdf) is a rasterised standalone-LaTeX render that lands in the
   REPORT'S "Rendered" column, not the "Scan image" column, and was
   excluded from the crop comparison on that basis (verified per-image via
   its dimensions and page against the standalone-math code path, not
   assumed).

   `pdfimages -j <pdf> prefix` extracts each jpeg's ORIGINAL bytes
   unchanged (no re-encoding), which is what "as embedded" requires: this
   is the exact stream the PDF carries, not a decode-and-recompress copy
   and not the on-disk crop file (which may have been rewritten since
   either PDF was built - not consulted at all in this task).

   Row identifiers were read from the rendered PDF text (pdfplumber
   word extraction of the Identifier column, x0 < 200pt), NOT from the
   .tex source - the source-regex trap named in HANDOVER-RULES ("a naive
   `\ident{[^}]*}` defeated by `\allowbreak{}`) does not apply to the
   rendered page, but a related trap does: for some rows pdfplumber
   tokenises the identifier's individual GLYPHS as separate one-character
   words (irregular kerning), and a plain per-word "EQ\d+" regex silently
   dropped EQ0528(was) in report.pdf and 4 identifiers in residuals.pdf.
   Fixed by clustering all words on a page within 2pt of vertical position
   into one line, concatenating, THEN matching "EQ(\d+)(\(was\)|\(now\))?"
   - verified by cross-checking the resulting identifier count against the
   independently-known image count (see below).

   Correspondence itself: within one page, both the Identifier column
   (x approx 60pt) and the Scan-image column (x approx 805pt) render
   top-to-bottom in LaTeX source (row) order. For every page in both PDFs,
   the count of non-"(was)/(now)" identifiers was checked equal to that
   page's count of jpeg images before zipping them in top-position order;
   a page where they were NOT equal would have been reported as a
   correspondence failure, not guessed past - none occurred once the
   identifier-extraction fix above was in place (checked by assertion in
   the script; it does not silently proceed on a mismatch).

   Sanity check beyond the count match: for two of the eleven rows
   (EQ0114, EQ0947) the LaTeX-source-column text was pulled from both
   PDFs independently and is byte-identical, confirming the same
   identifier in both PDFs names the same underlying row, not a
   coincidence of matching page position.

HOW THEY DIFFER
------------------------------------------------------------------------------
   Every one of the 11 differing pairs has residuals.pdf's crop SMALLER
   than report.pdf's crop at the SAME aspect ratio - a uniform downsample,
   not a different region or a different aspect:

     report_width / residuals_width   ranges 1.1769 - 1.1782 across the 11
     report_height / residuals_height ranges 1.1765 - 1.1839 across the 11

   Both ratios cluster inside a half-percent band around 1.177-1.178 (the
   width ratio is tighter than the height ratio, consistent with
   integer-pixel rounding of a single linear scale factor rather than
   independent width/height distortion). This is exactly the signature
   the task asked to distinguish for: SAME aspect ratio, SMALLER size ->
   the per-kind re-encoding rung from 655's size-budget ladder, not a
   wrong-region or wrong-image defect. No pair showed a different aspect
   ratio or an unrelated image. This is a measurement, not a diagnosis of
   WHY the rungs differ between the two builds - that is out of scope here.

   residuals.pdf's own printed header states this explicitly:
   "equations measured 2026-09-05T12:23:12Z against the model of

   longer exists under that name. Stated as measured fact (the header
   text plus the three build-phase JSON sidecars), not a diagnosis of
   consequence.

   Per-row, report.ink.json's 1,460 rows (e.g. the EQ0528 row) carry:
