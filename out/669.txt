669 — publish the refined reading where the raw is worse
==========================================================

"publish the refined reading where the raw is worse." Branch
eqblobs-and-gzip-tex, base commit 503beea9.

THE DEFECT, CONFIRMED AS STATED
--------------------------------
docs/layers/PROPS.md's `latex_refined` row: "a VERIFIED refinement in a
twin prop; `latex` is never overwritten (232). Reading `latex` alone
ignores every accepted repair (233)." The published surface
(docs/HANDOVER.md:25-42: evidence-equation.pdf, evidence-formula.pdf,
residuals.pdf, built from `src/pdfdrill/reports/`) did exactly that:
`reports/from_document.py::build_rows()` read `p.get("latex")` and
nothing else. Confirmed by reading the code before touching it, not
assumed from the brief.

THE MECHANISM, READ NOT REBUILT
---------------------------------
`refine.py` already carries everything this needed:
  - `REFINED_FIELD` — the constant (`"latex_refined"`), used throughout,
    never a string literal.
  - `refinement_state(obj)` — five states (NONE / VERIFIED / CONTRADICTED
    / UNVERIFIED / ORPHANED) with the reason; used, not re-implemented.
  - `chosen_latex(obj)` — the existing read-time choice (233): prefers the
    refined value whenever `refinement_state` says VERIFIED, else the raw,
    with an evidence dict describing which. Reused VERBATIM.
`report_tex.py` (the RETIRED reading path — `reporttex` is superseded for
reading per HANDOVER.md, kept only as the ink chain's measure build) also
already carries the surrounding apparatus for saying so on a page:
`refined_flag(info)` (an identifier-column mark, out/064's own precedent
for keeping the mark OFF the LaTeX-source/Rendered/Scan columns — HANDOVER-
RULES rule 16's free control) and `refined_note(refined_map)` (a top-of-
report summary). Both are REUSED as-is by the published path; neither was
edited to change behaviour. What report_tex.py's OWN `rows_for`/
`refined_map`/`--prefer-refined` do NOT have is a render-safety check —
they substitute the refined value unconditionally whenever
`title in refined_map`, which is the naive rule this task explicitly
rejects (see the DECISION TABLE below). That retired-path gap was left
alone, per the brief's own warning that a sibling task (661) fixed the
retired path by mistake once already and measured a result nobody reads.
The one addition to a shared, retired-path FILE is a legend line
(`LEGEND_REFINED`, appended to `report_tex.legend()`) explaining the mark
— infrastructure both paths already share (LEGEND_CONF/LEGEND_SRC/
LEGEND_INK), not a behaviour change to either.

THE SEAM ACTUALLY CHANGED: `src/pdfdrill/reports/from_document.py`
---------------------------------------------------------------------
`_chosen_reading(obj)` (new, ~30 lines): calls `refine.chosen_latex(obj)`,
then adds the ONE check that function does not make — whether the
VERIFIED value it prefers survives `report_tex.display_safe`. `ev` (the
evidence dict) is truthy and lacks a `"refinement_state"` key exactly when
`chosen_latex` chose VERIFIED (the non-VERIFIED branch always sets that
key); that is the discriminator used, not a second reimplementation of
`refinement_state`. `build_rows()` calls this for every Equation AND
Formula object (refine.MATH_TYPES is both, and this is not merely a
type-signature nicety: today's 31-object population is 30 Equation and 1
Formula — 0707.4470_FO0175, obj_0c9487434929, VERIFIED, both readings
render — so the Formula branch is exercised in the LIVE corpus, not only
by a unit test) and stamps the row's new `refined_info` field with the
evidence dict, or None.

One trap, avoided the way it needed to be avoided: the Formula loop keeps
the HOST-LINE lookup keyed on the RAW `p.get("latex")` (renamed `raw_lx`),
never on the possibly-refined `.latex` the row carries — the text a
`first_occurrences` span was recorded against in `.lines.json` never
changes, so re-keying it against a refined reading would silently break
every inline formula's host-line join.

A `"refined"` map was tried as a FIFTH key on `build_rows()`'s return dict
and reverted in the same session: `ensure_crops`/`crops.records` both do
`for kind, lst in rows.items(): ... for r in lst: dataclasses.replace(r,
...)`, and a fifth value shaped as `{identifier: dict}` handed `dataclasses
.replace` a dict key STRING instead of a row object. `refined_rows_map
(rows_by_kind)` is a separate function that reads `.refined_info` back off
the rows `build_rows` already stamped, so the return shape stays exactly
what every other consumer already assumes.

CORRECTION (fix round 1): this function was named `refined_map` through
fix round 0, colliding in NAME (never in behaviour -- nothing called both)
with `report_tex.refined_map` above, an unrelated, older function on the
RETIRED reading path (a tiddler-array reader, not a row reader; a review
minor finding). Renamed to `refined_rows_map` here, in `evidence.py`'s
import, and in its test; `report_tex.refined_map` (128) was left alone --
it has its own tests and its own internal caller, and renaming it would
be touching the retired path this task was told not to rebuild.

THE COLUMN QUESTION — DECIDED DIFFERENTLY FROM 661, AND WHY
----------------------------------------------------------------
out/661.txt's ruling: the "LaTeX source" column keeps `latex` UNCHANGED
(MathPix's own reading) while "Rendered" shows the SAME reading with
`to_inline_env()`'s environment-name map applied — because that map only
ever changes an environment's NAME, so the two columns describe the same
content and disagreeing is safe to leave unexplained beyond a legend line.

That precedent does not transfer here. A refinement can change the
CONTENT outright — 28 of 31 do. Showing MathPix's raw reading in the
source column beside a Rendered cell drawn from unrelated content would
not read as "a legitimate divergence, explained in the legend" the way
661's population does; it would read as a bug, because the two cells
would describe two different equations with nothing on the page saying
why. So the decision is the OPPOSITE of 661's for this case: `report_tex.
row()`'s own pre-661 mechanism (233, `refined_flag`/`refined_note`) already
substitutes the SAME chosen value into both the source and rendered
content and marks the identifier instead of leaving the columns to
disagree silently — that mechanism was reused as the model, not 661's.
