WHAT WAS BUILT
-----------------------------------------------------------------------------
`src/pdfdrill/reports/marks.py` (new) — a module that reads one
document's `marks.json`, runs the two checks against OUR OWN Formula
rows, and draws. Kept out of `from_document.py` (that package's rule:
one module is model-aware, and this one reads only `FormulaRow` objects
and files on disk, never a `docmodel.core.Document`).

  `check_row(row, mark_row)` — None when both checks pass, else a stable
  refusal-reason string:
    * `region`/`host_page` must equal OUR OWN host line
      (`row.host_line.region`/`.page`) for that row.
    * `math` must equal the row's current reading taken through
      `report_tex.display_safe` — NOT raw `latex`. Traced this by
      reading inkdrill's own `tools/formulafind.py:rows()`: `math` is
      parsed back OUT of the `\FitMath{$\displaystyle ...$}` group
      `reports/tex.py:_rendered()` writes, which is `display_safe(latex)`,
      not `latex` itself. Comparing against raw `latex` would have
      refused every row whose display form differs from its source
      (trailing punctuation is outside the group, so that part is
      already unaffected either way, but `to_inline_env`/`renderable`'s
      own mapping is not the identity function in general).

  `apply(rows, marks_path, doc_dir)` — off (a true no-op, same dict
  object returned) when `marks_path` is falsy; otherwise walks
  `rows["formula"]` only, joins by `identifier` against the file's own
  `id`, and for every `mark: true` row that passes both checks draws an
  outline rectangle onto a COPY of the row's crop
  (`reports.marks.MARKS_DIR = "report-crops-marks"`, a THIRD directory,
  never `report-crops/` or `report-crops-b/`) and repoints that row's
  `.crop` at it. Every other kind, and every formula row not drawn
  (absent from the file, `mark: false`, refused, or undrawable), keeps
  the exact row object `ensure_crops` already gave it.

  `_draw(src, dst, rect_frac)` draws from `rect_frac` — the SAME
  fraction-of-region rectangle regardless of whether `src` is the
  full-size `report-crops/` file or an already-scaled `report-crops-b/`
  copy — so one code path handles both sizes rather than a scale
  branch. Outline only (never filled), line width proportional to the
  image's own short side, floored at 2px so it cannot vanish at 655's
  0.42 floor.

Wired into `commands.cmd_evidence` (new `marks_path` parameter, CLI
`--marks PATH`, `.claude/skills/pdfdrill/commands.yaml` +
`tools/skillsync.py all .`): called strictly AFTER `ensure_crops` (the
655 budget/rung choice must see only the unmarked bytes) and strictly
before any kind is rendered. A new `commands._marks_line(counts)`
appends one line to the command's own output, per brief item 4: rows,
marked in the file, checked, drawn, refused by each reason.

WHAT crop_gate NOW COMPARES, AND WHETHER IT IS STILL THE RIGHT QUESTION.
Read `reports/gate.py` before answering this: `crop_gate` walks
`report.ink.json`'s rows, which are ink-measured EQUATION rows
(`_EQ...`, `report.pdf`'s population) — a population entirely DISJOINT
from what this task ever touches (Formula rows, `_FO...`, the crops
`evidence-formula.pdf` shows). So in this task, `crop_gate`'s comparison
target is UNCHANGED, byte for byte and row for row — confirmed on real
data below, not just argued from the code. Whether it is still the right
question: yes, and for a reason stronger than "no overlap today" — a
marked Formula crop is a PRESENTATION derivative, recomputed FRESH every
build from the untouched `report-crops/`/`report-crops-b/` source, never
cached across builds the way a stale `crop_sha256` would need catching.
Its own correctness (does the rectangle belong on THIS line, with THIS
reading) is enforced at draw time, every time, by the two checks above —
a persisted hash a later build could drift from would be solving a
problem this design does not have. If a future task extended
`crop_sha256`/`crop_gate` to Formula rows too, this module would still
not need to change: it never writes into `report-crops/`, so that
gate's source-of-truth read stays correct regardless.

   (documented in `reports/budget.py`'s own module docstring as of FIX

   somewhat further over once marked; `reports.budget.check_artifact`
   reports the true final number honestly either way.

FINDING 1 (blocking) — `apply()` drew on blank crops
-------------------------------------------------------------------------
`marks.py`'s `apply()` refused a row only when `row.crop is None`. A
crop can EXIST on disk, be a perfectly valid JPEG, and still carry NO
visible content — verified on real, currently-published production data
the review named: `1510.06699_FO0765`/`_FO0911` and `kohlhase-omdoc_
FO0045`, all `stddev == 0.0` (pure white) at every size on disk, all
already shown as `---` in today's `evidence-formula.tex` because the
content never rendered upstream. `_draw()` happily draws on these (PIL
opens a blank JPEG fine); the result is a red rectangle on nothing — an
evidence claim the crop does not support, worse than the honest `---`
it would replace. Round 0's own dry-run script had, by coincidence, been
resolving crops through `crop_file()`'s 500-byte floor, which happened
to catch SOME of these rows (miscounted as "no crop to draw on") but not
others, and would not have caught any of them in REAL production, where
`ensure_crops`/`_apply_budget` repoint `row.crop` at a scaled copy
unconditionally, with no byte-size re-check.

FIX: `reports.marks._is_blank(path)` — opens the crop, converts to
greyscale, and refuses when `ImageStat.Stat(im).stddev[0] < 1.0` (a real
blank crop measures exactly 0.0; the small positive floor tolerates
ordinary JPEG re-encode noise on an otherwise-flat source without
letting a genuinely blank crop through). `apply()` now calls it right
before drawing and refuses under its own reason, "crop has no visible
content (blank)", counted like every other refusal.

VERIFIED on the exact rows the review named, using the module's real
`apply()`, not a synthetic case: fed `1510.06699`'s real rows (crop
resolved the way `ensure_crops` actually resolves it — full-size

("crop has no visible content (blank)"), NEITHER produces a file under

FINDING 2 (blocking) — `_draw()` hardcoded JPEG quality 92
-------------------------------------------------------------------------
`_draw()` always saved at quality 92, regardless of the `(scale,
quality)` rung 655's budget chose for that kind. Measured on REAL
gilmore crops at the published floor (0.42/q70): a 30-row sample grew
from 86,805 to 163,231 bytes (review's own number, independently
reproduced this round). Re-encoding an already-scaled, already-quality-
70 source at quality 92 does not recover detail — it just spends more
bits on the same lossy pixels plus the rectangle's own high-frequency
edges. Gilmore is already reported OVER BUDGET at 20.45 MB (out/655);
this made it worse by construction, for every document at every rung
below 1.0, independent of anything `choose_rung`/`check_artifact`
already do.

FIX: `apply()` now takes a `rung` parameter — the SAME `(scale, quality)`
(or `None`) `ensure_crops` already computed for the "formula" kind
(`rungs.get("formula")` in `commands.cmd_evidence`, the identical value
`_evidence_line`'s own OVER-BUDGET message already reads) — and threads
`rung[1]` into `_draw`'s `quality` parameter. `rung is None` (this kind
was never scaled) draws at `DEFAULT_QUALITY` (92), which matches
`report_tex.render_crops`'s OWN save quality for a freshly-rendered,
unscaled crop — so an unscaled document's marked bytes cost only the
rectangle's own ink, exactly as claimed in round 0, and only a SCALED
kind's behaviour changes.

RE-MEASURED on gilmore, ALL 577 real marked rows (not a 30-row sample —
the exact, whole population), both before and after this fix, through
the real `apply()`:

    quality 92 (the bug, unfixed):  1,676,529 -> 3,177,365 bytes
                                     (+1,500,836 B, +1.43 MB, x1.895)
    quality 70 (fixed — gilmore's
    real published floor rung):     1,676,529 -> 2,101,979 bytes
                                     (+425,450 B, +0.41 MB, x1.254)

The fix does not make marking free — adding a rectangle's own ink to an
already-compressed JPEG always costs some bytes, and re-decoding +
re-encoding a lossy source a second time is not lossless even at the
same quality — but it cuts the real growth by ~3.5x (from +1.43 MB to
+0.41 MB on gilmore) by no longer re-encoding at a quality the rung
never chose. Round 0's CONCERNS claim ("does not grow the published PDF
beyond what a rectangle overlay costs") was wrong before this fix and is
now approximately true, not exactly — corrected in the CONCERNS section
above rather than repeated.
