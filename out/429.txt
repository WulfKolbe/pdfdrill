So MathPix measures every cell and the model discarded it at build. The dash
was honest about the container and threw away 1,924 measurements.

THE DECISION: THE MINIMUM OVER CELLS

Not a preference — banding the same 42 tables both ways:

              red <0.5   amber 0.5-0.9   green >=0.9
    MIN            1             5            36
    MEAN           0             1            41

The mean hides five of the six tables that contain a bad cell. The 14-cell
table whose worst cell reads 0.091 averages to 0.790; a 119-cell table with
one bad cell would average to 1.000 and show green. A reader scanning this
column is hunting for the defect, so the aggregate has to be the one that
cannot average it away.

It is also MathPix's own convention for rolling child confidence up to a
table parent, so this is their number rather than one invented here.

A NOTE ON HOW LONG THIS TOOK

I concluded twice that `TableProcessor.create_object` never ran — once from a
monkey-patched probe, once from a debug print I could not find in the output.
Both times the module was running correctly and I was reading the run's tail
while the module reports at procOrder 4, near the start. The code was right
from the first attempt; the reading of its output was not, and it cost more
steps than the change did.

EXISTING MODELS DO NOT HAVE THE PROP. It is set at model build, so a document
gains it on the next `pdfdrill model`. 417's rebuild does not include that —
it rebuilds reports, not models — so the tables column will show dashes on
any document whose model predates this change, which is all of them but
2608.09819 today.
