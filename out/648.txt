648 — what `bibliography` may do after `bibsource`
====================================================

BEFORE ANYTHING ELSE: the fixture COULD reproduce "22/81 linked then 0
linked", but not in the shape the user saw. It surfaces two DISTINCT defects
depending on whether bibsource left any FILLED (non-stub) Reference behind:

  A. bibsource fills SOME gold refs (the fixture, built per the brief).
     `cmd_bibliography`'s bare early-return gate correctly fires (a filled
     Reference exists) and detection does NOT run twice — Citation ids,
     count, `added_by` all unchanged. But the MESSAGE it returns is wrong: it
     is the generic `_format_bibliography(sc)`, reading `bibliography_*`
     sidecar evidence that was never set on this document (bibliography's
     own heuristic parse never got a turn), so it prints "Parsed 0
     bibliography entries (0 with a year)" with no mention that the document
     already holds 80 citations, 22 of them linked. The objects are right;
     the count is simply wrong.

  B. bibsource fills NO reference at all — measured LIVE on penev_A, which
     is on this machine and needed no fixture. `existing` (non-stub
     References) is permanently empty on this document (its heuristic
     References-section parse finds 0 entries, same as every corpus
     document with no `.bbl`/`.bib` and no printed reference list MathPix
     segments), so the early-return gate NEVER fires. A bare `bibliography`
     call always re-runs `detect_numeric_citations`/`detect_author_year_
     citations` unconditionally, and neither checked whether a Citation
     already covered the span it just found. Two bare calls in a row: 81 ->
     161 -> 241 Citations. This is 010's own OPEN item ("cmd_bibliography's
     ... early-return gate ... would redetect and duplicate WITHOUT
     --force, the same way --force did before this round") — reached, live,
     while measuring this task. Restored from backup; never committed.
     Detection really does run twice here.

Both halves of the ruling's bifurcation ("if the count is simply wrong ...;
if detection really runs twice ...") turned out true, on two different
corpus shapes. Both are fixed.

THE DECISION (rule 10)
  Ship BOTH fixes the measurement demanded, and reject one alternative:

  1. `_format_bibliography` (src/pdfdrill/commands.py) now takes `doc` and
     reads `bibliography.citation_link_breakdown(doc)` — "N citations, K
     linked to filled references, S to stubs" — computed fresh from the
     SAVED model every time, at both call sites (the early-return AND the
     normal end-of-run return). It no longer trusts `bibliography_cites`/
     `bibliography_numeric_citations`/`bibliography_authoryear_citations`
     sidecar evidence for the citation-linkage half of the message (only
     `bibliography_entries`/`bibliography_with_year` — what THIS command's
     own References-section parse found — still come from evidence, since
     `citation_link_breakdown` cannot recover that after the fact).
  2. `detect_numeric_citations`/`detect_author_year_citations`
     (src/pdfdrill/bibliography.py) now check a new
     `_existing_citation_spans(doc)` — identity = (stream, anchor, offset,
     length, citekey), the brief's own definition — before minting a
     Citation, and skip a group that identity already covers. A repeat bare
     call adds nothing new. `detect_author_year_in_objects` (bibsource's
     fallback) was NOT touched: its one call site always drops every
     `added_by == "bibliography"` Citation immediately before calling it, so
     it was already effectively idempotent by deletion-then-recreate.
  3. `add_reference_objects` (src/pdfdrill/bibliography.py) now skips a
     heuristic entry whose citekey already names a FILLED (non-stub)
     Reference — gold (or an earlier fill) wins; the heuristic References-
     SECTION parse never overwrites or duplicates it. Reachable via
     `cmd_bibliography --force`, whose cleanup deliberately KEEPS a
     gold-filled Reference (010 fix round 4) and then re-runs this parse
     unconditionally; the heuristic's own citekey generator (surname+year)
     can independently produce the exact string a gold citekey already has.
     Confirmed with a fixture where the printed References section names
     the same author+year an existing gold Reference covers
     (`test_bibliography_force_never_duplicates_a_gold_reference_from_the_
     heuristic_section`): before this fix, two Reference objects for
     "Asai2023"; after, one, untouched.

  REJECTED: changing the `if existing and not force: return` gate itself
  from "any filled Reference exists" to a PROVENANCE signal (e.g. the
  `BIBLIOGRAPHY_BUILT` sidecar fact, or "a Reference with `ref_source ==
  'text'` exists") so that `parse_bibliography`/`add_reference_objects`
  gets a turn to fill in citekeys bibsource's gold subset didn't cover, as
  the ruling's clause 1 ("MAY parse ... only for citekeys that have NO
  filled Reference") invites. Rejected for now: item 3 above already makes
  that parse SAFE whenever it does run (gold never gets duplicated), and
  the fixture's own `add_reference_objects` protection plus item 2's
  idempotent detection make a gate change low-risk in THIS repo's own
  detector family — but `detect_author_year_in_objects` (bibsource's
  detector, case-FOLDED citekeys, e.g. "smith2001") and
  `detect_author_year_citations` (bibliography's detector, case-PRESERVED,
  e.g. "Smith2001") mint DIFFERENT citekey strings for the textually
  IDENTICAL citation. The brief's own idempotency identity includes the
  citekey, so a same-span, different-case re-detection would NOT be caught
  by item 2's guard and would still duplicate. Opening the gate was not
  measured safe against this cross-detector mismatch, and "MAY" leaves it
  optional. What would change my mind: a citekey-normalisation fix (fold
  both detectors' citekey generation to one canonical form) landing first,
  or a real corpus document where bibsource's gold subset is a strict,
  incomplete subset of a printed References section AND the missing
  entries are needed (not observed here — penev_A and Steerable both carry
  no gold at all, so bibsource never gets a chance to leave a PARTIAL gold
  set for `--force` scoping doesn't even apply to the bare gate).

FIX ROUND 1 — two findings from review, both ruled real
  1. IMPORTANT. The gold-collision `continue` (item 3 above) skipped the
     `role="bibliography"` section-anchor realization too, so
     `bibliography_section_anchors` no longer excluded the printed line and
     a `--force` re-detect read the bibliography's own line as an in-text
     Citation. REPRODUCED (test_gold_collision_still_excludes_the_printed_
     line_from_redetection, confirmed failing first — 0 anchors, `ref_anchor
     not in anchors`): gold `Asai2023` + a printed "Asai, T. ... 2023 ...
     (Redlich, 1993) ..." line — the SAME citekey collides with gold, and
     the SAME line separately names "(Redlich, 1993)", which
     `detect_author_year_citations` mints as a spurious Citation whenever
     the line is not excluded. Fixed: on a filled collision,
     `add_reference_objects` still attaches the `role="bibliography"`
     realization to the FILLED Reference (guarded by `not any(z.role ==
     "bibliography" ...)`, same as the fill branch), and skips only the
     object creation/fill. After the fix: `bibliography_section_anchors`
     contains the printed line's anchor, and `detect_author_year_citations`
     with that exclusion set adds 0.
  2. IMPORTANT. `add_reference_objects`'s gold-skip can leave `n == 0` even
     when `parse_bibliography` found real entries (every one collided with
     gold) — a case `cmd_bibliography`'s `if n == 0:` gate conflated with
     "the heuristic found nothing at all", wrongly falling into
     `build_bibliography_from_source` (the keyless-arXiv path) and ingesting
     an UNRELATED `texsrc/*.bib` that has nothing to do with this citekey.
     REPRODUCED (test_collision_only_entries_do_not_wrongly_trigger_the_
     source_fallback, confirmed failing first — an unrelated
     `Someoneelse2050` Reference appeared). Fixed: the gate is now `if n ==
     0 and not entries:` — only fires when the heuristic parse found
     nothing, not when it found entries that all already had gold coverage.
  MINOR. `_existing_citation_spans`'s degenerate `(stream, anchor, None,
  None, citekey)` key (a Citation with no offset/length — a whole-line
  claim from `latex_source`/`markdown_source`) is documented as currently
  unreachable as a bug: `detect_numeric_citations`/`detect_author_year_
  citations`, its only callers, always construct a real `(offset, length)`
  pair for every candidate, so their own identity tuples never collide with
  a degenerate one.

  Both fixes verified by reverting each hunk in isolation and re-running its
  test (failed for the stated reason), then restoring.

CONCERNS
  The cross-detector citekey case mismatch named above
  (`detect_author_year_in_objects` folds to lowercase, `detect_author_year_
  citations` preserves case) is real and unfixed — it is the reason the
  provenance-gate alternative was rejected rather than shipped, and it would
  also let `link_citations`'s exact-key fast path miss a citation bibsource
  detected but bibliography's own detector would independently re-derive
  under a different-case key, on any document where BOTH detectors ever run
  against the same text. Not encountered on penev_A/Steerable (bibsource
  never detects on either — no `.bbl`/`.bib`), so not measured end-to-end;
  named rather than guessed at.
  `add_reference_objects`'s gold-skip changes `n` (the "Parsed N bibliography
  entries" count) to exclude entries that collided with an existing filled
  Reference — a legitimate, if forceful, mid-flight — no production call site
  or existing test depended on the old (always-`len(entries)`) semantics.
  The penev_A/Steerable library documents were left in the POST-FIX,
  freshly-verified state (matching 010's own precedent — the library is
  regenerable, backups are at `out/648/`), not reverted to the pre-task
  snapshot.

DECISION IN ONE LINE
  `bibliography` after `bibsource` prints the stored citation-link state
  (not a stale or this-run-only count) at both its early-return and its
  completed-run exits, never re-detects a citation it already has (identity
  = anchor+span+citekey), and never lets its own heuristic References-
  section parse duplicate a Reference that is already filled — the gate
  that decides whether to run the heuristic parse at all is left as "does a
  filled Reference exist", not switched to provenance, because the fixture
  and the corpus check together prove ONLY the count/duplication fixes were
  needed to make nothing move, and opening the gate further was not
  measured safe against the cross-detector citekey mismatch named above.
