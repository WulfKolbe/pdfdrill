THE FINDING — WHERE A CITATION'S SPAN COMES FROM, AND WHAT IS WRONG WITH IT
  The brief suspected the three `bibliography.py` detectors record no span at
  creation. They DO — all three write `offset`/`length` on a `surface`
  Realization, and on penev_A **0 of 81 citations lacked a span**, before or
  after. The defect is a different one and it is the reason citations did not
  reach the prose:

  A CITATION GROUP WAS N OBJECTS SHARING ONE SPAN.
    `detect_numeric_citations` (`[1,2,3]`), `detect_author_year_citations`
    (`(Oja 1989; Sanger 1989)`) and `detect_author_year_in_objects` each
    create one Citation per key and gave EVERY one of them the span of the
    WHOLE GROUP. The projector then substituted them one at a time, and
    `_apply_line_substitutions` (correctly, defensively) drops a substitution
    that overlaps one already accepted — so one key won and the rest were
    dropped on the floor. penev_A: 11 spans hold 25 citations; 14 citations
    were lost that way and with them 12 of 52 REF tiddlers' only inbound
    link. `(Linsker 1988; Oja 1989; Sanger 1989; Földiák 1990; Plumbey 1991)`
    is one span at offset 1, length 65 carrying four Citations; one survived.
    This is 646-c, measured and now fixed.

    FIX ROUND 1: all three detectors now record the span of the KEY, not of
    the group — the part's own `Surname … year` extent for the author-year
    pair (`_AY_STOP`, `_YEAR` and the surname match already give it), and
    `_numlist_spans` for the numeric one (`_expand_numlist`'s split and range
    guard, with positions; numbers expanded out of `3-5` share the range
    token's span, which is the truth — `4` has no text of its own). Grouping
    a shared span in the projector, which is what round 0 did, is the same
    fix seen from one step too far downstream: it makes the KEYS reach the
    page and still has to delete every character between them, because with
    one span covering the whole parenthetical the projector cannot know where
    a key ends. That is the content loss below.

  AND `CitationProcessor` (model build, the `[key]` scan) does the opposite:
    `_split_offsets` gives each key in `[a, b]` its OWN sub-span. Nothing was
    dropped there — but each key was replaced separately INSIDE the source
    brackets, and the `CIT` template renders `[<$link…>key</$link>]`, so the
    reader got `[[a], [b]]`.

  Both shapes are the same fact: a citation group is ONE piece of prose, so
  it is ONE substitution.

  AND THE SUBSTITUTION HAS TO BE LOSSLESS (fix round 1). A group is replaced
  by one `{{REF||CIT}}` per key with every character BETWEEN the recognised
  spans emitted verbatim, and only a bracket pair that wraps nothing else is
  swallowed. Round 0 replaced the whole group extent and deleted what no key
  covered: on penev_A that was `Földiák 1990` (a reference the paper makes,
  which no detector recognises — 645-b), the phrase `(see the review by )`,
  and every `; ` separator — 158 characters across 11 paragraphs, MEASURED by
  projecting the frozen before-model with the round-0 code and diffing the
  paragraph prose with transclusions stripped. 0 characters go the other way.
  A group that is NOT wrapped by a bracket pair of its own keeps its
  parentheses, so `(see Smith 1999 for a review)` stays a parenthetical.

  AND ONE SPAN WAS BEING GUESSED. `detect_author_year_in_objects` reads an
  OBJECT's joined text and recorded `m.start()` — a position in THAT text —
  against the object's own Realization, whose `start` is the object's FIRST
  line. On any paragraph longer than one line that offset names a character
  position that does not exist on that line: the projector substitutes the
  wrong stretch of prose, or (once the offset runs past the line) nothing.
  It is now LOOKED UP: `_span_on_its_own_line` walks the lines the
  realization spans and returns the group's real position on the line it is
  actually on. When no line reproduces the group (a mutator rewrote the
  object's text) NO span is recorded — the citation is still anchored, so it
  still gets its Reference stub and its `cites` edge, and `spans_unrecorded`
  counts it. A position is never invented (rule 5).

A SECOND FINDING, NAMED NOT FIXED — 645-b
  `detect_author_year_citations` (the mathpix-lines detector, which produced
  80 of penev_A's 81 citations) matches a surname with
  `\b([A-Z][A-Za-z\-']{1,})` — ASCII only. `detect_author_year_in_objects`,
  the same job on the object path, uses `_AY_SURNAME`
  (`[A-ZÀ-Þ][A-Za-zÀ-ſ\-']{1,}`) plus `_fold_key`. So the group
  `(Linsker 1988; Oja 1989; Sanger 1989; Földiák 1990; Plumbey 1991)`
  produces FOUR citations on penev_A and not five: `Földiák` matches
  nothing and the reference is silently absent from the model. `Wässle` is
  the same miss on two more penev_A lines. Confirmed by running both patterns
  against the strings. Not fixed here — a surname class change alters
  citekeys corpus-wide and deserves its own measurement, not a line inside a
  task about transclusion. What fix round 1 DOES guarantee is that the
  unrecognised name is no longer DELETED from the page: it stands as prose
  next to the keys that were recognised, which is what makes the gap visible
  to a reader instead of silent.

CONCERNS
  `group_text_kept` counts characters in the substitution INDEX, which is
  built for every line that carries a citation — including the footnote lines
  no paragraph body reads (645-a). It is therefore an upper bound on what
  reaches the page, not a count of characters in the output; the 158-character
  figure above IS a count of the output, taken by diffing two projections.
  penev_B's model changed materially in this run — 25 Citations and 23
  Reference stubs that were not there before, because `bibliography` had
  never been run on that document. That is a real improvement to the
  document and it is also the reason penev_B's before/after is not a
  like-for-like delta; it is labelled as such above and nothing is inferred
  from it that penev_A does not also show.
  `model --force` was run on penev_A to reach the LAST stub the fix had not
  touched: `CitationProcessor` creates stubs at model-build time (the one
  `[dB]` citation), so `bibliography --force` alone left that stub claiming
  its line and the Paragraph+Reference count read 1 instead of 0. Both
  documents were therefore rebuilt from `lines.json`; penev_A's object count
  (1405), anchor count (3178) and unclaimed count (243) are unchanged by the
  rebuild, which is the check that it changed nothing else.
  The residue is 645-a and it is the honest answer to the brief's "expect 52
  of 52": 48 of 52 on penev_A, and the four that are missing are missing for
  a reason that is written down and measured, not for an unknown one.
