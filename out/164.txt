   rows on the page                31   (12 + 8 + 11; the table runs on to p86)

Counted from the born-digital text layer with `pdftotext -layout`, every matched
row having exactly six cells. The page was extracted with `qpdf --pages`, which

it re-encodes the page and would have made the input a variable of its own.

WHAT MATHPIX RETURNS, EITHER WAY
------------------------------------------------------------------------------
   lines            6   (text 2, math 3, page_info 1)
   rows recovered  19  of 31
   cells recovered 92  of 186   (49.5%)
   rows with all 6 cells  4  of 31

The dominant defect is column merging: the page has two side-by-side blocks,
and MathPix runs them together into one row, so a left-hand row's coefficients
are followed by the right-hand row's equation:

   \lambda_{0}-\lambda_{2}=1 \quad 1 \quad 0 \quad 0 \quad 0 \quad
       \lambda_{0}+\lambda_{1}=1

Six such merges per run, identical in both arms. This is precisely the failure a
document-layout pass would be expected to fix, and it is unchanged by the flag.

WHETHER THE OPTION WAS HONOURED — THE PART THAT NEEDED CONTROLS
------------------------------------------------------------------------------
A null result from an option the server ignored says nothing about the option.
Three controls, because the first two were not enough:

  1. Invalid value.   {"enable_document_layout": "banana"}      -> HTTP 200
  2. Nonexistent key. {"totally_bogus_key_xyz_9f": "banana"}    -> HTTP 200

     The endpoint validates nothing. Acceptance is not evidence of anything,
     and GET /v3/pdf/{id} does not echo the options back — its keys are
     app_id, conversion_status, group_id, input_file, num_pages,
     num_pages_completed, pdf_id, percent_done, status, version.

  3. Is options_json read at all? Yes — proved on output, not on status.
     Our nested conversion_options set the markdown delimiters to $ / $$.
     The returned .md contains 6 occurrences of "$$" and zero of "\[" or "\(",
     which are MathPix's defaults. The document we sent was converted under
     options we supplied.

So options_json reaches the converter and is applied. The top-level key was
transmitted in a channel demonstrably read, and changed nothing.

One caveat I will not paper over: a fourth attempt, {"alphabets_allowed":
{"en": false}}, also produced byte-identical output. That option is documented
for /v3/text and may simply not apply to /v3/pdf. It means I have shown that
top-level keys in this request are read for some options (control 3, nested) but
I have not independently shown that a top-level key ever changes /v3/pdf output.
The honest scope of the result is therefore:

   Adding enable_document_layout to options_json on /v3/pdf-file, as we send it,
   changes nothing about this page — not the text, not the cells, not the
   confidence. Whether MathPix supports the option on this endpoint under some
   other spelling or placement is not settled by these runs, and the API gives
   no way to ask.
